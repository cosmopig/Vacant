**結論：第 97 輪的原始碼掃描讀進去的字，超過一半是註解不是文案；
修好之後原始碼路徑自己就看到了 `phone.js:256`——那一條第 98 輪要靠
rendered DOM 才看得到。候選 1 → 2。文案一個字都沒改。**

---

## 一、病因：第 98 輪寫的那個診斷是錯的

第 98 輪把病因記成「分支順序」——`_JS_STR` 把 `'…'`／`"…"` 排在反引號分支前面，
所以 `class="cap"`／`$('ripple')` 會「先配對」。

**那個診斷不成立。** 正則的交替只在**同一個起始位置**上比先後；單引號與反引號
不可能從同一個字元開始，調換分支順序不會改變任何一個 match。照那個診斷去修，
會得到一支「改過而且沒有變好」的程式，而 fixture 未必擋得住。

真正的病因是**配對錯位的連鎖**：

```python
_JS_STR = re.compile(r"""'([^'\\\n]{2,})'|"([^"\\\n]{2,})"|`([^`\\]{2,})`""")
#                                                            ^^^^^^ 內容不准含反斜線
```

反引號分支的內容類別是 `[^`\\]`。檔案裡**第一條含 `\` 的模板字面量**（`\n`、
`\`` 之類）就配不起來，掃描指標於是落進那條模板的**內部**；從那裡開始，
每一個反引號都跟「錯的另一半」配對——抽出來的是模板**之間**的程式碼。
`vacant_hm/world/js/phone.js` 的實測：

```
246 ';\n  } else {\n    head = '                                ← 兩條模板中間的程式碼
248 'cap'                                                        ← 屬性值
250 ";\n  }\n\n  $('ripple').innerHTML = head +\n    "            ← 又是程式碼
254 'bound'
```

三條 `head = \`<p class="cap">…\`` 的文案，一個字都沒進來。
**單點錯配會連鎖到檔案結尾**，所以越後面的文案越抽不到——這解釋了為什麼
`phone.js` 壞得最凶（那批模板在檔案後半）。

修法不是調順序，是把正則換成**逐字元走訪的 tokenizer**（`js_strings`）：
認跳脫字元、`//` 與 `/* */` 註解、正則字面量、模板裡的 `${}` 巢狀。
洞用 `▮` 頂掉讓句子不被切斷（`牠${who}被抓到了` 在洞的位置切開，
同句掃描就永遠看不到這一句），洞內的字串本身也遞迴抽出來
（`${bad ? '被抓到' : '通過'}` 兩個分支都是文案）。

## 二、兩個探針都先驗過，才准採信任何數字

**P5 tokenizer fixture（13 格，`--tok-test`）**。關鍵是它有「**不准抽到**」那半：
本輪的 bug 不是少抽，是**抽錯東西**，而只驗「文案有沒有抽到」的探針對那個形狀是瞎的。

- 一定要抽到：含 `\n` 的模板 · 跳脫模板**之後**的下一條 · 含 `class="x"` 的模板 ·
  跨行模板 · 洞不切斷句子 · 洞內兩個分支 · 字串裡的 `http://`
- 一定**不准**抽到：行註解 · 區塊註解 · **兩個模板之間的程式碼**（T4，本輪 bug 的形狀）

`--tok-test` 第一次跑是 **11/12，FAIL 的是 T3——而程式的輸出是對的**。
T3 原本斷言「模板整條抽出來時不准含 `cap`」，但 `class="cap"` 本來就是那條模板的
原文，那個斷言等於要求程式做錯事。**探針自己寫錯一格。**
改法不是刪掉意圖：T3 的斷言改對，另加 **T13** 驗後果——屬性若真的搶走配對，
**後面那條字串會不見**。13/13。

**P6 量尺 fixture（4 格）**。量尺（`--cjk-audit`）不解析字串，只問
「這段中文有沒有被讀進去」，而且**故意另寫一份** `comment_spans`：
量尺跟待測物共用同一份程式的話，同一個判斷錯誤會同時把某段中文
「排除在分母外」又「抽不到」，兩邊一起錯，結果是漂亮的 0 漏失。

量尺第一版也是錯的：逐行看「開頭是不是 `//`／`*`」，對 `vacant_hm/js/app.js`
那種**續行不加 `*`** 的區塊註解全部漏判，於是 legacy 量出 84.7% 漏失、
分母 4184 段裡塞滿註解。改成掃區間之後 legacy 是 **12.5%**（392 段漏 49 段）。
**84.7% 那個數字是量尺壞掉時量出來的，作廢。**

**量尺已知的限制（照記）**：它用「這段中文有沒有出現在抽出來的字串裡」判定，

全部是這種情形（`sampler.js:127–130`、`phone.js:226/230` 的註解在引用自己的文案），
**不是 tokenizer 抽錯**。

## 五、這件事回頭改了什麼

1. **第 97 輪 `s7_v1_CLAIM_AUDIT.md` 的「原始碼 53652 字元」覆蓋量閘門，
   不能再當成覆蓋量的證據**——那個數字一半以上是註解與程式碼。
   該報告已加註記指向本檔。掃描的**判定結論**（哪幾條踩到）本輪重跑後
   沒有任何一條消失，只多了 `phone.js:256`。
2. **「探針要先驗」這條紀律本輪兩次都收到錢**：tokenizer fixture 抓到我自己
   寫錯的斷言（T3），量尺 fixture 逼出量尺第一版對區塊註解全漏判。
   兩次都是**探針先錯**，而兩次的錯都會讓最終數字看起來更漂亮
   （T3 若照原樣通過就少一格覆蓋、量尺若不修就會給 legacy 一個誇大的 84.7%，
   讓「修好了」顯得更有功勞）。
3. **診斷寫進交接紀錄之後不會自動變成真的。** 第 98 輪那個「分支順序」的診斷
   是在正確觀察到症狀之後推錯的因，而它讀起來完全合理。
   下一輪照著修的人如果沒有先重現，會修一個不存在的 bug。
