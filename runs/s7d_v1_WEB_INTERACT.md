# S7d · 官網互動後才存在的文案，對上 S6 的紅線

第 100 輪（2026-08-17 UTC）。**一個字的文案沒有改**（規則七）。
本輪只動 `Vacant/runs/`。

## 一、補的是哪個洞

第 97 輪掃的是原始碼；第 98 輪掃的 rendered DOM **只涵蓋 `vacant_hm`**。
`vacant-docs-web`（專題官網）的互動狀態**兩條路都沒有看過**——而它那支
`js/main.js` 有六組互動，字全是點下去之後才進 DOM：

| 互動 | 只有互動後才存在的字 |
|---|---|
| 十秒找 bug（`resolveGame`） | 「你是少數／你點到了真的錯誤」·「沒關係，沒有人找得到」 |
| 共同盲區揭曉 | 「五個檢查者用的是同一款 AI……60% 錯在同一個答案」 |
| 收據逐項組裝 | 七列，含第 06 列「有沒有被抽查／已列入第 08 次重跑」 |
| 路由開關 | 「有可究責層」＋「被交給破壞者的工作：N 件」（N 由序列算出） |
| 團隊物件 | 「姓名 ／ 角色」讀值 |
| 全站目錄 | `<dialog>` 開啟 |

原始碼路徑看到的是七個彼此獨立的字串陣列，**看不到它們在畫面上相鄰之後長什麼樣**。
第 98 輪已經證明過那個形狀（跨元素的因果鏈，句級掃描結構上看不到）。

工具：擴充既有的 `runs/s7b_interact_dom.py`（`--sweep-web`／`--canary-web`／
`--check-web`），**沒有寫第二份**——同一個 `Driver`、同一台
`chrome-headless-shell`、同一份 `vacant-docs-web/probe/cdp.py`（HANDOFF §8）。

## 二、結果

### ① 官網互動路徑的新候選 ＝ **0 條**

```
--scan                          原始碼 49 檔 · 27179 字元 · 候選 2
--scan --dom runs/s7d_dom       ＋ DOM 9 檔 · 57732 字元 · 候選 2   ← 新增 0
--scan --dom runs/s7b_dom       ＋ DOM 21 檔 · 20336 字元 · 候選 15（第 99 輪，未變）
```

那 2 條都是既有的、來自 `vacant_hm` 的（`index.html:111`「抽到就扣分」、
`world/js/phone.js:256`「重跑抓到了……一段時間拿不到工作」）。

**這個 0 可以採信**，因為 D1 探針自驗雙向都過（第三節）：同一條管線、同一個官網頁面，
只差「有沒有點下去」，注入的正樣本在點擊前掃不到、點擊後掃得到。

### ② 比 0 更有資訊的一條：官網**根本沒有〈排除類〉這個詞族**

另寫一段獨立計數（不經候選邏輯，直接數詞頻）：

```
官網 DOM（9 個互動狀態）〈排除類〉：一個都沒有
官網原始碼（index.html ＋ main.js，含註解）〈排除類〉：一個都沒有
官網 DOM（9 個互動狀態）〈抓到類〉：抽查 50 · 抽樣 36 · 被抽 5 · audit 72
```

〈排除類〉＝`排除／踢出／淘汰／停權／出局／拿不到工作／不再派工／再也／永久／
slash／扣分／降權／封鎖／剔除`。全站（含互動後）**零次**。

所以官網「沒踩到 S6 紅線」不是因為它把歸因寫對了，而是因為
**它從頭到尾沒有講「後果」這一段**。`--diag` 的形狀直接對上：
官網的 DOM 貢獻了 165 句只中〈抓到類〉的句子、**0 句只中〈排除類〉**；
10 句只中〈排除類〉的**全部來自 `vacant_hm`**。

這是描述，不是建議。要不要在官網補上「被抽查到之後會怎樣」、補的話重心放哪，
是敘事決定 ⇒ 規則七，不拍板。**但若將來要補，這裡是 S6 紅線最可能被踩到的位置**——
因為現有文案已經把「抽查／抽樣」講了 91 次，後果句一旦接上去，最順的接法就是接錯的那個。

### ③ `audit: 72` 是裝飾不是文案（照記，免得下一輪把它當證據）

那 72 次全部來自十秒遊戲的 216 個 code-token（`audit4`、`rerun7` 之類），
是視覺亂數不是句子。〈抓到類〉的**中文**計數才是有意義的：`抽查 50 · 抽樣 36 · 被抽 5`。

### ④ 兩個「看起來是互動才出現、其實載入時就在 DOM 裡」的東西

- **宣稱卡背面**：`claim-card__back` 的字在頁面載入時就寫進 DOM，翻面只換 CSS。
  所以結論 09「抽查結果應影響下一次分配」與其背面「它提高作惡成本，不等於每次都對」
  **原始碼路徑本來就看得到**，不是本輪補的。
  （順帶：那句「提高作惡成本，不等於每次都對」正是誠實邊界句的正確寫法。）
- **全站目錄 `<dialog>`**：關閉狀態下內容已在 DOM。
  所以那一格的 D3 判準用的是 `dialog.open === true`（後果），**不是字比對**——
  拿它的字當「互動後才存在」會是一個必過的假判準。
  這一條是寫程式時當場發現並改回事前登記寫法的，不是事後補的理由。

- `D2` 驗的是**後果不是前提**：不問「`main.js` 載入了嗎」，問

  在說跟資料不同的話——第 68 輪踩過那個形狀（數字沒被編造，是跟錯了句子）。

## 四、覆蓋度：哪些沒掃到（照實記）

1. **`Vacant/vacant/web/app.html`（觀測台）沒掃。** 它要一個活的 dashboard 伺服器
   （`vacant up` 起生態）才有資料；靜態 http 下整頁是空的，掃出來會是**假的乾淨**。
   本輪不併，留給下一輪。
2. **收據只點了「交付 A」一顆。** 讀 `assembleReceipt` 確認五顆按鈕共用同一份
   寫死的 `rows`，只有標題的名字不同 ⇒ 點一顆等於點五顆。這是讀過原始碼之後的
   判斷，不是省略。
3. **共同盲區只點了「通過」一邊。** 同理：`data-blindspot-choice` 兩顆綁的是同一個
   handler、寫進去的是同一段 `innerHTML`（「不管你剛才怎麼選，答案都一樣」）。
4. **捲動觸發的 `reveal` 沒單獨抓。** `IntersectionObserver` 只加 `is-visible`
   類別、不改文字 ⇒ 沒有新字。
5. **鍵盤路徑（`M`／方向鍵／數字鍵）沒走。** 它們只捲動與開目錄，不產生新文字。

## 五、限制

- 這支仍然**只產生候選、不下判定**。第二節①的「0」是「句級同現掃描沒抓到」，
  不是「讀過每一句了」。第二節②那個詞頻計數是全稱的（零次），比候選數強，
  但它只覆蓋列出的 14 個〈排除類〉詞。
- 九個狀態是**疊加**的（後一個是前一個的超集合），所以「某句只出現在哪一格」
  這種問題本輪答不了；本輪要答的是「有沒有出現過」。
