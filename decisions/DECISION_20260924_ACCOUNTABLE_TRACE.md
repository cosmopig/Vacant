## 一、為什麼要改（人類的原話與它推翻了什麼）

2026-09-24 人類看完通用收件口後說：「你現在的這個版本是讓本機多個可以去驗證的驗證器，
**並非是咎責且抓出錯誤點**的東西」，並確認四件事：

| 問題 | 人類的答案 |
|---|---|
| 咎責對象 | **兩者都要**：步驟與行動者（agent／子 agent／模型） |
| 錯誤點 | **追到造成錯誤的那一步** |
| 後果 | **信譽＋路由** |
| 使用情境 | **人直接用一個 agent**（任務不一定是寫程式） |

以及最終體感：「讓產出越趨近於需求……不是隨便 AI 說什麼算什麼，而是至少經過一連串的追緝，
**就算有問題最後也要提出問題，而不是被上下文淹沒**」。

收件口回答的是「這份繳付物合不合格」。它說不出**哪裡**不合格（`ClaimResult` 沒有位置）、
**哪一步**弄錯的（沒有步驟紀錄）、**誰**弄錯的（沒有行動者），而回饋是一段泛用文字。
0924 論文一句話定位是「**知道誰做了什麼**，出錯時追得回去」——收件口只做了後半的「出錯時」。

## 三、架構

```
每一次工具呼叫（四個 agent 的原生掛鉤 → adapters/hook.py）
   pre  ─→ trace/recorder.pre   掃工作區；和上次不同而中間沒有步驟 ⇒ unrecorded_change（缺口）
   post ─→ trace/recorder.post  再掃；差異＝這一步寫了什麼；輸出與每個檔案版本進內容定址庫
                                 一筆簽章事件：行動者、工具、輸入、輸出、寫入、前後索引
回合結束（Stop）
   check ─→ 契約驗證（intake，不動）＋位置（evidence.locations）＋主動檢查＋人的標記
   blame ─→ trace/blame：失敗的位置 → 寫下它的步驟 → 在重建的前後狀態上重跑 → 錯的值從哪裡讀來
   feedback → 一則事實回饋（位置、錯的值、來源裡的值、第一次出現在第幾步）；KS-1＋無行動者
工作階段結束
   report ─→ 給人的報告：每個未解問題（不被淹沒）、每條缺口、每個結論的等級與證據
   actors ─→ 只有「可證明」進信譽；路由＝給人的建議＋`vacant do --agent auto`
```

一個**專案一條鏈**（不是一個工作階段一條）：子 agent 的寫入和主 agent 在同一個工作區，
分開記就會把子 agent 的寫入誤記成缺口。每一筆帶自己的 session 與 actor。

## 四、七個取捨（與 Fable 設計審查的逐條對照）

設計夥伴審查全文：`ops/accountability/design_review_fable.md`；論文取捨與約束：`ops/accountability/paper_synthesis.md`。量測底稿：
`ops/accountability/capture/`（四個真 binary＋假模型，[RUN] 標記是實跑）。

### 4.1 「錯」由誰決定

三個來源，只有前兩個能擋：
1. **契約**（既有驗證器；`policy.decide` 不動）。
2. **人標記**：`vacant flag <path>[:<行>-<行>] "<哪裡錯>"`——簽章、綁繳付物 sha256＋位置；
   `--required` 時以 `review` 類主張進入裁決（裁決規則不變）；`--dismiss <finding>` 撤銷。
3. **主動確定性檢查**（只提示，不擋）：
   - `unsourced_number`：繳付物裡的數字在這一回合**觀察到的讀取**（釘住的輸入、指令輸出、抓到的網頁、
     其他工具輸出）裡都找不到 ⇒「沒有觀察到來源」，**不是**「錯」；
   - `unhandled_failed_command`：某一步的指令失敗、之後沒有同指令成功重跑，而繳付物宣稱成功。

**不做**：任何模型判斷「這裡錯」；語意式的「報告與輸入一致」（那是換了名字的模型裁判）。

### 4.2 讀了什麼：下限，不是全部

掛鉤看得到工具輸出（Read 的檔案內容、指令的 stdout、WebFetch 的結果、子 agent 的回覆），
看不到模型上下文裡本來就有的東西、殼層指令執行中讀的檔、Codex 託管的 web_search 結果
（capture-codex §0-11）。⇒ **「沒找到來源」永遠不可以單獨推出「agent 的錯」**；
每份報告帶三態 `read_coverage`。

### 4.3 工作區怎麼看（**這一條與 Fable 不同**）

Fable 建議只雜湊契約列出的繳付物與輸入，以守住掛鉤時間預算。**不採用**，理由是量測：
Claude 的 Bash 與 Codex 的 shell 寫檔在**每一個**平台通道裡都只剩指令字串
（capture-claude §0-7、capture-codex §0-10）；Fable 自己的情境 C（`calc.py` 由殼層寫出、
報告抄了它的輸出）要追到「寫 calc.py 的那一步」，就必須看得到契約沒列的中間檔。
折衷：**整個工作區、增量**（大小＋mtime 沒變就沿用雜湊；`.git`／`node_modules` 等排除；
超過 5 萬檔就不追並記成缺口）；每一跑量掛鉤時間的 p95，端到端證據要附上。

### 4.4 何時介入

**偵測在步驟、送達在回合邊界**。Fable 建議每次寫入後就跑便宜的驗證以得到「第一個失敗的步驟」；
這次改成**Stop 時在重建出來的每一步狀態上重跑**——同樣精確（每一步前後狀態都重建得出來），
但成本從每次工具呼叫（30 秒預算、超時就靜默略過＝缺口）移到 Stop（600 秒）。
回饋：一則、≤12 行、穩定的 finding id、「這次新增／已解決」差異；沿用 `max_feedback_rounds` 與
`not_agent_fixable`。OpenCode `run` 沒有交件前回饋的通道（既有邊界），報告照樣產出。

### 4.5 等級與後果

（`provable` 是事實層；其餘都是推論層。過錯**類別**另外標，見 §4.8 K10。）

| 等級 | 意思 | 信譽 |
|---|---|---|
| `provable` | 在重建狀態上重跑，**恰好在這一步**由過轉不過，而且錯的值不在任何釘住的輸入或觀察到的讀取裡 | 對那個行動者 `record_review(0, weight=1.0)`（事實／邏輯維）；**不 slash** |
| `lineage_exact` | 錯的值逐字出現在這一步之前觀察到的**外部**內容（釘住的輸入、網頁、使用者提供的檔） | 行動者不動；來源記一筆計數；報告說「如果這是錯的，是輸入錯」 |
| `lineage_internal` | 錯的值來自更早一步的輸出（子 agent 回覆、指令輸出） | 往上追到產生它的那一步再分級；寫入者不動 |
| `heuristic` | 只有行歷史、沒有確定的翻轉 | 不動；只報告 |
| `gap` | 沒被記錄的改動、掛鉤缺席、逐字稿缺 | 不動任何人；記在「整合覆蓋率」 |

人撤銷（`--dismiss`）會反轉那一筆的信譽效果，帳本兩筆都留。
人**不進信譽表**（Raji；只有一位使用者時替他打分是敵意）。

## 五、今晚能證明什麼、不能證明什麼

今晚只能用假模型（不碰真模型 API）。能證明的是**機制**：
四個真 agent × 四個埋錯情境——A 輸入錯、B agent 憑空寫錯、C 中間步驟（腳本）錯、
D 掛鉤中途缺席（負控制）——外加 A′（輸入經 `cat` 讀進來而不是 Read 工具），
期望 A→`lineage_exact`、B→`provable`、C→`lineage_internal` 指到寫腳本那一步、D→`gap` 而**不是**怪人。
附帶量：在地化回饋有沒有出現在下一次模型請求裡（pi／Claude／Codex 應該有；`opencode run` 沒有）。

**不能證明**：真模型下產出會更接近需求。那要預註冊的實驗（`decisions/prereg/`，M7）：
RS（重抽三次、無回饋）／RF（今天的泛用回饋）／RL（在地化回饋），一般任務與程式任務兩層分開報告，
主要結果 accepted ∧ hidden pass，McNemar RL vs RF。**RL≈RF 也是結果**：那代表追緝的價值只在
給人的報告，不在收斂——事先寫下，免得事後被說成失敗。

## 六、誠實邊界（改碼請保留）

1. 竄改**可察覺**，不是不可能；鏈是本機金鑰簽的，本機 root 可以重簽整條（Figuera）。
2. **完備性要外部錨定**；缺口是「Vacant 看到了但沒有任何一步解釋得了」，看不到的看不到。
3. 讀取是下限；「沒找到來源」≠「編出來的」。
4. 模型 id 來自逐字稿時是**自稱**（`claimed`）。
5. 平行的步驟之間，寫入只能歸給「其中之一」（`concurrent_with`）。
6. 「可證明」的意思是**這個驗證器**在重建狀態上翻轉；驗證器本身可能錯（論文 7.4），所以人可以撤銷。
7. ❌「Vacant 抓出所有錯」「追緝一定正確」「agent 繞不過」——都不准說。
   ✅「**在有紀錄的步驟裡**，這個檢查在第 k 步由過轉不過，而第 k 步是 X 做的；證據可重跑。」

1. **追緝追「那一行」，不是「這個值在不在檔案裡」**：同一個值出現在好幾行時，用逐行對齊把被指出的那一行
   沿著版本往回追；重跑的翻轉也要落在那一行。否則把自己那行刪掉的人會替別人加的那行背事實層的錯。
2. **跑了程式卻認不出是哪一支 ⇒ 推論層**：只有「沒跑程式、值又是這一步寫的」才可能是事實層
   （`python3 -u x.py`、`uv run`、`cd dir &&` 曾經讓「跑腳本的人」背了「寫腳本的人」的錯）。
3. **一則「使用者訊息」不一定是使用者說的**：Claude 背景子 agent 的結果、Codex 子 agent 的任務說明都走
   UserPromptSubmit；前者追到子 agent，後者追到父 agent 的委派。
4. **後果只在病歷驗得過時才記**；病歷的鏈頭另外寫進收件端簽過的帳本（`trace_head`），從尾巴截短對得出來。
5. **給 agent 的文字逐行防呆**：一行踩到 KS-1 或行動者識別，只換掉那一行；隱藏主張一條一行、不標記開著／解決。
6. **憑證檔不進版本庫**（只記雜湊），版本庫 0700／0600；FIFO／裝置不讀。

另外，同日的完備性批判（`ops/accountability/capture/critique.md`）改了信譽鍵：主 agent 的 stream 帶平台前綴
（四個平台共用 `main` 會共用衰減時鐘），並把指令檔（`CLAUDE.md`、`AGENTS.md`）當成模型的輸入來源。

### 審查之後新增的誠實邊界

- **SessionEnd 不保證觸發**（Claude `-p` 有背景 Bash 還在跑時、pi 被 SIGINT／SIGKILL）：那一次沒有逐字稿封存、
  沒有工作階段結束的追緝與結果。`vacant do` 在行程結束後自己追緝，不受影響。
- **等不到 post 的步驟**：它的寫入最多算到同一個行動者的下一步開始為止；之後沒人解釋的改動記成缺口。
  平行執行的平台（Codex、pi）上，這會把還在跑的那一步的寫入記成缺口——寧可沒人解釋，不可錯怪。
- **工作區太大**：掛鉤裡的一次掃描最多 8 秒（掛鉤有 30 秒上限，被砍掉＝靜默略過）。第一次看就超過 ⇒
  改在背景看（`python -m vacant_network.trace.recorder baseline`），背景看完之前的步驟「寫了什麼不知道」
  （不是「沒寫」），那時已經在的值追緝回 UNOBSERVED／gap，不說「本來就在」；背景看不完（超過 5 萬檔）、
  等了 600 秒沒寫回來、或之後的增量掃描也超過 8 秒 ⇒ 這個專案不再逐步掃描，追緝一律 UNOBSERVED。
  這時 agent 仍然收得到驗證器自己的位置（`report.md:2 says "999"`），只是沒有「第一次出現在第幾步」。

### 大專案（同日，量測之後改的）

量測：`ops/accountability/evidence_20260924/perf/`（`ops/accountability/perf_scan.py`，真的掛鉤進入點、含行程啟動）。
第一次量的時候 4 萬檔的第一次掃描要 33.8 秒——超過掛鉤上限。改了四件事：

1. **便宜的內容儲存**：憑證樣式只編一次、版本庫寫入不 fsync（內容定址，讀的時候驗雜湊；當機留下的壞檔
   只會變成「重建不了」）、熱迴圈用字串路徑、沿用的版本不逐檔確認在庫裡（上一份索引是同一個版本庫掃出來的）。
2. **時限與背景**：見上面的誠實邊界。背景看的期間，掛鉤不各自重掃（否則每一步多 8 秒）。
3. **差異索引**：1000 檔以上的專案，每一步的工作區狀態存成對上一份完整索引的差異（每一步 0.9 KB，
   原本 4 萬檔要 4.9 MB）；差異檔用 sha256 指向完整索引，還原出來的狀態同樣被雜湊綁住。
4. **重跑只重建繳付物**：收件口的驗證器只看得到繳付物（`flow._verify_manifest` 只放 manifest 裡的檔），
   追緝重跑卻曾經重建整個工作區——`command` 類主張在追緝時看得到收件時看不到的檔（判決可能不同），
   4 萬檔的專案每條主張還要寫 8 萬個檔。現在兩邊看同一批檔。Stop 掛鉤裡的掃描也套同一個時限。

結果（4 核、本機磁碟、每個檔幾十位元組；掛鉤本身不追緝時約 130 ms；審查修正之後重跑）：

同日對抗審查（`ops/accountability/review_scale/FINDINGS.md`）：8 條全部成立、全部修掉。改了設計的是這兩條——
**開始時沒看到的步驟**（背景還在看第一眼）結束時，上一次看到之後的改動一律記成缺口，而且它不擋別人記缺口；
**讀不回來的狀態**（版本庫被改過或壞了）不再當成空的工作區：碰到它的追緝一律 UNOBSERVED，掛鉤裡則關掉逐步掃描。

### 子 agent 的端到端（同日）

假模型照對話開頭的 `ROLE:sub` 演子 agent，用各家自己的委派工具（Claude `Agent` 前景、OpenCode `task`、
Codex `multi_agent_v1` 的 `spawn_agent`→`wait_agent`、pi 隨附範例擴充的 `subagent`）。情境 E：子 agent 算錯寫進
`figure.txt`、主 agent 照抄進報告 ⇒ 四個 agent 都指到子 agent 寫錯的那一步（`lineage_internal`，帶子 agent 的 id），
主 agent 收到的回饋是「從第 2 步抄來的；第 5 步寫進報告」（沒有行動者）。

改了設計的一條：**pi 的子 agent 是另一個行程**，原本被當成另一個主 agent（自己的工作階段、回合結束跑驗收、
結束時交件）。現在 Vacant 的 pi 擴充在每個工具呼叫期間把 `VACANT_PI_PARENT`（最上層的 session、呼叫 id、
代理人名）放進環境；子行程讀到就回報成那個工作階段的子 agent，回合結束不跑驗收、結束送 `subagent_stop`。
邊界：平行的工具呼叫下標記可能指到兄弟呼叫（工作階段仍然對）；不是從 pi 擴充啟動的 pi 行程不會被認成子 agent。
