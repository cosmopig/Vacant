# D2′ 結論（草稿）：紀錄知道每條宣稱來自哪裡，來源變了只重查受影響的那幾條，有沒有用？

> 所有數字都附來源檔路徑（`~/dev/ops/d2_results/<批次>/`：`score.json`、`audit.json`、`analysis.json`、`analysis.txt`）。

## 一頁摘要（給擁有者）

**問的是什麼。** agent 照幾張網頁寫了一份有 20 個數字的報告，之後網頁陸續改了。要讓報告保持正確，有三種做法：
(b) 每次都叫 agent 把整份重查一遍；(d) 只告訴 agent「哪幾頁變了」；(c) 用 Vacant 的紀錄——紀錄裡有「每個數字是從哪一頁讀來的」——只把受影響的那幾行交給 agent。
c 是「紀錄本身的用途」，不是「叫它重做」。

**第一輪的答案：照事前定好的標準，沒有過。**（9B、Haiku、留出三批都判 FAIL）
- 省：9B 上，c 用的 token 是整份重查的 **1/3.6**（區間 1/3.0–1/4.4），是 d 的 1/2.1；c 從來沒有把對的值改錯（d 改錯 80 次、b 12 次）。
- 漏：但 c 漏掉的過期數字比整份重查多（19.2% 對 4.7%），超過事前定的容許範圍（10 個百分點）。
- 為什麼漏：**全部是因為紀錄沒認出「這個數字是從哪一頁來的」**——agent 抓網頁的寫法很多（存成檔再讀、寫成迴圈、和別的指令混在一起），產品只認得其中幾種。
  紀錄認得出來源的那 36 組裡，c 的漏抓（6.9%）和整份重查（4.2%）、頁面通知（7.2%）差不多。
- Haiku（雲端模型）：它最常用迴圈抓網頁，產品幾乎全部認不出（覆蓋率 30%）⇒ 漏了一半；而且雲端 agent 每次執行都帶著一大段快取的系統提示，只重查幾行也省不了多少（美元只省到 1/1.7）。
- 留出（另一個人寫的、沒看過的網頁結構）：覆蓋率 72%；漏抓差沒有定論（樣本小）；token 省到 1/6.5。

**第二輪改了什麼。** 只依第一輪主批次的紀錄（沒有看留出批次的逐條結果），讓產品認得更多抓網頁的寫法（迴圈、存檔再讀、混在其他指令裡），
重新凍結、換新的題目重新預註冊。另外加了「用紀錄驗收修正」：agent 改完後再用紀錄檢查一次，沒重讀來源就改、或改完仍和來源不符的，退回一次。
用第一輪的初稿重播，覆蓋率 9B 753→874／1000、Haiku 300→1000／1000。**第二輪的實跑結果：待填。**

**紀錄能不能被稽核。** 能，而且有人獨立驗過：
- 沒參與的稽核者自己寫程式、只讀紀錄，重算出的分數和我們的逐列一致（9B 主批次 17,000 列，0 不一致）；
- 每一條鏈的雜湊串接與簽章都驗得過（250 條），引用到的內容物件全部對得上；
- 每一個錯誤都歸得到是哪一段出問題（出處沒記到／記錯頁／變動沒偵測到／交辦了但 agent 沒重讀／重讀了沒改對／初稿就錯）。
- 抓不到的：同一個使用者帳號下，有人用新鑰匙把整條鏈重簽並改掉信任清單（要靠推到遠端的鏈頭錨點才抓得到，第二輪起每批都寫）；模型呼叫數只在 harness 的紀錄裡，不在簽章鏈上。

**另外發現的一個產品錯誤（已修）。** 產品預設的「交件前檢查」會把 agent 抓下來存成檔、再讀進來的正確數字誤判成「沒有出處」，叫 agent 多改兩輪、還把對的數字標成「假設」。已修並有測試。

## 一、設計（摘要）

- 教材：虛構產品頁（第一輪主批次：seed 20261126、50 組；第二輪：seed 20261137、50 組）。每組 5 頁、20 條宣稱、4 個週期：2 個有事實改動（F）、1 個只有無關改動（N）、1 個沒變（Z），順序洗牌。改動清單封存、agent 看不到。
- 臂：a 不維護；b 整份重查；c 依紀錄只交辦受影響的行；d 只告訴哪幾頁變了。第二輪另有 c_verify（c＋用紀錄驗收修正）、d_diff（d＋頁面文字差異）。
- 判準（事前寫死，兩個家族各 α/2）：出處覆蓋率 ≥80%；c 的漏抓（真值變了、週期開始時是對的宣稱）不比 b（或 d）多 10 個百分點以上（單側 97.5% 上界）；token 比 b/c 區間下界 ≥3（d/c ≥1）。Haiku 用美元（看過小量試才定的）。
- 評分是機械式的（改動清單對答案），不用模型當裁判。
- 預註冊與每一次設計變更：`ops/d2/plans/*.json`、`ops/d2/DESIGN_LOG.md`、`ops/d2/plans/ADDENDA.md`。

## 四、紀錄能不能被稽核（細節）

- 獨立重算：vacant-hope 派的稽核者不 import 我們的程式，從鏈、存取紀錄、改動清單重算分數，0 不一致；並抓出我們稽核腳本的三個錯（歸因表、出處表、驗鏈太鬆），已修、複查通過。
- 驗鏈現在檢查：每一筆的雜湊、串接、創世雜湊、Ed25519 簽章、簽章者在信任清單、步驟引用的輸入／輸出／索引、提示文字、索引裡每個檔案物件。
- 已知抓不到：同帳號用新鑰匙整條重簽＋改信任清單（第二輪起靠推上遠端的錨點檔 `anchor_d2.py`）；模型呼叫數不在簽章鏈上；簽章鑰匙 agent 讀得到（產品已知限制）。

## 五、限制（一定要一起講）

- 教材是合成的；第一輪的先導與主批次是同一個產生器（「調校過的同分布」），留出才是沒看過的結構。
- c 的漏抓幾乎完全由出處覆蓋率決定；覆蓋率又取決於 agent 抓網頁的寫法。
- 週期類型比例（F,F,N,Z）是設計參數；token 比主要來自 N、Z 週期不叫 agent，各類型的數字分開附在 `score.json`。
- 掛鉤用 observe 模式（不代表產品預設的 evidence 模式）。9B、12B、Haiku 各自判定。Haiku 的成本量是看過小量試才定的。
- 第二輪沒做：b2／d2（提示加強的敏感度）、c_every（沒出處的行每週期都交辦）；第二輪 12B 只跑 1003 的 25 組。
