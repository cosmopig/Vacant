## 一頁摘要（給擁有者）

**問的是什麼。** agent 照幾張網頁寫了一份有 20 個數字的報告，之後網頁陸續改了。三種維護做法：
(b) 每次叫 agent 整份重查；(d) 只告訴 agent「哪幾頁變了」；(c) 用 Vacant 的紀錄（紀錄裡有「每個數字是從哪一頁讀來的」）只把受影響的那幾行交給 agent。c 是「紀錄本身的用途」，不是「叫它重做」。

**白話總結。** **第三輪（產品 v3；這批教材、這個 9B）：**兩個主要比較照事前規則都過關（EFFECTIVE），但過關的餘地很小：同協定的另一臂（cCG）若當主要臂，對整份重查的漏抓差上界是 +9.6pp（門檻 10pp）、對頁面通知＋差異是 +10.8pp（未過）；三臂合併（24/661）對整份重查是 +1.36pp（上界 3.77）。有事實改動的週期裡 cCGR 只比整份重查便宜 3.5 倍（2.7–4.6）、和頁面通知＋差異一樣貴（1.02 倍）；省下的主要在網頁沒變或只有雜訊的週期。主要臂和產品修正是看過第二輪全部結果才定的；教材和開發資料同一個產生器（同分布確認）；虛構網頁（見第九節）。**但另外兩批都不過：在沒看過結構、每次抓取都有雜訊的新教材上（heldout-v3，25 組），cCGR 多漏（17/64 對 5/64，其中 13 條由越界守衛的 bug 造成）、176 條誤改（其中 145 條由守衛 bug 造成）、和整份重查一樣貴——雜訊讓片段比對幾乎每一行都判成受影響（第十一節）；在雲端 Haiku 上（60 組），Haiku 用變數拼網址的迴圈抓頁，出處覆蓋率 0%（第十節）。****第四輪（產品 v4）修好了這兩個原因（雜訊不再觸發、出口紀錄認得出變數拼網址），但在第四個產生器（36 組）上 9B 與 Haiku 又都不過：同一筆紀錄裡別的欄位剛好也是舊值時，「看值」判成沒變，漏三到四成（第十二節）——這個條件是教材規格硬性要求的（約六成改動宣稱舊值留在同筆紀錄），真實文件比例未知，不能外推；越界守衛的 bug 當時還沒被發現。**以下是第一、二輪：第一、二輪沒有任何一次「用紀錄只重查受影響的幾行」對「整份重查」被判有效。最接近的是 9B 第二輪：漏得不比整份重查多、也沒改壞東西，token 省 2.94 倍，差一點沒到事前訂的 3 倍。在刻意加難的新教材上，便宜版傾向多漏；保守版不多漏，但只省約 3 倍而且沒能確定，並且比「只告訴哪幾頁變了」貴。全部都是虛構網頁、一個本機 9B 模型（Haiku 另算），而且結果高度依賴 agent 用 curl／wget 這類指令抓網頁。

**名詞。** 「pp」＝百分點（漏抓率 5% 對 2% 差 3pp）。「上界」＝統計上能排除的最壞情況（97.5% 信心的單側上限）；事前規定：漏抓差的上界要小於 10pp 才算「不多漏」。「區間」＝成本比的 97.5% 信賴區間；下界要 ≥3 倍（對整份重查）或 ≥1 倍（對頁面通知）才算省。判定：EFFECTIVE＝三項都過；FAIL＝至少一項的點估計就沒過；UNRESOLVED（未定論）＝點估計過了、但區間還太寬；INCOMPLETE＝沒跑完。

**第一輪：9B 與 Haiku 都判 FAIL；12B 沒跑完（INCOMPLETE），已完成的部分覆蓋率也沒過。** 原因只有一個——紀錄常常認不出「這個數字是從哪一頁來的」。agent 抓網頁的寫法很多（存成檔再讀、寫成迴圈、和別的指令混在一起），產品只認得幾種：9B 覆蓋率 75%、Haiku 30%、12B 63%。認不出來源的行，c 就不會交給 agent，於是漏掉。

**第二輪：讓產品認得更多寫法，換新題目重新預註冊。**
- **在和開發資料同一個產生器的題目上（9B、Haiku 主批次），紀錄認得出來源之後，c 不再比整份重查多漏，而且不改壞東西**（這是 9B 第二輪主批次；在 r2heldout_b，c 有 20 次誤改，其中 18 次是同一次整份覆寫）。
  - 9B（50 組）：覆蓋率 97%；c 漏 3/196、整份重查漏 10/196（差 −3.6pp，這只是點估計，上界剛好 0）；c 改錯 0 條。token 省到整份重查的 1/2.94——事前門檻是 1/3，**差 0.06，照規則判 FAIL**；和「只告訴哪幾頁變了」比，c 少漏、省 1/1.56，但區間下界 0.96 沒到 1 ⇒ 未定論。
  - Haiku（50 組，雲端）：覆蓋率 100%；三種做法都幾乎不漏；美元省到整份重查的 1/2.28（沒到 1/3 ⇒ FAIL）；**比只告訴哪幾頁變了省一半、不多漏 ⇒ 這一個比較判 EFFECTIVE**（但成本用美元是看過小量試才定的，d 也沒有附文字差異）。
- **在沒看過、刻意加難的網頁結構上（60 組確認批次 r2heldout_b）：便宜的 c 傾向多漏（點估計 +8.75pp、上界 15pp，未定論）；保守的 c_verify 沒有多漏（+1.25pp、上界 5pp），但省的倍數區間太寬。**
  - 事前登記的主要臂是 c_verify——**它的實際做法是：沒有出處的行每個週期都交給 agent 重查，改完再用紀錄檢查一次、不對就退回一次**（不是「用紀錄把出處補回來」，見第五節）。
    c_verify 漏 10/240、整份重查漏 7/240（**不多漏**）；token 是整份重查的 1/3.12，但區間 1.69–6.95 的下界沒到 3 ⇒ **未定論**。和「只告訴哪幾頁變了」比判 **FAIL**——意思是它**比頁面通知貴**（d/c_verify 0.74 倍），**不是多漏**（漏抓 10/219 對 17/219）。
  - 次要（c，沒出處的行只交辦一次）：token 只有整份重查的 **1/9.95**（8.06–12.23），但漏 28/240。c 的 28 個漏抓：13 個出處沒記到、8 個出處記錯頁、7 個交辦了但 agent 沒重讀。
  - 「只告訴哪幾頁變了」（d）在這批**刪掉或改錯 264 條對的行**，其中 236 條發生在只有無關改動的週期（b 26、c 20、c_verify 8）。
  - 留出 v2（20 組，UNRESOLVED）是這批的開發資料，不再當確認證據。
- 12B 第二輪：50 組全部跑完（1003 那半 25 組；1004 那半在 15:30Z 讓位給第三輪、停在 s43，16:25Z 第三輪 1004 那份跑完後照原 root 續跑，18:06Z 完成）。覆蓋率 856/1000＝86% 過；c 漏 14/188、b 10/188（+2.1pp、上界 8.3pp，不多漏）；token b/c 0.85×（0.22–5.17）⇒ **FAIL**；對 d 漏 14/188 對 9/188、d/c 1.40×（0.42–8.28）⇒ 未定論。token 比被 gemma 的 600 秒逾時打亂（1003 那半 38 次、1004 那半 14 次），不宜解讀；呼叫數比 b/c 2.13×、牆鐘 2.99×。稽核 0/25,000 不一致、350 條鏈的雜湊與簽章全過；**但 s43/c_verify 有 16 個被鏈引用的物件被產品的保留 GC 刪掉（blobs_bad 16），那一格的紀錄無法完整驗證——GC 不該刪仍被鏈引用的物件，列為產品待修**；越界讀取掃描 0 筆。

**第三輪（產品 v3）：把第二輪歸因表的三個失敗原因用通用機制補上，在新題目上事前登記再確認。**
- 產品 v3：出處＝候選集合（寫入前讀過、含這個值的所有網址，不必解析指令）＋Vacant 自己存的來源快照；越界守衛；「沒重讀就改」退回一次。網路邊界記錄沒做。
- 結果（60 組，主要臂 cCGR）：覆蓋率 1104/1200（初稿寫對的 1104 條，正確頁全部在候選裡；沒覆蓋的 96 條是 5 組初稿壞掉、行不存在）。註：第三輪的覆蓋率是「候選集合含正確頁」（超集合；每條宣稱平均 2.18 個帶值的候選頁，70% 有兩個以上），不能和第一、二輪的單選覆蓋率並排比。全批 276 次交辦中 55 次（20%）不必要（26 次只因為錯的候選頁變了、18 次是正確頁的雜訊片段）。兩個主要比較照事前規則都過關，餘地很小（見上）。
- 拆解（次要、描述）：和舊協定比，主要的差來自**候選集合＋快照**（c 漏 20 → cC 漏 5、成本更低）。cC／cCG／cCGR 漏 5／16／3：cCG 的 16 條裡 12 條來自 6 個週期，9B **沒抓任何網頁就把交辦的行改成自己編的值**（出處檢查交辦的行是對的）；同樣的事在 cC 發生 2 次、cCGR 3 次——cCGR 的 3 次都被「沒重讀就改」抓到並退回，退回後 6 條全部改對。守衛整批只還原過 2 行，效果沒有量到。
- 邊界測試 v3：python urllib 寫法的出處 120/120（第二輪 0/80），wget 80/80，curl 380/400（s12 初稿沒抓任何頁面、0/20；初稿正確 580/600）；維護 4 週期 cCGR 漏 7/116（全是已交辦但 agent 沒改對，不是出處問題）、改錯 2；沒有對照，只能描述。

**出處記得到的條件**（抓取寫法 × 覆蓋率）：
- r2heldout_b 的 60 組裡 58 組是「一次抓一個網址、印在螢幕」，覆蓋率 1040/1160（90%；沒對上的是較難教材裡的撞值與沒有實體名的句子），2 組存到 /tmp 再讀 20/40。第二輪 9B 主批次各寫法 95–100%（836/860、76/80、20/20、40/40）。
- **邊界測試**（30 組新題目、只看初稿）：叫它用 curl 200/200，不提工具 196/200；curl 被換成失敗的替身後，改用 wget 的 6 組 120/120，**改用 python urllib 的 4 組 0/80**（產品對「自己寫程式抓」一律放棄）；初稿 600/600 全對。只量了初稿的覆蓋率，沒有量維護階段。
- 也就是說：第二輪的產品（v2）**記得到出處的前提是 agent 用 curl／wget**；python 之類自己寫程式抓的認不出。**第三輪的 v3 改用候選集合之後，python urllib 120/120**（邊界測試 v3，見第九節）。

**一定要一起講的限制。**
- 教材是虛構的合成網頁。兩個附帶變因：第二輪 9B 的上下文是 65536（第一輪 32768）；留出 v2 跑在另一台主機。c_verify 是看過留出 v2 的結果後才選為 r2heldout_b 的主要臂；最強的便宜基準 d_diff 沒有在確認批次裡跑。
- 第二輪的產品修正是對著第一輪的資料開發的；「用第一輪初稿重播，覆蓋率 9B 753→874、Haiku 300→1000」是**樣本內**數字。第二輪補的只是「看過的抓法」（迴圈、先存檔再讀、混合指令），而且只認 HTML。
- 留出 v2 的 20 組全部是同一種抓法（一次抓一個網址、印在螢幕），初稿 400/400 全對，**沒有測到抓法的多樣性**；它的規格是針對已知弱點設計的加壓測試，不是盲測。其中 s15 整組 0/20、s05 9/20 沒有出處。
- 只有一個本機小模型（qwen3.5-9b）有完整的第二輪結果。

**小模型被給大範圍指令時，會刪掉對的內容。** 「只告訴哪幾頁變了」那一臂（d）把對的行刪掉：9B 主批次 54 條（3 組整份重寫）、留出 v2 61 條（59 條整行刪除）、r2heldout_b 264 條（263 條刪行或把值刪掉；236 條發生在只有無關改動的週期）。c 只交辦來源變了的行，誤改少得多，但不是零：r2heldout_b 有一次（s56 週期 4）agent 只被交辦 2 行，卻用 write 把整份報告覆寫成 3 行自己編的內容、沒執行任何抓取，一次刪掉 18 行。整份重查（b）在 9B 主批次是 0 條，但在 r2heldout_b 的 b 有 26 條。所以這是「大範圍或頁面級指令＋這個 9B」時明顯，不是「整份重查一定會改壞」。

**紀錄能不能被稽核：能，有人獨立驗過，也有抓不到的地方。**
- 沒參與的稽核者自己寫程式、只讀紀錄，重算出的分數和我們的逐列一致（第二輪 9B 主批次 25,000 列、留出 v2 10,000 列、r2heldout_b 25,200 列，0 不一致）。
- 驗鏈檢查每一筆的雜湊、串接、Ed25519 簽章、簽章者在信任清單、步驟引用的內容、提示文字、索引裡的每個檔案；九種刻意竄改每一種都至少被一層抓到。
- 每個錯誤都歸得到是哪一段出問題（出處沒記到／記錄錯頁／變動沒偵測到／交辦了但沒重讀／重讀了沒改對／初稿就錯）。
- 抓不到或保證較弱的：同帳號用新鑰匙整條重簽＋改信任清單，要靠推到遠端的鏈頭錨點；第一輪 9B 主批次的錨點是結束 3 小時後才寫的（保證較弱）；模型呼叫數只在 harness 紀錄裡、不在簽章鏈上；簽章鑰匙 agent 讀得到。

**另外修好的產品錯誤。** 預設的「交件前檢查」會把 agent 抓下來存成檔再讀進來的正確數字誤判成「沒有出處」，叫 agent 多改兩輪、還把對的數字標成「假設」。已修並有測試（`decisions/notes/NOTE_20261125_ZEROCONFIG_FALSE_UNSOURCED.md`）。

## 一、設計（摘要）

- 教材：虛構產品頁（第一輪主批次 seed 20261126、第二輪 seed 20261137，各 50 組）；每組 5 頁、20 條宣稱、4 個週期（2 個有事實改動、1 個只有無關改動、1 個沒變，順序洗牌）。改動清單封存、agent 看不到。留出 v1／v2 由沒看過出處程式的 agy 另寫產生器（敘述文字、多格式、只給索引頁；v2 另外加難）。
- 臂：a 不維護；b 整份重查；c 依紀錄只交辦受影響的行（沒出處的行只交辦一次）；d 只告訴哪幾頁變了。第二輪另有 c_verify、d_diff（次要）。
- 判準（事前寫死，兩個家族各 α/2）：出處覆蓋率 ≥80%；漏抓差（兩臂週期開始時都對、真值變了的宣稱，配對）單側 97.5% 上界 <10pp；成本比 b/c 的 97.5% 區間下界 ≥3、d/c ≥1。Haiku 用美元。
- 評分是機械式的（改動清單對答案），不用模型當裁判。
- 預註冊、每一次設計變更、事後揭露：`ops/d2/plans/*.json`、`ops/d2/DESIGN_LOG.md`、`ops/d2/plans/ADDENDA.md`。

## 五、c_verify 實際做了什麼（請照這樣讀）

**它不是「用紀錄把出處補回來」。** 實際協定（`ops/d2/plans/ADDENDA.md` 11:10 那一筆，r2heldout_b 開跑後 4 分鐘揭露，那時還沒有任何週期跑完）：
1. 和 c 一樣用紀錄列出來源變了的行交給 agent；但**沒有出處的行每個週期都交**（c 只交一次——程式的抑制條件只寫了 c）。
2. agent 改完後，Vacant 再跑一次來源檢查；交辦過的行仍不是「來源沒變」就退回再交辦一次。

留出 v2 的實測（45 個有檢查的週期）：第一次交辦 181 行（沒出處 101、來源變了 80）；第二次檢查時，沒出處的 101 行裡 **98 行仍然沒有出處**，來源變了的 80 行裡 78 行改好了；共退回 100 行。
所以 c_verify 的 0 漏抓（c 是 5/80）主要來自「沒出處的行每週期都交給 agent 重查」，再加一次重試；它的 token 是 c 的 2.9 倍、仍是整份重查的約 1/3（b 是 c 的 8.78 倍）。第二輪沒有跑 c_every，所以「每週期重交」和「驗收重試」兩個因素分不開。
9B 第二輪主批次幾乎沒有沒出處的行（交辦 198 對 200、退回 10 行），c_verify 和 c 的成本差不多。
**c_verify 是 harness 裡的流程**：產品目前只有 `vacant trace sources --check` 這個指令，使用者要自己寫外層的「交辦→檢查→退回」迴圈。
