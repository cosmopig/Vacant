## 一頁摘要（給擁有者）

**問的是什麼。** agent 照幾張網頁寫了一份有 20 個數字的報告，之後網頁陸續改了。三種維護做法：
(b) 每次叫 agent 整份重查；(d) 只告訴 agent「哪幾頁變了」；(c) 用 Vacant 的紀錄（紀錄裡有「每個數字是從哪一頁讀來的」）只把受影響的那幾行交給 agent。c 是「紀錄本身的用途」，不是「叫它重做」。

**第一輪：照事前標準，三個模型都沒過。** 原因只有一個——紀錄常常認不出「這個數字是從哪一頁來的」。agent 抓網頁的寫法很多（存成檔再讀、寫成迴圈、和別的指令混在一起），產品只認得幾種：9B 覆蓋率 75%、Haiku 30%、12B 63%。認不出來源的行，c 就不會交給 agent，於是漏掉。

**第二輪：讓產品認得更多寫法，換新題目重新預註冊。**
- **在和開發資料同一個產生器的題目上（9B、Haiku 主批次），紀錄認得出來源之後，c 不再比整份重查多漏，而且不改壞東西。**
  - 9B（50 組）：覆蓋率 97%；c 漏 3/196、整份重查漏 10/196（差 −3.6pp，這只是點估計，區間上限剛好 0）；c 改錯 0 條。token 省到整份重查的 1/2.94——事前門檻是 1/3，**差 0.06，照規則判 FAIL**；和「只告訴哪幾頁變了」比，c 少漏、省 1/1.56，但區間下界 0.96 沒到 1 ⇒ 未定論。
  - Haiku（50 組，雲端）：覆蓋率 100%；三種做法都幾乎不漏；美元省到整份重查的 1/2.28（沒到 1/3 ⇒ FAIL）；**比只告訴哪幾頁變了省一半、不多漏 ⇒ 這一個比較判 EFFECTIVE**（但成本用美元是看過小量試才定的，d 也沒有附文字差異）。
- **在沒看過、刻意加難的網頁結構上（60 組確認批次 r2heldout_b）：便宜的 c 會多漏；改用保守的做法才不多漏，但省得沒那麼多。**
  - 事前登記的主要臂是 c_verify——**它的實際做法是：沒有出處的行每個週期都交給 agent 重查，改完再用紀錄檢查一次、不對就退回一次**（不是「用紀錄把出處補回來」，見第五節）。
    c_verify 漏 10/240、整份重查漏 7/240（差 +1.25pp，上界 5pp，**不多漏**）；token 是整份重查的 1/3.12，但區間 1.69–6.95 的下界沒到 3 ⇒ **未定論**。和「只告訴哪幾頁變了」比，c_verify 不多漏（10/219 對 17/219），但**比它貴**（d/c_verify 0.74×）⇒ **FAIL**。
  - 次要（c，沒出處的行只交辦一次）：token 只有整份重查的 **1/9.95**（8.06–12.23），但漏 28/240、差 **+8.75pp、上界 15pp** ⇒ 漏抓未定論、傾向多漏。c 的 28 個漏抓：13 個出處沒記到、8 個出處記錯頁、7 個交辦了但 agent 沒重讀。
  - 「只告訴哪幾頁變了」（d）在這批**刪掉或改錯 264 條對的行**（b 26、c 20、c_verify 8）。
  - 留出 v2（20 組，UNRESOLVED）是這批的開發資料，不再當確認證據。
- 12B 第二輪：待填。

**一定要一起講的限制。**
- 第二輪的產品修正是對著第一輪的資料開發的；「用第一輪初稿重播，覆蓋率 9B 753→874、Haiku 300→1000」是**樣本內**數字。
- **出處記得到的條件**（抓取寫法 × 覆蓋率，同一段看）：r2heldout_b 的 60 組裡 58 組是「一次抓一個網址、印在螢幕」，覆蓋率 1040/1160（90%；沒對上的是較難教材裡的撞值與沒有實體名的句子），2 組存到 /tmp 再讀 20/40；第二輪 9B 主批次各寫法 94–100%；邊界測試裡 agent 改用 python 抓網頁時只有 33%。也就是說：**紀錄記得到出處，前提是 agent 用 curl／wget 這類看得出「只是抓網頁」的指令**；python 之類自己寫程式抓的，產品目前認不出。
- 第二輪補的只是「看過的抓法」（迴圈、先存檔再讀、混合指令），而且只認 HTML。**邊界測試**（30 組新題目、只看初稿）：叫它用 curl 200/200、不提工具時它仍自己選 curl 196/200；把 curl 拿掉之後，改用 wget 的 4 組 80/80，**改用 python 的 6 組只有 40/120（33%）**——python 抓網頁是目前產品認不出的寫法（初稿本身 600/600 全對，差別只在出處）。來源：`d2_results/bnd_qwen9b_1004/coverage.json`。
- 留出 v2 的 20 組全部是同一種抓法（一次抓一個網址、印在螢幕），初稿 400/400 全對，**沒有測到抓法的多樣性**；它的規格是針對已知弱點設計的加壓測試，不是盲測。其中 s15 整組 0/20、s05 9/20 沒有出處。
- 只有一個本機小模型（qwen3.5-9b）有完整的第二輪結果。

**小模型被給大範圍指令時，會刪掉對的內容。** 「只告訴哪幾頁變了」那一臂（d）把對的行刪掉：9B 主批次 54 條（3 組整份重寫）、留出 v2 61 條（59 條是整行刪除）。c 幾乎不會（0 條、2 條），因為它只交辦來源確實變了的那幾行。但整份重查（b）在 9B 主批次是 0 條，所以這是「大範圍或頁面級指令＋這個小模型」的現象，不是「整份重查一定會改壞」。

**紀錄能不能被稽核：能，有人獨立驗過，也有抓不到的地方。**
- 沒參與的稽核者自己寫程式、只讀紀錄，重算出的分數和我們的逐列一致（第二輪 9B 主批次 25,000 列、留出 v2 10,000 列，0 不一致）。
- 驗鏈檢查每一筆的雜湊、串接、Ed25519 簽章、簽章者在信任清單、步驟引用的內容、提示文字、索引裡的每個檔案；九種刻意竄改每一種都至少被一層抓到。
- 每個錯誤都歸得到是哪一段出問題（出處沒記到／記錯頁／變動沒偵測到／交辦了但沒重讀／重讀了沒改對／初稿就錯）。
- 抓不到或保證較弱的：同帳號用新鑰匙整條重簽＋改信任清單，要靠推到遠端的鏈頭錨點；第一輪 9B 主批次的錨點是結束 3 小時後才寫的（保證較弱）；模型呼叫數只在 harness 紀錄裡、不在簽章鏈上；簽章鑰匙 agent 讀得到。

**另外修好的產品錯誤。** 預設的「交件前檢查」會把 agent 抓下來存成檔再讀進來的正確數字誤判成「沒有出處」，叫 agent 多改兩輪、還把對的數字標成「假設」。已修並有測試（`decisions/notes/NOTE_20261125_ZEROCONFIG_FALSE_UNSOURCED.md`）。

## 五、c_verify 實際做了什麼（請照這樣讀）

**它不是「用紀錄把出處補回來」。** 實際協定（`ops/d2/plans/ADDENDA.md` 11:10 那一筆，r2heldout_b 開跑後 4 分鐘揭露，那時還沒有任何週期跑完）：
1. 和 c 一樣用紀錄列出來源變了的行交給 agent；但**沒有出處的行每個週期都交**（c 只交一次——程式的抑制條件只寫了 c）。
2. agent 改完後，Vacant 再跑一次來源檢查；交辦過的行仍不是「來源沒變」就退回再交辦一次。

留出 v2 的實測（45 個有檢查的週期）：第一次交辦 181 行（沒出處 101、來源變了 80）；第二次檢查時，沒出處的 101 行裡 **98 行仍然沒有出處**，來源變了的 80 行裡 78 行改好了；共退回 100 行。
所以 c_verify 的 0 漏抓（c 是 5/80）主要來自「沒出處的行每週期都交給 agent 重查」，再加一次重試；它的 token 是 c 的 2.9 倍、仍是整份重查的約 1/3（b 是 c 的 8.78 倍）。第二輪沒有跑 c_every，所以「每週期重交」和「驗收重試」兩個因素分不開。
9B 第二輪主批次幾乎沒有沒出處的行（交辦 198 對 200、退回 10 行），c_verify 和 c 的成本差不多。
**c_verify 是 harness 裡的流程**：產品目前只有 `vacant trace sources --check` 這個指令，使用者要自己寫外層的「交辦→檢查→退回」迴圈。

## 七、紀錄能不能被稽核（細節）

- 獨立重算：vacant-hope 派的稽核者三次只讀紀錄重算（不 import 我們的程式），0 不一致；第一次並抓出我們稽核腳本的三個錯（歸因表、出處表、驗鏈太鬆），已修、複查通過。
- 驗鏈：每一筆的雜湊、串接、創世雜湊、Ed25519 簽章、簽章者在信任清單、步驟引用的輸入／輸出／索引、提示文字、索引裡每個檔案物件；外部錨點 `ops/d2/anchors/*.json`（鏈頭雜湊＋信任清單雜湊，推上遠端）。九種刻意竄改每種至少被一層抓到。
- 保證較弱的地方：第一輪 9B 主批次的錨點是結束 3 小時後才寫；第一輪三批的存取紀錄靠時間窗歸到臂與週期（之後的批次每筆都帶臂與週期）。
- 抓不到的：沒有錨點時，同帳號用新鑰匙整條重簽＋改信任清單；模型呼叫數不在簽章鏈上；簽章鑰匙 agent 讀得到（產品已知限制）。
