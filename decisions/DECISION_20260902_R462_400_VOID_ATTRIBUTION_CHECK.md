## 二、本輪要判斷的問題

round461 的決定檔第四節寫了第三個推翻條件：「若 400 錯誤的兩個 model_id
變體都持續失敗（不只是交替中一種暫時解析不到），那才是新故障」。round461
自己觀察到「尾端連續 5 筆 400」，但**檢查方法是眼看 `calls.jsonl` 裡
`model` 欄位交替**（round356 既有機制：8765 中轉換節點時 slash/underscore
格式跟著變），沒有回頭核對這些 400 是否真的讓某個任務兩個變體都試過仍失
敗、最終落到 `infra_void`。

本輪把 `notes.jsonl` 的 27 個 void 原因分解，發現 **3 個確實是「兩個變體
都重試殆盡仍 400」**（不是單次交替後恢復）：

```
mbppplus_Mbpp/9    plain-2   重試 2 次仍失敗：HTTP 400   ← void 序列 index 1
mbppplus_Mbpp/457  hasty-2   重試 2 次仍失敗：HTTP 400   ← void 序列 index 11
mbppplus_Mbpp/472  careful-2 重試 4 次仍失敗：HTTP 400   ← void 序列 index 22
```

`mbppplus_Mbpp/472` 逐筆呼叫記錄（`careful-2`, ts 1788307622392~1788307641678）
顯示 attempt 1（slash）→2（underscore）→3（slash）→4（underscore）全部
400，兩個變體都真的失敗過，不是猜測。

**字面上，這符合推翻條件 3 的敘述。** 但關鍵判斷是：這是不是「新」故障？

## 三、判讀：不是新增，是本來就存在、只是沒被分解過

用 void 序列的 index 回推時間軸：

- `mbppplus_Mbpp/9`（index 1）落在 round459 checkpoint（8/12 void）**之內**
  ——也就是說，round459 量到的 66.7% 裡，本來就已經有一筆是 400 造成的。
- `mbppplus_Mbpp/472`（index 22）落在 round461 checkpoint（23/30 void）
  **之內**——round461 判讀「不是新故障」的當下，這筆 400-void 已經存在
  於它自己的樣本裡，只是沒被挑出來對照條件 3。

也就是說：**400 造成的 void 從 round459 就存在，比例穩定在總 void 的
~10%（1/8 → 2/23 → 3/27，比例 12.5%/8.7%/11.1%，沒有上升趨勢）。** 這是
一個本來就在背景裡、只是這一輪第一次被分解出來看的既有現象，不是本輪
新出現、也不是持續惡化的故障模式。round461 用「眼看交替」得出的「不是
新故障」結論方向是對的，只是查證方法不夠精確（沒有對照 void 原因），
這輪把它補上。

## 四、決定：續跑，不殺、不改參數

- **選了什麼**：讓 PID 2513538 按原計畫跑完 60 題，不介入。
- **放棄了什麼**：沒有因為「字面上符合推翻條件 3」就升級處理——先查證
  「新不新」再決定要不要行動，字面符合但時間軸顯示是舊現象，不構成
  需要暫停的理由。
- **根據什麼**：void 序列 index 回推時間軸（可重放的具體證據，不是猜測）
  ＋比例三輪穩定在 9-13% 沒有上升趨勢。
- **修正記錄，不是推翻**：round461「400 不是新故障」的結論本身沒錯，但
  查證方法有缺口（只看交替、沒查 void 歸因）——這裡補上方法，供之後
  的輪次比照，不代表要否定 round461 的最終判斷。

## 五、推翻條件（供下一輪）

1. 400-造成的 void 佔比若明顯超過穩定的 9-13% 區間（例如某輪跳到
   >25%），才需要重新評估是否為新故障、要不要暫停等後端修好 slash/
   underscore 的節點切換問題。
2. 若某任務的 400 重試次數持續超過目前觀察到的 2-4 次上限（例如同一
   任務 400 重試 >6 次仍失敗），要懷疑重試機制本身是否失效，而不只是
   節點切換的暫時現象。
3. 跑完 60 題後整批 void 率仍 >60%：沿用 round459/461 已寫的評估，
   下一輪判斷是否改用 CMH 合併法。
