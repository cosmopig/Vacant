## 0. 研究問題（凍結）

在 gemma-4-12b、每次嘗試 600 秒的條件下：**harness 用可見測試從三次獨立嘗試裡挑出交付版（S），比三次裡隨機交一份（M）多多少隱藏測試全過的比例？**

- 這回答的是「**harness 用驗收來決定交哪一份**」的增益。
- 它**不是**「有沒有可見測試」的增益：每一次嘗試的工作區裡都有可見測試，agent 自己可以跑。
- 展場與對外口徑用「**可究責性／讓依賴有根據**」，不用「信任」。

## 1. 唯一的執行程序：一個池

- 每個（題, 重複）稱為一**格**。每格跑 **3 次獨立嘗試**（槽 1、2、3），每次上限 **600 秒**，**三次都跑完，不提前停**。
- 每次嘗試都從同一份乾淨原件開始，不帶前一次的任何東西：沒有工作區、沒有回饋、沒有提示差異。三次嘗試彼此看不到。
- **三次的 prompt 逐字相同**，就是題庫的 `instruction.txt`。不提其他嘗試、時間或評分；符合 **KS-1**（不得有「你有責任／會被懲罰」類措辭；harness 的 `_KS1_BANNED` 檢查必須開著）。
- 實作：計畫檔三個臂 `P1`、`P2`、`P3`，都是 `policy: single`、`attempt_timeout_s: 600`。**槽號就是臂名，在計畫檔裡寫死**，跟完成先後無關。
- 一格的 3 次嘗試**綁在同一台主機**，盡量同時跑在該台的 3 個串流上（每台 jobs 3 ⇒ 一次一格）。每次嘗試的開始時間照實記錄。
- 執行順序：每台都**以重複為外層**：先跑完所有題的第 1 重複，再跑第 2 重複，依此類推。同一重複內，依題的 sha 順序（§4）。

## 2. 四種取法（全部離線計算，只讀紀錄）

每次嘗試記：可見那一半是否全過（`accept`：`acc_status=="ok"`、跑到的測試數 >0、全部通過）、可見通過數、隱藏那一半是否全過（`h`）。

| 代號 | 取法 | 這一格的值 |
|---|---|---|
| **S** | 依可見測試挑：取槽號最小的「可見全過」那一次；都沒全過就取可見通過數最多的，**平手取槽號最小的** | 被挑那一次的 h |
| **M** | 三次的平均，也就是隨機交一份的期望值 | (h₁+h₂+h₃)/3 |
| **F** | 取第 1 次（槽 1） | h₁ |
| **O** | 三次裡至少一次隱藏全過。這是上限，**只描述** | max(h₁,h₂,h₃) |

注意：S 的平手規則（取最早）和 `redo.py` 的 `_policy_deliver`（取最後）不同。本批次的 S 由分析碼自己算，不用 harness 的交付欄位。

## 3. 主比較、次要比較、門檻、判讀

**主比較 S−M**：每格算 Dᵢ = h(S) − M。估計值 = 所有納入格的 Dᵢ 平均（pp）。
- 檢定：**以題為群集的精確符號翻轉置換檢定**，雙尾 α=0.05。統計量是各題 Σ(3·Dᵢ) 的總和，3·Dᵢ 是整數，所以可以用 DP 完全枚舉 2^T 種符號。
- 區間：以題為群集的 bootstrap，percentile 法，10,000 次，種子 20261128。

**次要比較 S−F**：每格 Eᵢ = h(S) − h₁，用同樣的檢定與區間。
- **多重比較的處理是固定順序**：主比較通過時，才在 α=0.05 下判讀 S−F；主比較沒通過，S−F 只描述，不寫顯著與否。
- O、O−M、捕捉率 (S−M)/(O−M)、各槽的成功率都只描述。

**最小有意義差與判讀**（依附錄 A 模擬：ctl34 型的池，母體效果約 +6pp）。四種結果互斥，依序判定：

| 判定 | 條件（全部成立） | 固定主句 |
|---|---|---|
| **過** | p<0.05、估計值 **≥3.0pp**、bootstrap 區間下界 >0 | 「在這 N 題、gemma-4-12b、每次 600 秒的條件下，harness 依可見測試從三次嘗試中挑選交付版，隱藏測試全過的比例比三次中隨機交一份多 X pp（95% 區間 [a, b]，題群集置換 p=…）。這是 harness 用驗收決定交哪一份的增益，不是『有沒有可見測試』的增益。」 |
| **反向** | p<0.05、估計值 <0 | 「依可見測試挑選，比隨機交一份少 X pp（[a, b]）。」 |
| **等價** | 不屬於上面兩種，且 bootstrap 區間完全落在 **(−3.0, +3.0)pp** 內 | 「依可見測試挑選和隨機交一份的差在 ±3pp 以內（95% 區間 [a, b]）；在這個條件下，用驗收挑選沒有帶來有意義的增益。」 |
| **未定** | 其他情況（包括 p<0.05 但估計值 <3pp） | 「沒有確認 harness 依可見測試挑選比隨機交一份好；95% 區間 [a, b] 也排除不了 ±3pp 以內的差，所以不能說兩者一樣。」 |

為什麼門檻定在 3pp：
- 模擬中，「p<0.05 且 ≥3pp」的檢定力只比單看 p 少 0.2–2.1 個百分點（48×3：0.895 → 0.889）。
- 真實效果為 0 時，這條規則的偽陽性率是 0.3–1.5%，單看 p 是 1.7–4.3%。
- 3pp 大約是預期效果的一半。所以這個門檻不會把顯著但微小的差寫成「過」，代價很小。

等價界限 ±3pp 的限制：真實效果為 0 時，模擬中能判成「等價」的機率只有 17–41%（見 §7）。所以「未定」是很可能出現的結果，**未定不得寫成「沒有效果」**。

**禁用句**（任何結果下都不准寫）：
- 「證明 Vacant 讓 agent 做得更好」；「驗收讓模型變強」；任何帶「信任」的說法。
- 「有可見測試比沒有好」（本批次沒有沒測試的臂）；「重開本身有用」（本批次只量挑選）。
- 外推到其他模型、其他時間上限或互動使用，例如「小模型都會」。
- 判定為未定時寫「沒有效果」「一樣好」。
- 把 M 寫成「實際隨機交件的結果」：M 是期望值（見 §9-1）。

## 4. 題庫：選題規則（機械化，不看任何模型在這些題上的結果）

題單與 sha 在發射前補進「發射前補充」。規則如下。

2. **排除已用過的題**（不分語言，比 slug）。以下任一處出現的題都排除：
   - 本預註冊推上 `auto/redo` 那一刻，repo 裡**所有計畫檔**（`ops/redo/plans/*.json`、`ops/d2/plans/*.json`）的 `tasks` 欄位；去掉 `ex_`／`pg_`／`js_` 等前綴，`_` 換成 `-`。
   - 所有題庫清單：`polyglot_py`（34）、`exercism_py_unused`（40）、`exercism_py_hard`（26）、ctl 校準的 37 題候選、ctl12、ctl16、ctl_smoke4、exam37、hardjs34／`exercism_js_d4` 用過的題。

   - 排除清單的 sha256 寫進發射前補充。
3. **測試數**：跳過被 skip 的測試之後，測試方法 **≥10**（每一半 ≥5）。
4. **有效性**（只跑參考解與原始 stub，不跑模型）：
   - 參考解（`.meta/example.*` 或 proof）在兩半各自全過，每半 ≤60 秒。
   - 原始 stub 在**兩半各自**至少有 1 條沒過。

5. **排序與取題**：依 `sha256(slug + ":acceptance-pool-20261128")` 由小到大排序，取前 T 題（T 由 §6 決定）。
6. **切半**：每題的測試方法依 `sha256("20261128:" + slug + ":" + 方法名)` 排序，前 ⌈n/2⌉ 條是**可見**，放進 `workspace/`；其餘是**隱藏**，放進 `hidden/`。

   - 切法程式與每題兩半的 sha256 寫進 MANIFEST。
   - `hidden/` 和 `scorer.py` **不掛進沙箱**；評分在宿主端對工作區副本執行。
7. **主機分配**：在第 5 步的順序裡，第 0、2、4…題給 **1004**，第 1、3、5…題給 **1003**。同一題的所有重複都在同一台。

## 6. 規模：發射前機械決定，不准中途降

候選組合依檢定力排序：**60×3 → 48×4 → 48×3 → 40×4 → 40×3**（題數 × 重複數）。

- 預估時間：每次嘗試的平均牆鐘取 ctl34 較慢主機（1003）的第 1 次嘗試平均 412 秒，加上驗收與評分約 35 秒，共 447 秒。每格 3 次 ÷ 每台 3 串流、兩台各一半格 ⇒ **預估時數 = 格數 × 223.5 秒**。
  - 60×3＝11.2 小時；48×4＝11.9；48×3＝8.9；40×4＝9.9；40×3＝7.5。
  - ⚠ 412 秒是在不對稱的上下文設定下量到的，當作保守值。
- 規則：發射時刻 t，可用時數 H = (11/28 22:00Z − t) − 1.5 小時。取清單中**第一個**同時滿足以下兩條的組合：
  - 題數 ≤ §4 選出的可用題數；
  - 預估時數 ≤ H。
- **沒有任何組合同時滿足 H 與檢定力 ≥0.75（40×3 是 0.79）就不發射**，回報「條件不足，不值得跑」。
- 例：10:00Z 發射時 H=10.5 ⇒ 可用題 ≥48 時是 **48×3**；08:30Z 發射、可用題 ≥60 時是 60×3。
- 選定的組合、H、可用題數寫進發射前補充後才發射。**之後不准改組合**。

## 8. 事前的無法區分條件與缺格規則（在算 S−M 之前判定）

**缺格**：以格為單位，3 次嘗試沒有全部有效完成（硬停時沒跑完、或依 §5 作廢）的格**整格排除**。排除的格超過選定格數的 **10%** ⇒ 判定為**未定**，只描述。

**無法區分條件**（任一成立 ⇒ 判定「本批次無法區分」，只描述，不下 §3 的判定）：
1. **單次成功率**（全部納入格的 M 平均）<15% 或 >85%。
2. **S 和 F 挑到同一份的格 >85%**。ctl34 型的池模擬中這個比例的 5–95% 範圍是 56–72%。超過 85% 表示挑選只在不到 15% 的格改變交付版，S−F 幾乎沒有資訊。
3. **有資訊的格**（三次的隱藏結果不全相同，即 h₁+h₂+h₃ ∈ {1, 2}）**<5%**。模擬中這個比例的 5–95% 範圍是 6–21%。S−M 只可能在有資訊的格不為 0，而每格 |D| ≤ 2/3；這個比例 <5% 時，|S−M| 的上限約 3.3pp，連最小有意義差都達不到。

**硬停**：最晚 **11/28 10:00Z 發射**，**11/28 22:00Z 硬停**。硬停時正在跑的嘗試立刻結束；它所在的格依上面的缺格規則排除。

## 9. 最可能被挑的三個弱點

1. **M 是同一批嘗試算出的期望值，不是實際「隨機交一份」。**
   - 緩解：在給定三次嘗試的情況下，隨機交一份的期望值就是三次的平均（期望值的線性），不需要「各次獨立」這個假設，只需要三個槽同分布。
   - 為了讓三個槽同分布：prompt 逐字相同、同一台、同時跑、槽號事前寫死、和完成先後無關。各槽的成功率分開報（只描述）；任兩槽相差 ≥10pp 時，結論加註。
   - 實際抽籤只會增加變異，期望值相同。
   - 照實寫的限制：如果同一台同時跑三個串流造成槽之間的系統差，例如第 1 個請求先拿到快取，M 和 F 都會受影響。
2. **agent 自己也會跑可見測試，所以這不是「有沒有可見測試」的增益。**
   - 照實寫：本批次所有嘗試的工作區都有可見測試；量到的只是 harness 層級「用驗收挑交付版」的增益。agent 層級的自我測試，五批事後資料和本批次都無法分離（`NOTE_20261129` §3）。
   - 結論主句已寫進這個限定。要量「把測試給 agent」本身，需要另一個工作區沒有測試的臂，不在本批次範圍內。
3. **只用一個模型、一個題目家族（Exercism）、一個時間上限，無法外推。**
   - 照實寫：結論的範圍就是「gemma-4-12b、600 秒、這 N 題」。外推列在禁用句。
   - 門檻與檢定力是用 ctl34（同一個模型、polyglot 題）定的，新題的難度分布可能不同；§8 的條件 1–3 會擋下太簡單、太難或沒有資訊的情況。

其他也會被問、這裡先照實寫：
- **可見與隱藏來自同一題，所以有相關。**這正是被量的機制：可見那一半能預測隱藏那一半多少。誤收率（可見全過、隱藏沒過）與誤擋率分槽報。切法是方法層級的隨機切，近乎重複的測試可能落在兩半，讓兩半的相關偏高、增益偏大；這是限制。
- **門檻是看過 ctl34 才定的。**但它們是在本批次任何資料存在之前定的，本批次的題也還沒選。
- **S 要跑 3 次，F 只跑 1 次。**花費的比較見 §10。這裡的增益是「花 3 倍嘗試、用驗收挑」相對「花同樣 3 倍但隨機交」（S−M，等花費），以及相對「只跑 1 次」（S−F，不等花費）。

## 10. 花費與時間（只描述）

- 每次嘗試的牆鐘時間與 token（輸入＋輸出；缺值記 null 並報缺幾筆），分槽、分台報。
- 每格花費：S、M、O 都是三次的總和；F 是第 1 次。報 S 相對 F 的倍數，以平均與中位數報。
- 另報「依序跑、驗收過就停」的反事實花費：依槽 1→2→3 的順序，算到第一個可見全過的那一次為止的總和，也就是 R 臂式的花費。
- 不據此講效率結論；token 只在同結構之間比較。

## 附錄 A：模擬方法（撰寫者執行，種子 11；可重現）

母體是 `ctl34_g12` 稽核包第二版（`edf6d323f`）裡，每個（題, 重複）R、B、C 三臂的第 1 次嘗試。它們提示相同、從同一原件開始、彼此不以對方為條件，等於每題 6 次獨立的 600 秒嘗試（33 題；pg_transpose 的 C 是 void，排除）。

每次模擬：
- T 題以放回方式從 33 題重抽；
- 每個重複從該題的 6 次嘗試**不放回**抽 3 次，當成槽 1–3；
- 依 §2 算 S（平手取最早）、M、F；
- 依 §3 的檢定算 p，「過」規則同 §3。

其他設定：
- 「效果為 0」的世界：把 S 換成三槽裡隨機一槽。
- 等價機率：每次模擬做 400 次群集 bootstrap，看區間是否落在 ±3pp 內，共 200 次模擬。
- 每個組合跑 1,500 次（判「過」與檢定力）、600 次（效果為 0 的偽陽性）、200 次（等價、區間寬度）。
- 分布：S 和 F 同一份的比例 5–95% 在 0.56–0.72；有資訊格比例 5–95% 在 0.06–0.21（2,000 次）；單次成功率 5–95% 在 0.31–0.52。

程式核心（與 `ops/redo/analysis/acceptance_signal_offline.py` 的 `power_sim` 相同，只改平手規則與判定規則）：

```python
def S(tri):                      # 取槽號最小的可見全過；否則可見通過最多、平手取最早
    for i, x in enumerate(tri):
        if x["accept"]: return i
    return max(range(3), key=lambda i: (tri[i]["acc_passed"], -i))
# 每題：sm += 3*h[S] - sum(h)；sf += h[S] - h[0]
# 主比較：signflip([各題 sm]) < 0.05 且 mean(D) >= 0.03（判「過」）
```
