## 二、手機是什麼角色：三個選項與取捨

這個決定會改變整個展件的意思，所以先講清楚再動手。

### 選項 A — 手機＝**下任務的人**（委託端）

觀眾在手機上講出自己的需求 → 世界替他做 → 收據回到手機。

- **展件的意思**：「這個世界會替你工作。」
- **現成的**：`world3` 的 `WorldBridge` 已經有訪客流程（spawn → 目標泡泡 →
  `matchTask` 比對 → 重放 → 分享卡）。手機掃 QR 投件的管線幾乎是現成的。
- **取捨（致命）**：真模型每題約 114 秒，**現場等不起**（CLAUDE.md 硬約束 1）。
  所以實作上只能是 `matchTask`——把他的需求**比對到一題我們跑過的**。
  那一頁必須講清楚「這不是你的題目，是世界做過最像的一題」，
  否則觀眾會以為自己那句話真的被執行了。**它不是「真實運作的過程」，是配對重放。**
- **另一個擋點**：真正的 A（從觀眾自己的 AI 記憶匯出萃取 persona）
  **卡在人類未決的倫理線上**（`SPEC_v3 §四`／`HANDOFF.md §六-2`／前一份裁決 Q2），
  本輪不跨。所以 A 現在只做得出半套。

### 選項 B — 手機＝**拿收據自己重驗的人**（稽核端）

電視演到哪一格，手機就收到那一格的收據頁，在自己的瀏覽器裡從創世驗到鏈頭，
翻一個位元看簽章變紅。

- **展件的意思**：「你不必相信我們，你自己算。」——**這就是可究責性的定義**。
- **現成的**：`examples/twin_viewer.html`（0.74 MB、離線、`file://` 直開、
  13 條 node check 全過）已經在做這件事，`examples/receipt_viewer_multiparty.html`
  也是同一套。缺的只有「**指到電視現在那一格**」（C4）。
- **取捨**：單向。電視 → 手機，手機不影響電視。
  人類要的是「手機**連動**電視」，B 只滿足一半。

### 選項 C — 手機＝**決定要測什麼的人**（下一步／導播端）

手機上是兩顆按鈕：**「介面扣住」／「介面寫明」**——同一題、同一個分身，
唯一差別是它知不知道客戶要的介面叫什麼。按下去，電視就演那一格。
第三顆按鈕是「翻掉一個位元」，電視當場演簽章對不上。

- **展件的意思**：「**你來決定測什麼，然後你自己驗結果。**」
- **取捨**：手機沒有「提出自己的需求」那種親近感；觀眾玩的是我們給的題庫。
- **算得過來**：全部是預跑好的格子 ⇒ 零模型呼叫、毫秒級回應、離線、可無人值守。

### 推薦：**C 當主幹 ＋ B 當帶得走的東西**（手機＝導播＋稽核，不是委託人）

理由四條：

1. **只有 C 能同時滿足「真的連動」與「秒級互動」。** A 要嘛等 114 秒（現場不可能），
   要嘛降級成配對重放（那就不是「真實運作的過程」）。C 的每一次按壓都落在
   已經跑完、簽好章的真資料上，回應是毫秒級的，而**資料本身是真跑**。
2. **我們手上最容易被外行看懂的東西是一組反事實對照**，而不是一段演出。
   `runs/twin_fixture_20260919` 的排程本來就是「同一題 × 扣住／寫明」兩格一組。
   **觀眾自己選要看哪一邊**，那件事才從影片變成示範。
3. **B 單獨做不到人類要的「連動」，A 卡在倫理未決。** C＋B 是現在做得出來、
   而且不會對觀眾說錯話的那一個。
4. **口徑上 C＋B 落在「可究責性」而不是「信任」。** A 說的是「這個世界會替你工作」
   （那是要你依賴它）；C＋B 說的是「你來決定測什麼、你自己驗結果」
   （那是不必依賴監督者的說法）。CLAUDE.md §硬約束 4 要的是後者。

**A 不是刪掉，是排後面。** 等倫理定案（persona 萃取那條線）之後，
A 可以接在 C 的前面當入口：觀眾先留下一個需求、世界替他配對，
然後他用 C 的按鈕決定要測哪一邊。屆時那一頁要逐字講明「配對重放，不是你的題目」。

## 三、活模式要補什麼才能「真的連動」

**電視端的接口已經在了，缺的是生產端**（前一份裁決的結論不變），
但 §一 的 D 三條說明：接口在，不等於接得上。

### 生產端（本 repo，要做）

1. **`ops/exhibit/twin/serve_twin.py`** — 展場機上的一支 stdlib HTTP 伺服器
   （零依賴、localhost、離線）：
   - `GET /live/events.jsonl` — 活模式來源，**逐格追加**（不是一次吐完整批）
   - `GET /state` — 電視現在演到哪一格（手機要對齊時間軸）
   - `POST /control` — 手機按下「扣住／寫明／翻一個位元」
   - `GET /r/<cell_id>` — 那一格的收據頁（C4：per-cell 的 `verify_url`）
   - 電視端：`index.html?live=http://<展場機>:8899/live/events.jsonl&poll=2000`
2. **`to_events.py` 的逐格吐出模式**（`--follow` 或由 `/control` 驅動）。
   本輪已經把**事件內容**改忠實了，還沒做**時間軸**。
3. **`twin_viewer.html` 吃 `#cell=<cell_id>`**，直接捲到那一格（C4）。
4. **手機頁**（`ops/exhibit/twin/phone.html`）——選項 C 的三顆按鈕＋B 的收據入口。

### 電視端（`vacant_hm`，**要先問過人類**）

§四 的 13 條。其中 **D1 不改，活模式就一格都播不出來**——
其餘 12 條是「播得出來之後，播出來的話對不對」。

### 展場鐵律怎麼守

- **秒級**：全部預跑，現場零模型呼叫。手機按下去到電視有反應 ＝ 一次 HTTP POST。
- **離線**：整條線都在展場機的 localhost 上。**電視不需要外網**，
  但**需要一個 localhost 伺服器**（D3）——這一點要寫進展場開機腳本。
- **無人值守**：沒有人按手機的時候，`serve_twin.py` 自己照排程輪播 18 格；
  有人按就插隊。`LIVE.seen` 的成長問題用「每輪播一圈重置 events.jsonl」解掉。
- **鐵律 5**：證據等級**逐格**跟著事件走（本輪已做），
  電視那兩處寫死的「正在發生／真的 agent 此刻做的」必須改成讀它（§四 P6）。
