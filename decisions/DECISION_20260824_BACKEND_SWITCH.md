## 四、換載成本（量到的）

先試過兩個家族（qwen ＋ nemotron-3-nano-omni）。實測每題 120s，而且
**nano 那個反而更慢（195s vs 82s）**——那不是模型大小，是 LM Studio 在
兩個模型之間換載。GPU 24GB 只剩約 5GB（VMware 也在用），塞不下兩個。

兩個家族的代價與好處各是什麼：

- SPEC_GAIN §5.1 的共同盲區問題在 ON 臂會更嚴重——同一個模型評審自己家族的
  產出，Kim 2025 量到兩個模型都答錯時 60% 錯在同一個答案。
- 池子的異質性只剩 system prompt，沒有模型家族的差異。

**但這兩點對 OFF 臂都不成立**：OFF 沒有評審，也不做信譽路由。
所以就「量 OFF 失敗率」而言，兩個家族買到的是更接近正式條件的池子，
付的代價是慢 2.4 倍（60 題約 2 小時 vs 約 82 分鐘）。兩種都可以，
**這一輪實際走的是兩個家族。**

## 五、這不影響 SPEC_GAIN §6 的平台無關宣稱——反而是它需要的

§6 說宣稱平台無關要「兩個不同的後端各跑一次，結論同號」。
Cline 是第一個後端，本地 LM Studio 是第二個。**現在還不能宣稱任何東西**，
因為兩邊都還沒有完整的三臂結果；但端點身分已經逐呼叫落盤（`api` 欄位），
兩個後端的數字不會混在一起。

## 七、再更正：端點是 8765 算力中轉，不是 1234（人類 2026-08-24 當場糾正）

**「增益應該是跑 8765 吧，不是 lmstudio 吧」**——是。上面整份文件寫的
`:1234` 是錯的端點。

`1234` 是 win1003 那台 LM Studio 自己的埠。`8765` 與 `8766` 由**同一個
python 進程**（pid 21112）提供，那是兩台電腦的算力中轉：`8765` 是
OpenAI 相容的推理面，`8766` 是控制面（打 `/v1/models` 回 `Not Found`）。

直接打 1234 會**繞過中轉的協調**——中轉也在派工給同一張卡，兩邊各自
打同一個後端卻互相不知道。那不只是慢，是把別人的排程弄亂。

不是常態；**正因為罕見才更要留下看得懂的訊息**，事後才查得出來。
