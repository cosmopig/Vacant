## 1. 判定技術：沒有標準答案時可用的訊號

|---|---|---|---|
| **模型當評審**（同模型／較強模型／多評審） | 強評審與人類的一致率「over 80%」，與人人一致率同級（Zheng et al., arXiv 2306.05685, 2023-06-09, **B**）。13 個評審裡「only the best (and largest) models achieve reasonable alignment with humans」，分數最多差 5 分，有寬鬆傾向（Thakur et al., arXiv 2406.12624, 2024-06-18, **B**；小模型的逐一數字在圖裡，我沒抽出）。37 個模型、9 個基準：**跨家族驗證優於同家族、優於自我驗證**，「self-verification yields little verifier gain across all tasks」（arXiv 2512.02304, 2025-12-02, **A**）。 | 自我偏好：評審能認出自己的輸出，且辨識力與偏好強度成線性關係（Panickssery et al., arXiv 2404.13076, **B**）；偏好與困惑度相關，不只是「自己寫的」，而是「熟悉的」（Wataoka et al., arXiv 2410.21819, 2024-10-29, **B**）。Stechly 2023：GPT-4 驗證圖著色時把對的也退掉（PA 筆記 #3）。 | 〔事實〕2512.02304 的重抽實驗用的是各家族最小的三個後訓練模型；驗證器增益與實測增益相關 r＝0.796（3 次嘗試）、0.892（10 次），斜率 0.221／0.405。〔事實〕小模型自我修正要配強驗證器才有用、弱的自我驗證器決定「何時修」時有限制（Zhang et al., arXiv 2404.17140, 2024-04-26, **B**）。〔推論〕同一個 9B 當自己的評審，預期增益接近 0；要用評審，應是不同家族。 |

| **驗證器模型、過程獎勵模型** | 訓練驗證器做 best-of-N（Cobbe et al., arXiv 2110.14168, **B**）；過程監督 PRM 在 MATH 子集解 78%，優於結果監督（Lightman et al., arXiv 2305.20050, **B**）；GenRM 以生成式驗證：GSM8K 73%→93.4%（arXiv 2408.15240, **B**）。不靠測試、比較候選補丁的 R4P：驗證 SWE-bench 補丁 72.2% 準確，做補丁挑選從 26.2% 到 32.8%（arXiv 2510.22775, **B**）。Agentic Rubrics：先由 agent 讀 repo 寫評分清單再給補丁打分，SWE-Bench Verified 比最強基線至少 +3.5pp（arXiv 2601.04171, **B**）。 | 驗證器被選擇／優化時會被迎合（Baker 2025，PA 筆記 #12）。 | 〔推論〕需要訓練資料；本專案目前沒有。可借用的是現成的小型「有無出處」分類器（§3 第二層）。 |

**§1 小結〔推論〕**：便宜判定的價值，取決於（1）誤收率（決定天花板）、（2）它的錯和生成器的錯是否相關（同模型評審、同題重抽都高度相關）、（3）後面接的動作。小模型當評審在文獻裡沒有正面證據；小模型讀 logprob 當分類器有證據，但必須校準。

### 2.2 有沒有獨立評測

- 〔事實〕**Jev 有一篇獨立評測**：Deußer et al., arXiv 2609.37647（2026-09-29，v2 2026-10-29，Bonn／Fraunhofer，**A**）。37 個資料集、346,009 個請求、花費不到 $10。與本專案最相關的：**LLM-AggreFact（有無出處判定）平衡準確率 78.6% [77.6, 79.6]**，11 個來源從 59.8%（ExpertQA）到 90.6%（Reveal）；同請求下 Qwen3.8-27B 76.9%、Gemma-4-E4B 75.6%。Choice 機率合併 ECE 0.028；**單一 Noul 偏保守**（平均 P(yes) 0.465 對實際 0.518，ECE 0.052），所以 0.5 門檻下召回偏低；多標籤 Noul 高估 yes（0.209 對 0.041）。調門檻後 UNFAIR-ToS micro-F1 0.50→0.75。評分題（rubric）三個模型都弱（SummEval ρ 0.554）。
- 〔事實〕**Gemma 4 26B 直接讀標籤 logprob 與 Jev、DiffusionGemma 的比較**（AWS Builder Center, 2026-09-24, **P**，預註冊、逐筆輸出公開）：在 Bespoke Labs 公開的 3,880 筆套件上，純 Gemma 落後 Jev 1.13.0 2.1pp（0.2–4.0），是非題 84.8% 對 84.6% 無差，選擇題落後 4.5pp；DiffusionGemma 與純 Gemma 準確率無差（McNemar p＝0.25），**擴散那一步沒有量到準確率增益**，但未校準時 DiffusionGemma 的 ECE 較低；L4 上純 Gemma 每次決策 61 ms，DiffusionGemma 單讀 1.9–2.0 倍、自動重讀規則 5.0–5.1 倍。
- 〔事實〕**Gemini Decisions 沒有找到獨立評測**。廠商基準圖（Google 部落格）：Top-1 ECE 0.0250（7 個共用評測），Jev 1.14 0.0494；Artificial Analysis Decision Index 給 66 分，等於該榜中位數，每任務 211 ms（`artificialanalysis.ai/decision-models/gemini-decision-1`, **P**）。LLM-AggreFact 榜上沒有它。
- 〔事實〕**介面與偏誤的獨立研究**：DICE（arXiv 2610.14404, 2026-10-09, **B**）——Jev 本身沒被攻擊，但上游的「狀態抽取、問題生成、輸出解讀」三個轉接點各自都能改變最終決策；綁定來源的檢查擋得住，但也誤擋了一些正確決策。偏誤稽核（arXiv 2611.00496, **B**）：12 個模型、1,638,000 個決策，**選項對調讓 0.0%–72.6% 的選擇翻轉**，是非題可以被位置決定（1.00 對 0.005）。arXiv 2611.05553（**B**）是把決策模型當經濟學調查的人類替身，與判定無直接關係。

### 2.3 拿它當我們的判定可不可行〔推論〕

- **「這一行的值有沒有被這段頁面文字支持？」**——可行，而且有現成的參照數字：LLM-AggreFact 上 Jev 78.6%、開放的 9B 級分類器 76–78%（§3 第二層）。這類判定恰好補我們字串比對的弱點：公司組的標記失準來自格式差異與表格拆值（B34／B40），字串比對做不到語意比對，Noul 可以。限制：Jev 32k token 上限，我們的頁面每組平均約 3.4 萬 token（E 家族 HP 30 組的輸入 7,657–99,157 token、平均 34,464，`efamily_hp_per_set.jsonl`），必須切窗；Gemini Decisions 262k 可整頁。

> ⚠ 暫定註（2026-11-28）：「公司組的標記失準」可能受評分器缺陷影響（正確值被判錯，見檔頭），待第二正規化器重評。

- **「這份報告完成了任務要求嗎？」**——不建議當主判定。Jev 論文三個模型在評分題都弱、需要多步推理的事它明說做不到（codelab「will not … follow a multi-step chain of reasoning」）。拆成原子題（「第 k 個要求的欄位有沒有值」）再在程式裡組合，才符合官方最佳實務（「Atomic checks, composed in code」）。
- **機率當「判定強度」的連續版**——可行，正好對上 ROC-n-reroll 的框架（§3.3）：每個門檻 τ 給一組（TPR, FPR），掃 τ 就是一條 ROC，接受取樣的準確率＝Tπ/(Tπ+F(1−π))。但兩個前提：(1) 門檻要事先定或用留出組定（破口 6）；(2) 只有在**機率經過校準、且記了標籤質量**時，同一條曲線才能跨組使用。
- **DiffusionGemma 在單張 24 GB 3090 自架**——〔事實〕已有人在 24 GB 的 L4 上以 AWQ 4-bit（社群檔，約 17 GB）配 vLLM nightly（含 PR #57250）跑起來，但只用 2048 token 上下文、64 token canvas（AWS 文章）；djev-run 的 Cloud Run 設定是 4096 token、RTX PRO 6000（djev-run README）。模型卡說量化後「fits within the 18GB VRAM」。llama.cpp 支援仍在 PR（僅搜尋摘要，**S**，未核對）。〔推論〕3090（Ampere）**跑得起來的機率高，但上下文會很短**：17 GB 權重後剩約 6 GB，我們平均 3.4 萬、最多約 10 萬 token 的頁面放不進去，只能把頁面切成小窗逐窗讀；NVFP4 檔官方只列 Blackwell／Hopper，3090 要用 AWQ／GGUF 類的檔，未驗證。**更重要的是 AWS 文章的結果：擴散那一步沒有量到準確率增益，普通 Gemma 讀標籤 logprob＋50 個標籤校準就同級而且快 1.9–5.1 倍**——所以本機要的不是 DiffusionGemma，而是「任何本機模型的標籤 logprob＋校準」，或現成的 9B 判別模型（Cloudflare Clef-flash＝Qwen3.5-9B 凍結＋LoRA，Apache 2.0，`blog.cloudflare.com/clef-decision-models/`, 2026-10-01, **P**；LLM-AggreFact 76.6%）。

#### 離線測的規格（同一批 1,747 行；事前定好門檻與比較方式）

先做 **步驟 0：錯誤分類**（本機、用原文；分類先於任何新判定的結果，分類規則先寫進計畫檔）。每個錯行歸入且只歸入一類，依序判：
- **U 解析失敗**：`canon_parsed=false`。再由人工或第二個正規化器判「與答案鍵等值」（量具問題，改評分後應算對）或「真的不合格」。
- **S 舊修訂**：值的 HMAC 等於答案鍵 k≥1 的修訂（git 裡就能算，見上：公司 0、足球 3）。
- **F 頁上沒有**：值（做數字正規化：去千分位、比例尺 thousand／million／billion、百分比、四捨五入到答案的有效位數）不出現在 agent 抓過的任何頁。
- **R 頁上有，再細分**：對凍結站 HTML 解析表格，找出值所在儲存格的（列標題、欄標題），和答案鍵所在儲存格比：**R-欄**（同一列、不同欄＝欄位錯）、**R-期**（同一欄名、不同年份／期間欄）、**R-單位**（與答案鍵只差比例尺或四捨五入）、**R-他處**（內文或別的表）。內文用句子窗做同樣比對。
- 每類隨機抽 20 行人工核對分類器，報一致率。
- git 裡已能先做的：U、S 兩類的計數（上面已做）；F 對 R 只能在 60 份 A 臂子集用現成的 `before_etype` 近似。

再做 **步驟 1：三種問法，同行配對**（每行都跑三種，比較都是配對的）：
- **V1 原問法**：已有，不重跑（固定為基準）。
- **V2 欄位對齊問法**：輸入加上 (a) 欄位定義與口徑（答案鍵 manifest 裡的欄位標籤之外，加任務說明裡對這一欄的年份、單位、範圍的文字；**只用 agent 當時也看得到的任務文字**，不給答案）；(b) 值在頁上出現處所在的那一列（表格：整列＋表頭；內文：前後各一句）。問兩題 Noul：「這一列／這一段是不是在描述 `{實體}` 的 `{欄位，含口徑}`？」與「若是，它給的值是不是 `{值}`？」；主分數＝兩題機率相乘。值不在頁上時第一題不送、直接記 F。
- **V3 兩段式**：第一段用 Choice 問「頁上哪一段在回答 `{實體}` 的 `{欄位，含口徑}`？」，選項＝值出現處與欄位標籤關鍵詞出現處的候選段（每段一個選項，最多 255，另加「都不是」）；第二段在程式裡比對被選段落中的值與初稿的值（同一套數字正規化），不再呼叫模型。主分數＝被選段的機率 ×（值相符為 1，否則 0）。
- **機制對照（不需要錯行）**：對每個**對的**行，把欄位換成同一實體的另一個欄位（答案不同者）再問 V1 與 V2。理想的判定在換欄後應該說不支持；「換欄後仍 p≥0.9 的比率」直接量判定對欄位的敏感度。

**要報的量**（兩組分開；以組（set）為群集 bootstrap 10,000 次——公司組只有 10 組，區間會寬，照實報）：
- 主要：**公司組 AUC(V2) − AUC(V1)** 與 **AUC(V3) − AUC(V1)** 的配對差與區間；次要：足球組同樣的差（看有沒有變差）。
- 依步驟 0 的類別分層的召回（U、F、R-欄、R-期、R-單位各自被抓到的比率），**主分析排除「U 且等值」的行**（量具問題，不算判定的錯），另報不排除的版本。
- 校準：ECE（15 等寬箱）、Brier、可靠度表；機制對照的換欄後 p≥0.9 比率。
- 門檻（事先定，兩個）：p<0.5；以及「在足球組讓標記率等於 V1 在 p<0.5 時的標記率（15.7%）」所對應的門檻，原封不動套到公司組。報兩個門檻下的召回與放行錯誤率。不另外掃門檻挑最好的。
- **事前寫定的判讀**：V2 或 V3 在公司組「AUC 區間下界 >0.5 且相對 V1 的差區間下界 >0」⇒ 欄位對齊問法有效；足球組相對 V1 的差下界 > −0.03 ⇒ 沒有變差。兩條都過才建議換問法。

### 3.3 第三層：判定強度 → 增益的關係，有沒有公式

| 來源 | 公式／主張（事實） |
|---|---|
| ROC-n-reroll（arXiv 2507.12399, 2025-07-16, **A**） | 單題層級：接受取樣（RS）的準確率＝精確度＝**Tπ/(Tπ+F(1−π))**；期望計算量 C＝1/(Tπ+F(1−π))；高計算極限由 ROC 在原點的斜率 T′(0) 決定；固定計算下 RS 勝 BoN，無限計算時兩者收斂；**低計算的觀測一般無法預測高計算的表現**。 |
| SPLIT（arXiv 2610.23255, 2026-10-16, **A**） | 單一生成器：**S_N＝(a/s)(1−(1−s)^N)**，a＝τp、s＝a+f(1−p)；對題目分佈取平均才得總成功率，明確模型化「題目難度異質」「跨模型共同盲點（Gaussian copula）」「同一候選重複驗證的相關」；但**給定題目之後仍假設各候選獨立**。指出多評審多數決降低精確度的條件（§1）。 |
| When Does Verification Pay Off?（arXiv 2512.02304, **A**） | 「verifier gain」＝精確度 − 單次準確率；3 次嘗試時實測增益 ≈ 0.22 × verifier gain（r＝0.796）。 |
| Stroebl et al.（arXiv 2411.17501, **A**） | 誤收率 > 0 ⇒ 重抽準確率有上限；單次準確率與誤收率強相關。 |
| arXiv 2602.05370（協調者轉述為此主題） | **對不上**：實際是 PACE（迭代 DPO 的探索效率），只順帶提到高 N 增加驗證器誤收風險（**B**）。 |

**〔本 repo 資料〕把 SPLIT 公式套到我們三批本機資料**（`origin/auto/redo` 的 `ops/redo/audit/ctl_20261128/*_cells.json`；R 臂＝失敗就丟掉工作區重開、最多 3 次；用 R／B／C 的第 1 次嘗試估 p、τ、f——三臂第 1 次是同一程序的獨立抽樣；都沒過時交件規則近似成「被退回的那次」）：

| 批 | p（第 1 次） | τ | f（錯的被放行率） | 精確度上限 a/s | verifier gain | **獨立假設**預測的增益 | **逐題異質**預測增益（留一重複） | 實測 R 臂（最終−第 1 次） |
|---|---|---|---|---|---|---|---|---|
| ctl12_q9 | .667 | .986 | .472 | .807 | .14 | +13.5pp | +8.2pp（.721） | **+8.3pp**（.639→.722，n＝36） |
| ctl12_colab_e4b | .157 | .941 | .220 | .444 | .29 | +15.9pp | +3.4pp（.228） | **+8.3pp**（.194→.278，n＝36） |
| ctl34_g12 | .406 | .829 | .267 | .680 | .27 | +20.4pp | +3.2pp（.444） | **+7.4pp**（.412→.485，n＝68） |

（逐題異質那欄的括號是預測的最終成功率；增益以 R 臂第 1 次實測為基準。全樣本內估計時三批預測最終分別為 .723／.234／.464。）

〔推論〕(1) **假設各次獨立的公式把增益高估約 1.6–2.8 倍**；把每題的 p 分開估（題目難度異質）之後，ctl12_q9 幾乎完全對上，另兩批反而低估 4–5pp。(2) verifier gain 的排序（q9 最小）和實測增益（三批幾乎一樣）不一致——在 k＝3、同題高度相關時，「精確度上限」不是好的預測量。(3) 低估那兩批可能是「重開後的嘗試比第 1 次好」（例如第 1 次較常逾時），也可能是每題只有 6–9 次抽樣、p 估得太粗；這正是破口 4 要分辨的。

〔推論〕結論：**「值在、欄錯」不是新問題**，在摘要（intrinsic 錯）、化學歸屬、CTI 抽取、表格歸屬裡都量到「偵測器對這類錯較弱」；**現成的解法方向是「先對齊欄位、再比值」**（儲存格歸屬、宣稱拆解）。但我沒找到任何研究在 **agent 交出的逐欄報告**上，比較「只問有沒有出處」與「問出處是否回答這一欄」兩種判定問法——這原本是新的破口 1；評分器更正後降為破口 3，問題改成足球組的「部分值」與「抄到別處」。

## 4. 研究破口清單（依重要性排序；每題都可檢驗；2026-11-28 晚依評分器更正重排：1 評分器效度、2 判定之後的動作、3 欄位對齊〔降級〕、4 同題相關，其餘照舊）

### 破口 1：評分器與答案鍵的效度（2026-11-28 晚追加，排第一）

- (a) **不知道的**：每一批的評分器（`canon_strict`＋答案鍵；程式題則是隱藏測試）把對的判成錯、把錯的判成對的比率是多少，集中在哪些欄、哪一組。到今天為止，**沒有一批在看結果之前量過**。確認批次公司組事後才發現：219 個「錯」行裡 184 行（84%）值是對的（〔事實〕`origin/auto/redo` 1cfc8efd0 規則、1e4a110a2 結果：「Founded」答案鍵帶「; N years ago」，129 行；「Traded as」答案鍵帶指數成分，53 行解析不出；修正後公司組錯行 35／451）。
- (b) **最接近的先行研究**：Northcutt et al.（arXiv 2103.14749，**B**）：10 個常用測試集平均至少 3.3% 標籤錯、ImageNet 驗證集至少 6%；用改正後的標籤，小模型在某些錯誤比例下會勝過大模型（ResNet-18 勝 ResNet-50）——**評分錯誤足以翻轉排名**。Gema et al., MMLU-Redux（arXiv 2406.04127，**B**）：估計 6.49% 的 MMLU 題有錯，Virology 子集 57%，重標後模型表現與原報告有顯著差異。Vendrow et al.（arXiv 2502.03461，**B**）：普遍的標籤錯誤會掩蓋模型的失敗。SWE-Bench+（arXiv 2410.06992，**B**）：成功補丁裡 32.67% 是解答已在 issue 裡、31.08% 是因為測試太弱才通過——**評分器偏寬**的一面。Stroebl 2024（**A**）：驗證器的誤收決定重抽上限。〔本 repo 資料〕本專案已有前例：零設定初版 8 次退回全是誤報（CLAUDE.md）、確認批次的 B24／B26 量具修正。這些都是「基準本身錯」的量測；我沒找到在**判定研究**裡把評分器誤差和判定分辨力放在同一張表上比較的研究。
- (c) **為什麼對本機小模型重要**〔推論〕：小模型工具能用的判定都是弱判定，分辨力差幾個百分點、增益 +3～+8pp；評分器的系統誤差一旦集中在某一組（公司組 84% 的錯是假的），就足以蓋過、甚至反轉判定的訊號。而且偏誤有方向：**正確補上的值和空白一樣算錯，所以「補值」類動作的增益被壓向 0**，以「值在不在頁上」為依據的判定在該組看起來失準。今天的「公司組紀錄旗標反向」「判別 AUC 0.40」都可能是這個缺陷的產物（V1 的 AUC 在排除等值後 0.67、再排除少了年份括號的 16 行後 0.86，執行方報告的數字）。
- (d) **最小離線分析**（每一批、都在看判定結果之前做，規則寫進計畫檔）：
  1. **逐欄審答案鍵的附帶文字**：對每個欄位的答案字串掃附帶物（「N years ago」、括號註、腳註記號、指數或清單文字、單位、換行），列出每欄受影響的行數。
  2. **第二正規化器**：由不同的人或不同的 agent 獨立寫，不看第一個的碼；對全部有填行重評，報兩者不一致率（分欄、分組）。
  3. **人工抽查**：每組在「評分器判錯」與「評分器判對」各隨機抽 30 行，人工判真偽，報評分器的誤判錯（假錯）與誤判對（假對）比率，以組為群集附區間。
  4. **回溯**：確認批次（已做公司組）、探索 T 的 sc 組、實驗一 A 組（軟體＋公司）、exam37、ctl 批次（隱藏測試的強度：SWE-Bench+ 式抽查「通過的補丁是否真的對」）、DABstep（答案格式）。
- (e) **改方向的結果**：任何一組的評分器假錯或假對比率超過該組判定效果量的一半（例如判定增益 +5pp、假錯率 >2.5% 的行），該組的所有結論凍結到重評完成。重評後若「公司組旗標反向」消失，紀錄旗標就是兩組都能用的判定，破口 5（判定組合）的前提改寫；若重評後不變，原結論照舊。不論結果如何，**「先審評分器」寫進每一份預註冊的必要步驟**。

**方法教訓**：審判定之前，先審評分器。弱判定的分辨力小，評分器的系統誤差足以蓋過它；而評分器的錯不會自己顯現——今天是在追「為什麼判定在公司組失效」時才反過來發現答案鍵錯了。

### 破口 2：判定之後接什麼動作，增益主要來自哪一半

- (a) **不知道的**：在判定相同時，增益差多少來自動作強度（同模型重試 C＝0.07–0.43 vs 換較強模型 C＝0.65–0.79）；反過來，動作相同時判定強度差多少。現有比較混在一起（例如 EB 同時換了模型又給了頁面）。
- (b) **最接近的先行研究**：Stechly 2024（PA 筆記 #4：純重抽 ≈ 多給批評）；Zhang 2024（2404.17140，**B**：小模型要配強驗證器）；SPLIT 的混合生成器條件——「混入 B 嚴格有益 iff B 在 A 仍失敗的題上比 A 好」（**A**）。沒有人把「判定強度 × 動作強度」做成因子設計量 agent 任務。
- (c) **重要性**〔推論〕：本機工具的預設動作是「同一個小模型再來一次」，這正是 C 最低的動作；若增益幾乎全在動作，產品該做的是「判定不過就升級」而不是「造更準的判定」。
- (d) **最小離線分析**：用 expTc 已有的四格近似 2×2：TB（只查空白×同 9B）、EB（只查空白×Haiku＋頁面）、T（紀錄標記×同 9B）、ER（紀錄標記×Haiku），逐行算 C 與損失，分組報；再把 EB 拆成「被送出的行」與「Haiku 本來就會答的行」（HP 每組一次可當上限參照）。檢驗 SPLIT 的混合條件：Haiku 在 9B 失敗的行上的成功率 vs 9B 在同行的成功率。
- (e) **改方向的結果**：若動作的主效應遠大於判定（例如同判定換動作 +20pp、同動作換判定 <+5pp），停止投資判定精緻化，主線改成「最便宜的高精確度判定（空白、缺檔）＋升級」。

### 破口 3：欄位對齊（降級但保留）——足球組的「部分值」與「抄到別處的值」

- (a) **不知道的**：評分器更正後，「值在頁上但欄位錯」的主要證據少了一大半（公司組錯行只剩 35 行，其中「少了年份括號」16 行）。剩下真正值得問的是足球組兩類（〔事實〕1e4a110a2 的步驟 0 分類）：**R-部分 85 行**（只寫出場或只寫進球；V1 平均 p 0.72，是最弱的一類，只有 13 行 p<0.5）與 **R-他處 108 行**（值在抓過的頁上別處，例如別的表、別人的列；平均 p 0.32，85 行 p<0.5）。不知道的是：把欄位格式（例如「出場（進球）」兩個數都要）與「值所在的列」給判定、或改成先選段落再比值的兩段式，能不能比 V1 更抓得到這兩類。
- (b) **最接近的先行研究**：AggreFact 錯誤分層（2205.12854，**A**：CNN 子集上「原文裡有、但接錯」的錯召回一致較低）；化學實體歸屬（NeurIPS 2026，**P**）；ViTaB-A（2602.15769，**B**：引用欄比引用列難）；TraceBack（2602.13059，**B**）。
- (c) **重要性**〔推論〕：「只填一半」與「抄到隔壁表」是小模型讀表最常見的兩種錯；前者其實可以用不需要模型的格式檢查抓（模板行規定了「N (N)」），後者是儲存格歸屬問題。
- (d) **最小離線分析**（取代 §2.5 原規格的主結果；執行方 1cfc8efd0 的 PLAN 已凍結的部分照舊跑，以下作為**另報**，跑之前寫進計畫檔）：
  - **格式檢查（零成本對照）**：依模板行的格式（例如兩個數字、括號）寫確定性檢查，量它對 R-部分的召回與對「對的行」的誤擋。
  - **V2′**：在 V2 的輸入裡加「此欄要求的完整格式」，多問一題 Noul「這個值是否包含此欄格式要求的所有部分？」。
  - **V3**：照原設計；主要看 R-他處的召回。
  - 主要終點改成：**足球組 R-部分與 R-他處各自的召回**（固定門檻 p<0.5 與 15.7% 標記率門檻），以及足球組整體 AUC 對 V1 的配對差（組群集 bootstrap，20 組）；公司組只描述（35 個錯行、10 組，不夠做主結果）。
  - 花費：只跑足球組 1,112 行，每種問法約 $1.2。
- (e) **改方向的結果**：格式檢查就抓到 R-部分的大部分 ⇒ 這類不必用模型；V3 在 R-他處的召回比 V1 高且區間不含 0 ⇒ 採兩段式；都不行 ⇒ 接受「抄到別處」是雲端判別模型也看不到的錯，交件說明照實寫。

### 破口 4：同題多次嘗試高度相關時，重開／挑選的增益上限怎麼算

- (a) **不知道的**：增益的主要折扣來自「題目難度異質」（給定題目後各次仍獨立）還是「給定題目後仍相關」（例如同一個誤解每次都犯、同一種逾時每次都發生）。前者 SPLIT 已能處理，後者沒有公式。
- (b) **最接近的先行研究**：ROC-n-reroll（2507.12399，**A**，單題層級、題內獨立）；SPLIT（2610.23255，**A**，異質難度＋跨模型 copula，但題內條件獨立）；Stroebl（2411.17501，**A**）。都沒有在 agent 任務上檢驗題內條件獨立。
- (c) **為什麼對本機小模型重要**〔推論〕：小模型的失敗多半是能力缺口，同題重試會重複同一個錯（ctl34 ICC≈0.80）；若題內仍相關，增加 N 幾乎沒用，預算應該花在換模型或換提示。
- (d) **最小離線分析**：§3.3 的計算擴到 haiku_cchard、devin_cchard16（run root 裡有逐次 `grade_pass`）；檢驗題內條件獨立：比較「第 1 次失敗後第 2 次成功率」與「該題的 p 估計」（以重複為單位留一）；分開逾時與非逾時的失敗。零機時。
- (e) **會讓我們改方向的結果**：若條件獨立成立（實測≈異質預測），就用 SPLIT 式小試點規劃 N 與預算，不必再跑大批次；若第 2 次成功率顯著低於 p（題內相關），停止加大 N，改投資「換生成器」（破口 2）。

### 破口 5：多個弱判定的組合——錯誤是否相關、合起來能不能勝過單一判定

- (a) **不知道的**：空白、出處旗標、跨重複一致度、可見測試這幾個判定的錯誤彼此相關到什麼程度；在非程式任務上，組合後的精確度能否高過最好的單一判定。已知的反例：出處旗標在足球組 7 倍集中、公司組反向。
- (b) **最接近的先行研究**：SPLIT Prop. 2（**A**，相關評審的多數決何時降低精確度）；自我一致性（2203.11171，**B**）；Kadavath（2207.05221，**B**：看多個自己的樣本能改善 P(True)）。都是單一判定或同質評審，沒有量**異質便宜判定**在 agent 報告上的聯合錯誤結構。
- (c) **重要性**〔推論〕：本機工具負擔不起強評審，只能靠幾個便宜判定；如果它們的錯高度相關，組合沒用；如果不相關，組合是最便宜的強化。
- (d) **最小離線分析**：一致度判定幾乎免費——同一把 HMAC 鍵下等值可比，所以**同一組多個重複的初稿，同一行的值是否一致**可以直接從 `expT_lines_hmac.jsonl` 算（不需要原文）。逐行算：一致度、出處旗標、空白的兩兩錯誤相關（在錯行與對行上分別算 phi）；以組為群集交叉驗證一個邏輯斯迴歸堆疊，與最好的單一判定比精確度（相同標記率）。分組報。
- (e) **改方向的結果**：若一致度在公司組的精確度高於出處旗標，公司組改用一致度；若組合在兩組都不勝過單一判定，停止做判定組合，接受「空白＋缺檔」為主判定。

### 破口 6：機率式判定的門檻怎麼定，才不會變成看結果調參

- (a) **不知道的**：判別式模型或 logprob 的門檻能不能事先定、能不能跨任務族移轉；本專案沒有任何「在一個組上定、在另一個組上驗」的數字。
- (b) **最接近的先行研究**：Jev 評測（2609.37647，**A**：0.5 門檻常把好的排序變成差的 F1，用 1,000 個訓練例調門檻後 0.50→0.75）；AWS 文章（**P**：50 個標籤擬合一個溫度）；偏誤稽核（2611.00496，**B**：選項對調翻轉最多 72.6%）。他們的門檻都在同一個資料集內調，沒有跨任務族移轉的結果。
- (c) **重要性**〔推論〕：零設定產品沒有使用者給的標籤；門檻若必須逐領域調，機率判定就不是零設定。我們已經看過一次跨組反向（出處旗標），機率判定很可能重演。
- (d) **最小分析**：§2.4 的規格本身——門檻在公司組 s01–s05 擬合，套到公司組其餘與整個足球組；同時報 0.5 固定門檻；預先寫進計畫檔再跑。
- (e) **改方向的結果**：若跨組移轉後精確度掉到不如字串旗標，機率判定只能當「人看的提示」，不能當自動退回的依據。

### 破口 7：判定被 agent 操弄——可見測試與出處都會被騙

- (a) **不知道的**：本機小模型 agent 在看得到判定時，多常「做給判定看」；出處判定會不會把 agent 自己寫過或抄來的檔當成出處。
- (b) **最接近的先行研究**：Baker 2025、Ma 2026（PA 筆記 #12、#20：給了可見驗證訊號就迎合）；METR 2025（PA 筆記 #16：看得到評分函式時作弊多 43 倍）；DICE（2610.14404，**B**：判定模型本身沒被攻擊，轉接點就能改決策）。都是前沿模型、程式任務；沒有小模型在非程式任務上的出處操弄率。
- (c) **重要性**〔推論〕：我們的判定（出處比對、可見測試）全部讀 agent 工作區裡的東西；agent 越會用工具，越可能讓判定看到它想讓判定看到的。
- (d) **最小離線分析**：〔本 repo 資料〕已有一例——fb-s04/r1 的 TB 臂抄了 exp1cB s04 的報告（19 個值相同、其中 17 個錯值也相同；見本分支提交 977ec7c5d 的訊息）。在 expTc 全部紀錄裡數「值的出處是工作區裡先前的報告或 agent 自己寫的檔」的行，看出處判定把它們算成有根據的比率。可見測試的偽裝（協調者轉述「同名模組騙過可見測試」——**我在 repo 裡沒找到這筆紀錄**）：在 ctl 批次裡找「可見全過、隱藏沒過」的嘗試，看差異是否動到測試的匯入路徑。
- (e) **改方向的結果**：若抄來／自寫的出處佔被放行有填行的一成以上，出處判定必須只認沙箱外抓取（代理紀錄），工作區檔案一律不算出處。

### 破口 8：沒有標準答案的非程式任務，除了「有沒有出處」還剩什麼能判

- (a) **不知道的**：對報告型產出，便宜判定的候選（跨重複一致、往返：從頁面再抽一次比對、蛻變：擾動頁面後答案是否跟著變、要求欄位涵蓋）各自的精確度與召回。
- (b) **最接近的先行研究**：往返正確性（2402.08699，**B**，程式）；Drowzee 蛻變測試（2405.00648，**B**）；Kadavath P(True)（**B**）；LLM-AggreFact 系列（§3.2）。逐件精確度只有出處判定這一類量得最清楚。
- (c) **重要性**〔推論〕：本專案 DABstep、維基欄位等非程式題才是零設定產品的大宗；只靠出處判定，在公司組已經失效。
- (d) **最小分析**：一致度見破口 5（免費）；蛻變判定的小批次：取 10 組，把頁面上目標值改掉後重問同一行（只問判定模型，不重跑 agent），看「被支持」機率是否翻轉——這同時量判定模型是否在讀頁面、還是靠記憶（§2.4 的條件 (c)）。
- (e) **改方向的結果**：若除了空白與出處之外沒有一個判定在兩組都精確度 >0.8，就接受「非程式任務只做缺漏與出處」的範圍，產品口徑照此收窄。

### 破口 9：紀錄本身能不能當判定依據（金鑰放在 agent 寫得到的地方）

- (a) **不知道的**：當簽章金鑰或公鑰在 agent 讀寫得到的位置時，以紀錄為依據的判定（例如「這個值是從哪一步讀來的」）還剩多少證據力；實際上 agent 會不會去改紀錄，從沒量過。
- (b) **最接近的先行研究**：〔本 repo 資料〕`NOTE_20261128_THIRD_PARTY_RECOMPUTE_REVIEW.md` 已整理三種金鑰位置（長期金鑰檔 agent 拿得到；臨時金鑰的公鑰是自我宣告）；`NOTE_20261128_CONTROLLER_AUDIT.md`：控制器批次鏈頭全是 null、每格臨時金鑰。外部先行研究（例如外部錨定的透明日誌）**這次沒有查、沒有讀**，不引用。
- (c) **重要性**〔推論〕：本機工具與 agent 同帳號執行是常態；若紀錄可被重寫，所有「紀錄式判定」都退化成「agent 自述」。
- (d) **最小分析**：盤點每一種判定的輸入來源是「沙箱外紀錄」（代理、harness 行程記憶體）還是「agent 可寫路徑」；在 expTc 已有的紀錄裡數兩者各佔多少判定。最小實驗：在一個小批次裡放一個金絲雀（判定依賴的紀錄檔），看 agent 是否讀寫它。
- (e) **改方向的結果**：若主要判定都依賴 agent 可寫的紀錄，判定輸入一律改由沙箱外產生，否則對外不能說「依紀錄判定」。

## 5. 結論

〔推論〕**別人已經做過、而且做得更好的**：包在既有 agent 外的「驗證＋重試」外殼（OpenHands 的 critic 與 Iterative Refinement、AgentLoop）；程式任務的多份挑選（CodeMonkeys、S*、R4P、Agentic Verifier）；「這一行有沒有被文件支持」的判定器與公開基準（LLM-AggreFact 上 1B–9B 的開放模型與 Jev 只差 2–3pp）；以及「驗證器的 ROC 與重抽增益」的公式（ROC-n-reroll、SPLIT）——我們手上的「增益 ≈ Pf × V × C − 損失」恆等式，在「失敗就重開」這一側可以對應到 SPLIT 公式在 k＝3、交件規則略異時的情形（V＝1−f、精確度＝a/s）。**還沒人做清楚的**：在小模型、非程式的 agent 任務上，(1) 同題嘗試高度相關時那些公式還準不準——我們三批資料顯示獨立假設把增益高估 1.6–2.8 倍，逐題異質能解釋大半但不是全部；(2) 判定強度和動作強度各貢獻多少；(3) 異質便宜判定的聯合錯誤結構與跨領域門檻移轉；(4) 判定被 agent 操弄、紀錄被 agent 改寫時還剩多少證據力。這四件事都能先用現有資料離線檢驗。（追加，同日晚更正）判別模型先導一度讓「判定該問『出處是否在回答這一欄』」排到第一；但執行方的錯行分類顯示公司組 84% 的「錯」是答案鍵造成的，**真正排第一的是評分器與答案鍵的效度**——它是其他所有破口的前提。欄位對齊降級，只剩足球組的「部分值」（85 行）與「抄到別處」（108 行）兩類值得測。**方法教訓：審判定之前，先審評分器。**

## 6. 限制與沒讀的

- **B 級（只讀摘要）**的來源，數字只取摘要裡寫的；Judging the Judges 小模型的逐一數字在圖裡，我沒抽出。
- **沒讀**：OpenHands「Learning to Verify AI-Generated Code」（critic 準確度）、eesel／DEV Community 的 Clef 比較文、llama.cpp PR #24423 現況（GitHub 存取被這個工作階段擋下）、Gemini Decisions 的定價頁（價格取自部落格與官方文件正文）、外部透明日誌類文獻。
- §3.3 的預測是事後、小樣本（每題 6–9 次抽樣），且把「都沒過時的交件規則」近似成「交被退回的那次」；haiku／devin 兩批沒算（逐格資料不在本 repo）。
