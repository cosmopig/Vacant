# 「可由第三方重算」加註清單的審查（2026-11-28）

> 審查對象：`origin/auto/redo` c1e1d83e5 的 `ops/redo/review/THIRD_PARTY_RECOMPUTE_ANNOTATIONS_20261128.md`。
> 口徑：可以寫「第三方可以驗證這條鏈內部一致、沒有被截斷或局部竄改，並重放出同樣的判定」「鏈的內容只對沙箱外的紀錄有外部錨點；其餘事件的真實性取決於簽章金鑰沒有被鏈所記錄的那個 agent 拿到」；不可以寫「紀錄可由第三方重算，所以可信」「agent 無法竄改紀錄」。
> 只出審查意見；README 的改動要經擁有者核准。

## 先釐清：Vacant 裡有三種簽章，威脅模型不一樣
加註句若一體適用，會在某些地方說錯機制。

| 類型 | 金鑰在哪 | agent 拿得到嗎 | 真正的弱點 |
|---|---|---|---|
| **K：長期金鑰檔**（`vacant install` 的掛鉤病歷、D2′／實驗 T／確認批次的 `VACANT_HOME`、intake 的 verifier／owner 金鑰） | 同一 OS 使用者讀得到的檔；實驗批次放在 agent 自己的 live 目錄 | **拿得到**（同帳號；確認批次的沙箱還把 live 目錄掛給 agent 讀寫） | agent 可以用**同一把**金鑰整條重簽，也通得過簽章者信任清單 |
| **E：每次執行的臨時金鑰**（`vacant run` 收據、控制器批次） | 只在 launcher／harness 行程的記憶體裡，私鑰不落盤（`docs/VACANT_RUN.md`：「私鑰不落盤，RECORD_SPEC §7」）；公鑰寫在鏈旁的 `.pub.json` | 從磁碟偷不到 | **公鑰是自我宣告**：`verify_receipts.verify_arm` 直接讀同一目錄的 `.pub.json` 來驗（`PublicIdentity.from_hex(meta[...])`），沒有釘到外部。任何能寫 run 目錄的程序（同帳號的 agent、作者本人）都能換一把新鑰匙，重做一條同樣驗得過的鏈 |
| **M：多方金鑰**（r454 三把金鑰的收據展件） | 三台執行器各自的金鑰 | 取決於受測程式和簽章程式是否在同一台機器、同一帳號上跑 | 「誠實多數」與「金鑰沒被受測程式拿到」都是前提 |

外部錨點也要分批看：
- 確認批次有 netns 沙箱：伺服器存取紀錄在沙箱外，agent 碰不到。
- **D2′、探索 T、控制器三批沒有沙箱**：伺服器存取紀錄、出口紀錄也在 agent 同一帳號可寫的位置。能當外部錨點的，只剩不在受測主機上的紀錄（例如 LM Studio 端的日誌），或執行當下就推到遠端的鏈頭；而且要實際拿來對過才算。

所以加註句「同一系統帳號下的 agent 可整條重簽，外部錨點只有沙箱外的紀錄」：
- 對 K 類、有沙箱的批次正確；
- 對 E 類說錯了機制（不是 agent 重簽，是公鑰可被整份換掉）；
- 對沒有沙箱的批次說得太強（暗示有沙箱外的錨點）。

## 4. README／VACANT_RUN 的建議文字（送擁有者核准）
- **README.md 第 761 行**：「Vacant 滿足**防竄改**與**小到可被驗證**」改成「Vacant 只滿足**小到可被驗證**；**防竄改不成立**：紀錄是**竄改可察覺**（tamper-evident），但簽章金鑰是同一 OS 使用者讀得到的檔（見本頁開頭的 ⚠），持有金鑰的程式（包括 agent）可以整條重寫。**complete mediation 也不滿足**。」第 1012 行同樣改。`README.en.md` 第 846、1158 行改成「Vacant satisfies only **small enough to be verified**. It is **not tamper-proof**: the record is **tamper-evident**, but the signing key is a file readable by the same OS user (see the ⚠ at the top), so a program holding it, including the agent, can rewrite the whole chain. It does **not** satisfy complete mediation either.」
- **README.md 第 1005 行**：「要越過那一關得持有簽章金鑰」後加：「（前提是金鑰保管：`vacant_network/receipt.py` 的誠實邊界寫明『key custody 假設下』；同一 OS 使用者讀得到金鑰時，這一關擋不住同機的程式，部署層要另外用沙箱或 ACL 把金鑰和 agent 分開。）」第 1100 行表格「說 Vacant 是強制層」那一列的「對」欄，在「沒有可驗證收據的交付不被接受」後加「（收據只證明簽的人持有那把金鑰、之後沒被改）」。
- **docs/VACANT_RUN.md §4（誠實邊界）加一條**：
  > ### 4.x 收據的公鑰是自我宣告的
  > `receipts_<ARM>.pub.json` 和鏈放在同一個 run 目錄，`verify_receipts` 用它來驗。所以驗得過只證明「這條鏈和旁邊那把公鑰一致、之後沒被改」。私鑰不落盤，agent 從磁碟偷不到；但任何能寫 run 目錄的程序（同帳號的 agent、作者本人）都能換一把新鑰匙，重做一條同樣驗得過的鏈。要排除這一點，收件端必須事先釘住公鑰，或在執行當下把鏈頭交給 run 目錄以外的地方。收據也不證明 agent 做了什麼（§4.2）。
