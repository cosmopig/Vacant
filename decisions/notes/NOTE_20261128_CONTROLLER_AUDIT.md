## 2. ctl34 C 的分母 66（判定：有保留）

**缺的兩格**（逐格表 `infra_void`）：

| 格 | 主機 | 原因 | 被判 void 之前那一次有效嘗試 |
|---|---|---|---|
| pg_transpose/r1/C | lms1003gemmaN | `void×4:infra_marker` | 第 1 次：驗收 0/6、600 秒逾時、隱藏 0/6、135 萬 token；控制器規則 6「續做」 |
| pg_transpose/r2/C | lms1004gemmaN | `void×4:model_died_mid_run` | 第 1 次：驗收 0/1（載入失敗計成 1 條）、600 秒逾時、隱藏 0/1；規則 6「續做」 |

兩格都是同一題，都是第 1 次有效、接著從那個工作區「續做」，然後連續 4 次基礎設施失敗；整格牆鐘 3,219 秒與 3,211 秒（超過 1,800 秒預算，因為 void 重試的退避不算預算）。

**排除依據**：三份計畫的 `prereg.infra_void` 都寫「仍失敗該格 infra_void 不進分母、逐一列出；比較時任一臂 void 的那一對在該比較不計」。ctl34 的配對 66 對照規定做了。結論的限制段有寫「C 臂有 2 格 infra_void」，**但沒有寫是哪兩格、也沒有寫它們對比較的影響**。

**對 C 有利還是不利**：同一題的其他臂：B r1 過、r2 不過；R r1 不過、r2 過；A 兩次都不過。所以丟掉這兩對，**C 對 B 少算 B 的一次成功，C 對 R 少算 R 的一次成功**——兩個比較都朝 C 有利的方向移動。

| 缺格的處理 | C vs B | C vs R |
|---|---|---|
| 丟掉配對（結論採用） | 32 vs 30，+3.0pp，p=0.625 | 32 vs 32，0.0pp |
| 算失敗 | 32/68 vs 31/68，+1.5pp，p=1.0，Newcombe [−5.4, +8.3] | 32 vs 33，**−1.5pp**，p=1.0 |
| 算成功（上限） | 34 vs 31，+4.4pp，p=0.375 | 34 vs 33，+1.5pp |

「算失敗」不只是保守假設：若照交付規則交出唯一的有效嘗試（第 1 次），兩格的隱藏評分都是 0，就是失敗。

**可能是 C 自己造成的**：void 的判定是「工作區沒動＋0 次成功模型回應，或連線類錯誤」。兩格都在 C 選了「保留工作區續做」之後才連續失敗，而 B、R 在同一題、同一台機器上沒有 void。若是「續做一個逾時、上下文已經很大的工作區」讓 agent 或模型伺服器掛掉，那是 C 這一臂的結果，不是基礎設施。稽核包沒有匯出 void 嘗試的紀錄（`void_*_attempt_*` 目錄、時間戳），**從稽核包判斷不了**。r2 在 1004、`model_died_mid_run`，時間上可能接近 1004 12:56Z 的 OOM，但逐格表沒有時間欄位，也確認不了。

**要改的句子**：
- 「C 臂有 2 格 infra_void。」→「C 臂有 2 格 infra_void，都是 pg_transpose（r1 在 1003、r2 在 1004），都發生在控制器選了『續做』之後；依預註冊丟掉這兩對，等於少算 B 與 R 在這一題各一次成功。若把它們算失敗（照交付規則交出的那一版確實沒過），C 對 B 是 32/68 對 31/68（+1.5pp），C 對 R 是 32 對 33（−1.5pp）。」
- 表格「C 32/66」→「C 32/66（另 2 格 void，見限制）」，並在 C 對 B 欄註「配對 66 對」。

## 3. 措辭有沒有超出證據（判定：不通過）

## 4. 公平性（判定：有保留）

**R／B／C 之間**：每一對 (題, 重複) 的四臂都在同一台主機（三批 0 對跨主機），四臂交錯執行；主機差異在配對內抵銷。逾時分布也重現了 `token_timeout_by_arm_host.json`（每一列的格數、逾時次數、嘗試次數、每格 token 全部一致）。重開臂之間的逾時暴露相近（ctl34：R 63／B 75／C 64 次；ctl12：9／8／10；E4B：8／9／6）。但這也表示控制器是在「600 秒常常不夠」的條件下被測的：ctl34 觸發規則 5（修復）之後，下一次有 10/15 次又逾時。結論應寫明「控制器沒贏」是在這個速度條件下的結果。

**對 A 的比較**：結論的限制段寫了「A 是單次 1800 秒、其他臂是 3×600 秒，結構不同」，也寫了「慢速對有 600 秒上限的臂比較不利」。**後一句和資料方向相反**。ctl34 有 21 題的兩次重複落在不同主機，在這 21 題裡從 1004 換到較慢的 1003：A 10/21 → 4/21、R 13 → 10、B 12 → 9、C 13 → 9。A 在 1003 有 17/35 格連 1,800 秒都用完。依主機分開，R−A 在 1003 是 +17.1pp（p=0.031）、在 1004 是 +12.1pp（p=0.22）。所以 1003 對 A 的傷害至少一樣大，「重開 > A」有一部分來自 1003 這台。⚠ 2026-11-28 補註：ctl34 的 agent 上下文設定兩台不對稱（1004 是 60000，1003 還在查；ctl12 兩台都是 32768），所以這裡的主機差異可能含上下文設定，不一定是速度。這不推翻方向（兩台都同方向），但限制句要改。E4B 上 A 平均只用 195 秒就結束（0 次逾時），重開臂則多用了嘗試次數；那裡的「等預算」是上限相同，實際用量差很多。

**ctl12 並行過高**：決策文件與結論都有交代（每串流約單串流的 35%；逾時幾乎全在 1004）。對 R／B／C 之間影響對稱；對 A 的影響方向同上，判斷不了。

**ctl34 harness 中途變更**：逐格表裡新 harness（`4c687dcaf469`）只有 11 格、4 對：pg_dominoes/r2（A、C）、pg_rest_api/r2（四臂）、pg_transpose/r2（只有 R）、pg_variable_length_quantity/r2（四臂）；其中 2 對同一對內兩種 harness 混用。新 harness 下 C 3/3（含 pg_rest_api/r2 這個 C 獨過的對）。丟掉這 4 對：C vs B 29 vs 28（+1.6pp，p=1.0）、C vs R 29 vs 30、R vs A 30 vs 22（p=0.021）。結論的方向不變，但 C 對 B 的 +3.0pp 有一半來自受影響的對。**OOM 續跑**：逐格表沒有時間欄位，也沒有「續跑前／後」標記，除了 1004 的 harness 雜湊之外看不出影響；ctl12 1003 的 OOM 在資料裡沒有任何可分組的痕跡，驗不了。

**E4B 的偏離（結論沒寫）**：
- 預註冊寫 A100-SXM4-40GB、並行探針也是在 A100 上量的（jobs 12）；README 與結論寫 L4。
- 預註冊在 03:55Z 提交（計畫自己寫「commit（不 push）」）；資料的 harness 是 `4c687dcaf469`，也就是 12:59Z 之後的版本。

**要改的句子**：
- 「A 的單次上限是其他臂的 3 倍，所以慢速對有 600 秒上限的臂比較不利。」→「A 的單次上限是其他臂的 3 倍。實際資料裡，慢主機（1003）對 A 的傷害至少一樣大（同一批題換到 1003：A 10/21 → 4/21，R 13 → 10），所以 A 與重開臂的差有一部分來自慢主機；這個結構差的影響方向無法事先判定。」

## 5. 決策事件（判定：有保留）

**重建**：三批共 257 個事件，在 140 個 C 格裡；每格的事件數都等於嘗試次數、attempt 編號連續。每個事件我只用它自己的 evidence 欄位（加上前一事件的簽章與通過數），照決策文件的順序與門檻重推規則：1 全過；2 剩餘嘗試 ≤0 或剩餘秒數 ≤0 或 < 60（第十次稽核補註 3a）；3 通過數 < 先前最佳通過數；4 失敗簽章與上一次相同、通過數沒增加、連續第 2 次（逾時的狀態簽章也算，補註 3b）；5 通過數 ≥ 驗收總數的 70%（整數比較 `passed×10 ≥ total×7`）；6 其他。**257 個 0 不符**。evidence 內部也一致：`pass_ratio`＝passed/total、`mostly_passing`、`prior_best_passed` 與我依「驗收全過者勝，否則通過數最多、同分取最新」重算的最佳一致；passed 等於逐測試結果裡 true 的個數；事件的規則、通過數、總數和逐格表 `attempts[]` 相同（逾時與載入錯誤時逐格表寫 null、事件寫 0，視為相同）。

**門檻的實際意義**：
- 規則 5 的 70% 用的是**驗收那一半**的通過率，分母是「實際跑到的測試數」，不是固定的測試方法數。8 個事件的總數是 1（模組載入失敗計成 1 條），都是 0/1，沒有讓規則 5 誤觸發。
- 規則 3 比的是**通過條數**，不是比例；逾時或載入錯誤記 0 條，所以「agent 把檔案弄壞」會走規則 3。

**抽查 5 條 C 序列**。抽法（確定性規則；我是在看過規則次數之後才定的，不是事前登記）：ctl34 依格名排序，分別取第一個含規則 3、規則 4、規則 5 的格（互不重複）；E4B 取第一個含規則 5 的格；ctl12 取第一個含規則 4 的格。

| ctl34 pg_affine_cipher/r1 | 7/8 → 5 修復；4/8（4 < 7）→ 3 回最佳；8/8 → 1 | 第 3 次，隱藏 8/8 | 順序與門檻正確；回到 7/8 的快照後修好 |

**要改的句子**：「規則實際觸發（C 臂的決策事件，都上了簽章鏈，可以重建）」→「規則實際觸發（C 臂的決策事件寫進每格自己的簽章鏈；稽核包附了事件內容，可以據此重推每一步的規則，但沒有附鏈檔與公鑰，鏈頭欄位是空的，外部無法驗簽；每格用臨時金鑰，簽章只證明鏈內一致）」。

## 6. 沒被問到、但看到的問題

1. **E4B 的 hidden/ 對 agent 可見**。E4B 計畫寫「Colab VM 上不套 bwrap」；題庫（含 `hidden/`）放在同一台 VM 的 `/srv/redo/bank`；`redo.py` 自己的誠實邊界寫明「暫存工作區不是沙箱，它讀得到磁碟上的 hidden／別次嘗試的歸檔」。本機兩批有 bwrap，E4B 沒有。逐格表看不到明顯的洩漏訊號（驗收沒全過卻隱藏全過的格：E4B R 1、C 1、A 0、B 0），而且 E4B 的成功率很低，所以不像有大量讀取；但沒辦法排除，結論也沒寫。要排除得 grep 那一批的 agent 工作階段紀錄裡有沒有碰到 `hidden`／`/srv/redo/bank` 的路徑。
2. **修正 5 的時序**。條件是在 ctl12 完成 142/144 格之後寫的，執行方看過約 20 行逐格輸出，而 `attempts=N` 就在那些行裡；條件 3 實測 11、門檻 10。決策文件交代了，結論沒有。ctl12 被判無法區分，也決定了結論主句只依賴哪兩批。因為三批都是同樣的無效結果，這不會改變結論，但應該在結論裡寫一句。
3. **R 對 A、B 對 A 不是預註冊比較**；預註冊比較是 2 個 × 3 批，沒有多重比較校正（都不顯著，所以實際上沒差）。
4. **有效樣本比格數少得多**。真正有不一致的題：C vs B 在 ctl34 只有 4 題、E4B 1 題、ctl12 6 題。E4B 12 題裡 6 題四臂全部格都不過、1 題（binary）全部都過，資訊只來自 5 題。以 (題, 重複) 為單位的 McNemar 把重複當成獨立；以題為群集時 p 一樣或更大，結論方向不變，但「12 題 × 3 次」的檢定力比字面上低。
5. **評分器逾時算失敗**：ctl12 的 ex_camicia 有 6 格 `hidden_total=0`，E4B 與 ctl34 也有 `hidden_total` 為 0 或 1 的格（評分器逾時或載入失敗）。各臂都有，但那幾格量的是「會不會卡住」，不是「對不對」。
6. **E4B 用 9B 挑的題**，E4B 在其中 6 題四臂完全做不到，地板效應讓這一批幾乎只能測「能不能多做出一兩題」。
7. **主機與題目混雜**：ctl34 的 pg_beer_song r1（1003）四臂全不過、r2（1004）四臂全過，主機效應很大。配對內抵銷，但跨批「A 的成功率」不能直接比較。

## 給擁有者的話（白話）

我把三批實驗從逐格資料重算了一遍，數字全部對得上，控制器也確實照它的規則在跑。結論的大方向沒錯：**控制器沒有贏過「固定重做三次」**；「做三次、用看得到的測試挑最好的那次」比「一次做到底」好，這一點在 12B 那批很清楚。

但有三句話說得太滿：
1. 「三者打平」——資料只能說「看不出差別」。這麼少的題目，5～9 個百分點以內的差都量不出來，不能說一樣好。
2. 「控制器省 token、比較不會弄壞」——只在其中一批成立，另一批反過來（E4B 上控制器比較貴）。
3. 「慢的機器對重做比較不利」——資料剛好相反，慢機器拖垮最多的是一次做到底的那一組。

另外，12B 那批控制器少的兩格，剛好讓兩個對手各少一次成功；如實算成失敗，差距就從 +3% 變成 +1.5%／−1.5%。E4B 那批在雲端跑的時候沒有把隱藏測試關起來，機器也和事先登記的不一樣，這兩件事結論裡都要寫。
