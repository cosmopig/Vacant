# 「背景子 agent 在做時先不驗收」與「委派呼叫不寫檔」的對抗審查（2026-09-24）

審查對象：`53a6459f`（延後驗收）、`de3bb2bf`（委派呼叫的寫入歸真正寫它的那一步）、`e4eb3d55`（標記的字樣）。
兩個鏡頭，每條附重現腳本，另一個 agent 試著推翻。8 條裡 **5 條是這幾個改動引進的、成立**；另外 3 條被判為既有或低度，
其中 2 條照樣修了（一條會讓子 agent 可證明的錯變成「不知道」，一條是提示注入）。回歸測試：
`tests/test_trace_capture.py` 的 `test_defer_review*`／`test_flag_review8_*`、
`tests/test_trace_blame.py::test_credit_review_*`（改之前全紅）；審查者自己的重現在修正後全部轉紅（問題消失）、對照組照舊綠。

| # | 問題（判定） | 怎麼修 |
|---|---|---|
| 1 | 沒送 SubagentStop 的子 agent（使用者結束、當機、Esc 中斷）在工作階段結束後還算「在做」⇒ `--resume` 之後一小時內每一次回合結束都不驗收（成立，中） | 工作階段結束時，它的子 agent 一律記成結束（子 agent 不會活得比它久） |
| 2 | 延後的那一次沒有更新這個工作階段的結果 ⇒ 先 accept、之後自己刪掉報告、叫一個背景子 agent、結束 ⇒ 信譽記成成功（成立，中；反過來也會） | 延後時把這個工作階段上一次的結果作廢，結束時以新的驗收為準 |
| 3 | 每一回合都先叫一個背景子 agent 的主 agent 永遠不被驗（一小時的上限是每一個子 agent 各自算）（判為設計缺口，低） | **連續**延後最多 3 次，之後照常驗收；真的驗過就歸零 |
| 4 | 主 agent 的回合結束把背景子 agent 正在跑的那一步收掉 ⇒ 子 agent 真的 post 被當成重複丟掉，可證明的錯變成「不知道」（既有，但延後正是這個情況） | 回合結束只收**這個行動者自己**的步驟 |
| 5 | 「同一個版本」只比後版本：委派期間有人把檔改回很早以前寫過的版本 ⇒ 版本鏈被接錯，之後只加了一行的另一個工作階段背「可證明」（成立，中） | 只認委派**之後**才收尾、而且前版本與後版本都一模一樣的步驟 |
| 6 | 同一個原因：缺件時「最後寫這個檔的」指到寫了正確內容的那一步（成立，中） | 同上 |
| 7 | 同一個原因：委派期間沒人解釋的改動消失，結論變成「那時候那裡沒有這個值」（假的）（成立，中） | 同上 |
| 8 | 任何能寫檔的步驟都能往病歷加一筆沒有 owner 簽章的「標記」，下一次回合結束它以「the task owner says」回饋給 agent＝提示注入（既有，這次的字樣讓它更像委託者的話） | 標記與撤銷都要有 owner 金鑰的簽章、而且簽的就是事件裡的內容；沒有就不回饋 |

仍然成立的邊界：延後是「時機」不是「內容」——工作階段結束時的背景追緝與（開著的話）自動交件照樣驗；連續延後的上限
是次數不是時間。標記的簽章金鑰和 agent 在同一個帳號時，agent 拿得到 owner 金鑰就偽造得了（`intake/keys` 的既有邊界）。
