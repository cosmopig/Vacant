# HTTP 收件口回應裡的定位：對抗審查（2026-09-25）

審查對象：`e1c68c65`（`server._locate`、`trace.blame.locate_results`）。一個審查者、三個鏡頭（洩漏、安全、準不準），每條由另一個
agent 在本機起的 HTTP 服務上重現。**9 條，全部成立、全部修掉。** 回歸：`tests/test_intake_server_cli.py` 最後五條（修之前全紅）。

| # | 問題 | 怎麼修 |
|---|---|---|
| 1 | **總數的定位是平方時間**：報告裡每一行都是同一個錯的總數 ⇒ 1 MB 花 26 秒、2 MB 花 100 秒（驗收本身 0.3 秒），而 HTTP 的上限是 60 MB——任何拿到 token 的人一次交件就能佔住一個核心好幾個小時（高；本機的回合結束也用同一個定位器，只是這次讓它遠端叫得到） | 每一個命中都從頭數換行 ⇒ 改成一次建好行首索引（`_Lines`，查一次 O(log n)）；一個主張最多 50 個位置、一段文字最多數 200 次出現（`contains` 只要 1 次）；HTTP 交件超過 5 MB 不定位（只回裁決與各主張的細節） |
| 2 | **追溯訊息裡的絕對路徑在伺服器上被檢查**：沙箱裡跑的交件印出 `File "/主機上的路徑", line 1` ⇒ 回應只列出主機上真的存在的那幾個＝一個「哪些檔存在」的神諭；驗收者自己的檢查程式與標準庫也被當成交件的問題（中） | 只認成果目錄**裡面**的檔：絕對路徑、`..` 一律不碰檔案系統；尾巴比對從錨點之後算起 |
| 3 | 定位把交來的每一個檔都寫出來，連不在繳付物裡的（`node_modules/…`）⇒ 回饋指著沒驗過的檔，還把真的位置擠掉（中） | 定位看的是**收件口凍結、驗過的那一份**（隔離區的 manifest 攤開） |
| 4 | 反斜線路徑：驗的是正規化後的名字、寫出來的是原樣 ⇒ 回饋說檔案不存在（中） | 同 3 |
| 5 | 被略過的小檔一樣寫進暫存目錄（沒有檔數上限）；一個寫不出來的名字讓整份回饋掉、還回報伺服器的暫存路徑（中） | 同 3；錯誤只回例外的類別名 |
| 6 | `exists`／`forbid_paths` 沒過時，位置是「繳付物的前五個檔」（和問題無關）（低） | 新的定位器：`exists` ⇒ 缺的那個樣式；`forbid_paths` ⇒ 被禁止的那個檔 |
| 7 | 文字主張因為「不是 UTF-8」沒過，回報成「length rule」（低） | 讀不出文字 ⇒ 位置寫「not UTF-8 text」；其他整檔的原因用驗證器自己的話 |
| 8 | HTTP 的回饋說「這是 `vacant check` 的回饋、不是最後裁決」「跑 `vacant check`」——但這份回應**就是**簽過的裁決（低） | `render_agent` 的開頭／結尾／截斷提示可以換；HTTP 用「這次交件的裁決是 …（簽過、交件的一方改不了）」 |
| 9 | `issues[].value` 沒截：回應會原樣吐回交件裡任意長的一行（低） | 每個欄位截到 200 字、清單最多 50 條 |

仍然成立的邊界：交件的大小在 5 MB 以下時，定位的成本和交件大小成正比（有上限、不是平方）；HTTP 交件沒有步驟，
回饋裡不會有「第一次出現在第幾步」、也不記任何人。
