# No-key serial rerun protocol

**Question.** Under matched wall-clock caps, does no-hint R3 improve independently graded OpenCode completion on this hard programming bank without four-way CPU inference contention? This is a harness study, not a product test or a causal comparison with another model or with the first pilot.

- **Runtime.** Use the same pinned OpenCode 1.18.33 and Qwen3-Coder-30B-A3B-Instruct Q4_K_M (30.5B total parameters, 3.3B active). Use a single llama.cpp slot and one active pair at a time, with eight CPU threads and the same per-slot context. No external model calls or credentials. Do not substitute a free hosted model on an outage.
- **Tasks.** Keep the pilot's eight tasks and their exact specifications and grading fixtures; add four original tasks: bounded min-cost transfer, weighted grammar parsing, aging scheduler, and water depth with spill thresholds. Each has four visible cases; separate hidden inputs include held-out stress and edge cases. There is one pair per task, and no task is repeated within this run.
- **Arms.** A has one 1,080-second attempt; R3 has up to three fresh 360-second attempts, also capped at 1,080 seconds total. Each attempt gets the same tools, requirements, starter and visible tests. Stop or select using visible acceptance only. Hidden tests score saved work, including at timeout; they never guide retries. As in the pilot, an infrastructure void does not count as a scored attempt. Arm order is fixed by the new plan seed. These are equal caps, not necessarily equal realized wall time or tokens.
- **Calibration.** Before scoring, save three attempts on a separate synthetic read–implement–test task (different from the task bank). Require at least two independently correct deliverables within a 360-second cut, each with model-driven read/write/test tool activity. The calibration observer may stop the agent after the passing test and solution readback; there is no observer stop in scored cells. This gate checks delivery, not natural process exit, and does not establish that the hard tasks fit.
- **Outcome.** Require 12 scored pairs for a completed run. Report A/R3 passes, discordant outcomes, exact two-sided McNemar at nominal .05, and separate descriptive counts for the eight reused versus four new tasks. Report completion/timeouts and changed-solution counts by arm. Do not pool with the pilot or interpret a non-significant result as no effect. This plan was motivated by the previous CPU pilot, so it is not an independent confirmation of its outcome.
- **Evidence.** Use the same isolation, per-attempt model traces, independent replay, and archive checks as in [the first protocol](PROTOCOL.md). Keep calibration and scored requests separate and retain local model logs. Preserve the initial pilot unchanged and archive this rerun under its own ID.

## Reproduce

Use the setup in [the first protocol](PROTOCOL.md) but create a new wire and output directory. Use `--plan serial_plan.json` for both the runner's `server-args` and `run` actions. Run the neutral calibration before any scored requests. Regrade and pack the new output as in the first protocol. Verify the runtime inventory before interpreting either report.
