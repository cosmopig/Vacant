# 等待態 第三輪：**排隊的那幾位也要有一團屬於他的土**（2026-09-21）

> 這一份接在 `../wait_shape/README.md`（第一、二輪）後面。
> 第二輪把「一個人投卡之後那 15–700 秒」變成畫面上的一件事。
> 第三輪處理它自己在 §十一 列出來的缺口：**同時多人投卡只驗到「排隊」那一半，
> 沒有錄下三個人同時投卡的畫面。**

---

## 一、要解決的那一格（先錄，再改）

展場是**一班人一起走進來**的。同時投卡是常態不是邊角。

`routeSubmission` 一次只讓一位進等待態，後到的進 `waitBacklog`
（第二輪的設計，沒有改）。所以三個人同時投卡時：

* 第 1 位：光柱、黏土、成形中的輪廓、心跳、他的秒數 —— 都有。
* 第 2、3 位：畫面上**只剩右下角投遞口那一列靜止的文字**「排隊中」。

先實錄再判斷（`74_console_診斷_三人同時投卡.log`）：t=17.5 秒起
`backlog=2`、`mode=visitor_wait`，一路撐到收錄為止**沒有任何變化**。
截圖 `10_BEFORE_三人同時投卡_只剩一列字.jpg`。

🔴 而那張 BEFORE 還順便曝出第二件事：大標寫「**信封蠟 正在成形**」，
右下角投遞口同時寫「**1 信封蠟 接下來就是他**」——**同一個畫面自己打自己**。
（`arrivals.spawned()` 只在 `startVisitor` 被呼叫，進等待態不算「上台」。）

## 二、做的事

### 2-1 排隊的那幾團土（主交付）

把他們的土**先搬到台上**，在光柱外圍站成一圈：

| | 中央那一位 | 排隊那幾位 |
|---|---|---|
| 位置 | 光柱正下方 | 光柱左右，四個固定位子（避開 SIMPLE 版 QR 與投遞口板） |
| 大小 | 身高 `0.30H·depthScale` | 約前者的 1/5 |
| 顏色 | 他的卡 ＋ 退化時去飽和 | **只吃他的卡**（見 2-3） |
| 心跳 | `waitPulse(el, seed)` | 同一支，**吃他自己的 seed ⇒ 不同步** |
| 捏痕 | `clayMound` | **同一支**（同一種土、同一種捏法） |
| 會不會長高 | 會（漸近，上限 0.93） | 🔴 **不會**。燈還沒照到他，畫面不可以先演完 |
| 字 | 代號＋已經幾秒＋量過的區間 | 代號 ＋「接下來就是他／排隊中 · 已經 N 秒」 |

`11_AFTER_三人同時投卡_每人一團土.jpg`、`12_AFTER_排隊那兩團特寫.png`、
影片 `20_vid_AFTER_排隊_61s.mp4`（61 秒）。

### 2-2 投遞口那一列不再對著已經在成形的那一位說「接下來就是他」

`startWaiting()` 進場那一刻呼叫 `arrivals.spawned(sub.id)` —— 那支方法的語意
就是「他從排隊中變成台上」，而他現在就在光柱底下。**一行，而且是呼叫抵達層
既有的公開方法，沒有改抵達層一個字。**

AFTER 的投遞口只列還在排的那兩位，`arrivalsWaiting` 從 3 筆變成 2 筆
（`70_console_AFTER.log` 對照 `71_console_NEGCTL_off.log`）。

### 2-3 🔴 被否決的那一版：**排隊也染冷色，但一句話都沒有**

第一版讓 `waitDegraded(sub) === true` 的排隊者染成冷灰藍。實拍
`40_REJECTED_排隊也染冷色而沒有字_全幀.jpg`／`40b_REJECTED_特寫.png`：
三團土、一團是冷的、**旁邊一句話都沒有**。

那正是第二輪 §3-1 抓到而且修過的同一個錯——「顏色變了而字沒出來，
等於要觀眾自己看懂顏色的意思」。而且修法**不能是「在這裡也印一句」**：
`twinEngineNote` 逐字是「他說的話是查表湊的」，他**還沒上台、還沒有話**，
那句話在這裡為假；另寫一句短的又違反「措辭只有一份」。

⇒ **排隊這一段不講 `engine`，一個字都不講。** 它的主張只有三件：
他的代號、他在排隊、他排了多久。退化留給他進到光裡那一刻，
由中央那一版**用字**講（顏色只是伴隨）。出貨的樣子：
`41_SHIPPED_排隊不講engine_全幀.jpg`／`41b_SHIPPED_特寫.png`
（同一個輸入，兩團都是暖的）。可執行判準 **W13k**＋負控制 **W13p**。

### 2-4 角落那一版跟投遞口板疊死（第二輪就在的 bug）

`drawFormingCorner` 的 x 跟 `dockGeom()` 幾乎相同、y 差不到一張板 ⇒
只要有人在排隊（投遞口就是那時候才亮），**兩張板疊在一起，兩張都讀不到**。
實拍 `30_BEFORE_角落卡疊在投遞口板上.jpg`。

修法：投遞口亮著的時候角落卡**往上疊一層**（讀 `arrivals.dock` 與
`dockGeom()`，不動抵達層）；投遞口收起來就回原位。同時把**版面單位 `u`
跟卡片高度 `bh` 拆開**——舊版兩者同一個數，卡片一長高裡面的土團與字級
就等比放大，變成另一張卡。修完：`31_AFTER_角落卡往上讓.jpg`、
`32_AFTER_角落卡特寫_另有2位在排隊.png`、影片 `22_vid_中央到角落_70s.mp4`。

## 四、「它真的在動」是量出來的

`50_motion_queue_ON.json`（產生器 `82_r3_motion.py`）。判準＝相鄰兩格在同一塊
區域的平均絕對灰階差。**五條線缺一條這個數字就沒有意義**：

| 區域 | 開（n=119，38.9 秒窗口） | 關（負控制，n=119） |
|---|---|---|
| `q_left` 排隊第 1 位那一團 | min **3.97** · 中位 **5.49** | min 1.61 · 中位 **2.35** |
| `q_right` 排隊第 2 位那一團 | min **4.36** · 中位 **6.30** | min 1.86 · 中位 3.29 |
| `clay_center` 中央那一位（**正對照組**） | 中位 4.46 | 中位 4.46 |
| `floor_front` 同景深帶的空地板（**空間對照組**） | 中位 2.49 | 中位 2.46 |
| `ambient` 左上暗牆 | 中位 0.33 | 中位 0.35 |
| `frozen` 同一格重複（**這把尺自己的負控制**） | **0.000000** | **0.000000** |
| 判決 | `QUEUE_MOVING` | `INCONCLUSIVE` |

判讀：開的時候兩個框都**沒有任何一格**掉到空地板的水準，中位數是空地板的
2.2／2.5 倍；關掉之後兩個框就退回空地板附近（`q_right` 中位 3.29 略高是

而量法本身對真正靜止的輸入回傳精確的 0。

⚠ `q_left` 的量測框從土團頂端**下面一點**開始（y=866 而不是 838），
因為框的上緣會掃到一位站著的居民的腳。座標寫死在 `82_r3_motion.py` 裡。

## 六、🔴 本輪三個「量具說謊」的標本

### 6-1 `--disable-gpu` 讓幀率差 5.4 倍，而它會改變「畫面有沒有卡住」的答案

第一次錄「三個人同時投卡」時畫面 58 秒什麼都沒發生，讀 code 看起來像
`waitBacklog` 死鎖。**先量**（`87_r3_fps.mjs`）：

| Chrome 旗標 | rAF 幀率 | `setInterval(500ms)` 實際跳了幾次 / 應該幾次 |
|---|---|---|
| `--headless=new --disable-gpu` | **1.01 fps** | 10 / 41.6 |
| `--headless=new`（不帶） | **5.50 fps** | 31 / 40.0 |

不是死鎖：`arrivals.holdT` 走的是 `dt`，而 `dt` 有 `Math.min(…, 0.1)` 的上限
⇒ 1 fps 之下 2.8 秒的抵達優先權要 28 幀＝**28 秒真實時間**才扣得完。
全文與判讀：`94_錄影環境的幀率_不是展件的幀率.txt`。
**這一條要在展場機（1003，Windows）上重量一次，本輪沒有量。**

### 6-2 `r3_replay.py` 第一版會**安靜地少套一段**

把改動從 A→B 搬到第三個檔的那支工具，第一版把每個 difflib opcode 各自當一段。
兩段改動只隔 4 行時 context 會重疊，第一段替換完第二段的 `old` 就不在字串裡了，
而 `str.replace(old, new, 1)` 對找不到的字串是**安靜地什麼都不做**——
角落卡那兩行改動整段掉了，而腳本回報「12 段全部寫入」。

**是下游的 `waitcheck.mjs` W13z 把它抓出來的**（合併結果跑出 1 條 BROKEN）。
兩個修法都上：相鄰太近的段先合併；每次 replace 之後檢查字串真的變了。
再加一條自我檢驗（`84b_r3_replay_selftest.sh`）：把同一批改動套回 A，
結果必須**逐 byte 等於 B**——第一版在這裡就會紅。

### 6-3 排隊兩位的秒數有時候會一模一樣，那**不是 bug**

`96_探針_排隊那兩位的牆鐘章.log`：兩位的 `__wqAt` 分別是 6964 與 13606 ms，
確實不同。但另外幾次錄影兩位顯示同一個秒數——因為 `bridge.js` 的輪詢在
主執行緒吃緊時會把兩筆**在同一次輪詢裡**送進來。
⇒ 誠實邊界：那個數字是「**這面螢幕看到他的那一刻**起算」，
不是他在手機上按下送出那一刻（兩支時鐘沒有對過）。碼裡有註解。

## 七、怎麼把它裝上去

🔴 `~/Documents/GitHub/vacant_hm` 是**另一個 repo、正在運作的展件**，而且同一天有
十幾個代理在改。本輪**沒有動那棵樹一個 byte**（`git status` 那邊的 `world3/index.html`
從頭到尾是別人的改動），交付物是 patch。

本輪親眼看到 `world3/index.html` 在**兩小時內被改了六次**：
4262 → 4491 → 4492 → 4498 → 4526 行（sha 709d717d → 96a1168c → ebabae34 →
8e2ec474 → e6ff639d）。所以**不要 `patch -p1`**，用附的三方合併腳本：

```bash
bash <此目錄>/92_rebase.sh ~/Documents/GitHub/vacant_hm
```

* `base` ＝ `91_base_world3_index.html`（跟第二輪同一份，sha256
  `709d717d4da5c19e5ad0b6cb6d8e221e160def9cad2213ec7dec319daf85f807`）
  `theirs` ＝ base ＋ `90_vacant_hm_wait_shape_r3.patch`（第二輪＋第三輪，
  5460 行；`tools/waitcheck.mjs` 455 行為新檔）
  `ours` ＝ 你當下那一份。
* **有衝突先交給 `92b_resolve_update_conflict.py`**，那一支**只吃一種**衝突：
  兩邊都在 `director.update(dt)` 的同一個插入點各自插入、**基底是空的**。
  順序是語意不是排版：`this.waitTick()` 要排在會 `return` 的
  `if (this.mode === "wait")` **前面**，否則相位機在待機時停擺，
  那一團土會永遠留在角落、退役儀式永遠不會演。基底不是空的就整支停下來。
* 實跑紀錄：`93_rebase_run.txt`——對**當下**那棵樹（`e6ff639d…`，4526 行）
  合併後 5724 行，waitcheck **106 條**、livecheck **194 條**全過。
* **還原**：`git -C ~/Documents/GitHub/vacant_hm checkout -- world3/index.html`
  ＋ `rm tools/waitcheck.mjs`（一行還原，`92_rebase.sh` 跑完自己會印出來）。

## 九、誠實邊界（改碼時保留）

1. **排隊那幾團不吃 `formingLevel`。** 它們不准自己長高——燈還沒照到他，
   畫面不可以先演完。W13j 是可執行防呆。
2. **排隊那一段不講 `engine`。** 顏色變了而字沒出來＝第二輪 §3-1 的錯；
   而 `twinEngineNote` 那句話（「他說的話是查表湊的」）對還沒上台的人為假。
   W13k 是可執行防呆。
3. **秒數是「這面螢幕看到他」起算**，不是他按下送出起算（§6-3）。
4. **「接下來就是他」這句跟投遞口那一列逐字相同**，是刻意的：同一個畫面上
   兩處講同一件事，措辭不一致觀眾會以為是兩件事。
5. **角落卡的讓位不是美術決定**，是「讀不到等於沒講」（§2-4）。
6. **公共大螢幕不印觀眾原話。** 排隊那兩行只有代號（W13f）。

## 十、沒做、不知道、還沒對帳的

* 🔴 **排隊的人要等到前面那一位落地（或退役）才輪得到他。** 第 1 位 42 秒之後
  縮到角落，但 `director.wait` 仍然被他佔著 ⇒ `waitBacklog` 不會前進。
  本輪**沒有改這一條**（`director.wait` 是單數，改成多人是另一次重構）。
  畫面上現在至少講得出來：角落卡寫「另有 N 位在排隊」。
  ⚠ 實測中位 34 秒、最大 54 秒（n=7）**都小於 42 秒**，所以常見情況下
  第 1 位會在讓出整格之前就落地；但那是 2026-09-20 那批數字，不是展場現場。
* **排隊那幾團只畫四個位子。** 第 5 位以後只在角落卡的「另有 N 位」裡出現，
  場上沒有他的土。位子是寫死的座標（避開 SIMPLE 版 QR 與投遞口板），
  **沒有做自適應排版**。
* **展場機器上沒跑過。** 全部證據都是這台 Mac 的 headless Chrome。§6-1 那條
  幀率因果在 1003（Windows）上要重量一次。
* **沒有跟真的 `twinlink loop` 對接過**（跟第二輪同一條）。`80_r3_drive.py`
  扮演的是寫快照那一方。
* **`SIMPLE` 沒有審視過排隊這一段。** 位子有避開 SIMPLE 版 QR 的座標，
  但「三團土＋六行小字會不會太複雜」沒有被人類看過。
* **排隊中的人的 `engine` 不會更新。** `bridge.js` 的 `seenIds` 只送一次，
  而第二輪的重讀器只重讀**中央那一位**。所以排隊期間他的狀態是凍結的；
  他被取出進到光裡之後重讀器才會接手（最壞是退回舊行為，不是演錯）。
