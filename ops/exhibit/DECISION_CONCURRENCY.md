# 環境決定：genimg.sh 不是併發安全的——這解釋了 floor_lower 為什麼生歪

**2026-08-18 執行端拍板**（規則七授權，不需要 sudo，不必等人類）。

## 撞到的事

這一輪一開場（06:40 左右）就發現這台 VM 上同時跑著**至少兩份**別輪的
`claude -p`（`timeout 45m` 包著，PID 629972 起於 06:34、634919 起於
06:37），各自獨立呼叫 `genimg.sh` 在生排圖（`floor_lower`、`floor_mid_a`、
`floor_review`、`floor_mid1`……同一批任務被重複派工）。

追下去發現 `genimg.sh` 本身的「哪張圖是我剛生的」判斷方式：對
`~/.codex/generated_images/` 這個**全域共用**的池子拍 BEFORE／AFTER 快照，
取差集裡最新的一個檔案，當作自己的產物搬走。**這個判斷方式沒有把「這次
codex 呼叫」跟「別的並發呼叫」分開**——兩個 `genimg.sh` 同時在跑，各自的
AFTER 快照都會看到對方剛生出來的圖，`sort -rn | head -1` 撿到的可能是
別人的產物。

**這解釋了 `floor_lower.png` 上一輪生歪的真正原因**：EXHIBIT_STATE.md
原本記成「codex 生錯場景」，但更可能是「genimg.sh 撿到了另一個並發呼叫
（很可能是同時在跑的角色貼圖生成）剛吐出來的單一角色圖，誤搬成
floor_lower.png」。DECISION_PIPELINE.md 記的「floor_lower 生歪，要重試」
這個判斷本身沒錯（產物確實不對），但**歸因**（以為是 codex 生錯）現在看
站不住——沒有直接證據能回頭確認，但時序與症狀（一個完整場景任務生出一個
孤立角色特寫）都吻合「撿錯圖」而不是「codex 誤解提示詞」。

## 決定

`genimg.sh` 加**全域 flock**（鎖檔 `~/.codex/genimg.lock`），把從「拍
BEFORE 快照」到「搬檔到目的地」整段包進鎖裡，逼所有並發呼叫排隊，
不再靠猜時間戳分辨產物歸屬。序列化的代價本來就存在——PLAN.md 早就把
codex 容量記成「共用、有限」，這只是把那個事實在程式碼裡兌現。

**這個鎖只保護新的呼叫**：已經在跑的舊版 `genimg.sh`（bash 在啟動時讀進
整份腳本，不會中途重新讀檔）不會補上鎖，這一輪撞到的那兩份並發呼叫
會照舊跑到底。之後任何新啟動的呼叫都會排隊，不會再撿到別人的圖。

## 沒解的部分——需要人類看

這是**症狀**的止血，不是**病因**的修復。病因是外部的排程器同時起了
兩份以上的 45 分鐘 round，而它們用的是同一台 VM、同一個 codex 帳號、
同一個 `~/.codex/generated_images` 池子。Vacant repo 裡已經有一次類似
教訓（commit `669bc7b`，`ops/loop.sh` 加了 `flock` 防止兩份迴圈的
`git pull` 互撞），但**這台 VM 上找不到 `loop.sh` 這個檔案**
（`find / -iname loop.sh` 全機掃描是空的），也沒有 `.loop.lock`——
可推論實際派工這些 round 的排程器**不在這台 VM 上**（大概是稽核端
或另一台控制機直接 ssh 派工），`669bc7b` 那個鎖保護不到這裡。

**這件事需要人類去改派工端**（不是這台 VM 的規則七授權範圍）：
在派工前檢查「這台 VM 上有沒有還在跑的 round」，或者把
`genimg.sh` 的鎖邏輯往上提一層，變成「同一時間只派一個 round 到這台
VM」。目前的 flock 修法只能防止產物互撞，防不了 codex 容量被多份
round 同時瓜分（14 個 `codex exec` process 同時掛著，符合 PLAN.md
記的「複雜場景會服務端逾時」多半也是這樣被撞出來的）。

## 什麼情況下這個決定該被推翻

- 派工端修好之後，同一時間只有一份 round 在跑——這個 flock 不會造成
  任何行為改變（沒有並發就不會排隊），可以留著當保險。
- 如果之後想要「多份 round 平行生圖」變成刻意的設計（不是意外撞出來
  的），需要把 `~/.codex/generated_images` 換成每個呼叫獨立的池子
  （例如傳一個 session 專屬子目錄給 codex），而不是共用同一個目錄，
  否則 flock 只是把平行變成排隊，沒有真正平行。

## 追加觀察（同一輪，06:46）——病因比原本記的更嚴重

flock 修法上線後幾分鐘，`ps` 再撈一次發現**同一台 VM 上有三份**
`timeout 45m claude -p` 在跑（PID 629972 起於 06:34、634919 起於 06:37、
645758 起於 06:46，且 645758 的 ppid 是 634618——跟另外兩個不同源，
代表至少有兩個獨立的派工者在對這台 VM 派工，不是同一個排程器連續派兩次
那麼單純）。本輪撞到時，629972（本輪自己）跟一個更早、已經孤兒化的
`/tmp/g_floor2.sh`（父行程已死，PID 628750 起於 06:33）同時在對
`floor_lower.png` 呼叫 `genimg.sh`——本輪選擇**主動 kill 掉自己剛起的
並發呼叫**，等孤兒行程單獨跑完，而不是兩邊搶，這是 flock 上線前的
過渡期土法（flock 保護不到已經在跑的舊行程，DECISION 本文已經寫了）。

**這比原記錄嚴重的地方**：三份以上同時活著意味著 codex 容量、
`~/.codex/generated_images` 池子、以及 `vacant_hm` 這個 git repo 的
push 序，同時被三份 round 競爭。flock 只解決「撿錯圖」，解決不了
「三份 round 各自 commit 然後互相 rebase／conflict」──這件事本輪
用「commit 前一律先 `git pull`」土法應對，但**真正的修法還是同一句：
需要人類去改派工端，確認同一時間只派一份 round 到這台 VM**。

## 追加決定，2026-08-18 這一輪——排隊改成背景非阻塞，不是不排

連續五輪的判斷都是「佇列裡已經有兩張排圖在排（`floor_review.png`／
`floor_archive.png`），不重複排隊」，理由是**前景阻塞等待**：如果自己
的 `genimg.sh` 呼叫排第三，45 分鐘的 round 時間預算會整段耗在
`flock` 等待上，什麼別的事都做不了，而且大機率連輪都輪不到。這個判斷
本身沒錯，但它有一個沒被注意到的前提：**只考慮了前景阻塞這一種呼叫
方式**。

這一輪改用 `nohup ... &`（Bash 工具的 `run_in_background`）把新的
`genimg.sh` 呼叫丟到背景，立刻拿回終端控制權，不阻塞這一輪剩下的時間。
排的是 `sp_carry2.png`——courier 走路循環的第二格（另一腳跨出的中段
姿態），這是唯一一件「除了排圖，還有價值且不需要等 floor_review／
floor_archive 先落地」的生圖任務（蓋章／放大鏡兩個姿態經
`DECISION_PIPELINE.md` 核對後**不需要**額外生——評審員是畫進背景排圖
裡的靜態角色，不是疊上去的貼圖，只有 courier 本人會動）。

**代價與下限評估**：這個呼叫排第三，`floor_review.png` 這一輪開場時
已經是第三次 codex exec 嘗試（`ATTEMPTS=4` 上限），`floor_archive.png`
還沒輪到鎖。就算兩者都在合理時間內清掉鎖，`sp_carry2.png` 大機率也
不會在**這一輪**的 45 分鐘視窗內真正跑到 codex exec 那一步。下限
（如果 45 分鐘內完全沒輪到）跟「不排」完全一樣——沒有消耗這一輪的
前景時間，只是在 `~/.codex/genimg.lock` 後面掛一個等待中的 bash
行程，本輪 `timeout 45m` 到期時這個行程會被一併結束（未驗證，但即使
真的被殺掉，效果也只是「跟沒排一樣」，不會弄壞佇列或撿錯圖——
`genimg.sh` 直到 `mv` 那一步才落地產物，中途被殺不會留下半成品）。
上限（如果活過 45 分鐘、且真的排到鎖）是幫下一輪省一次重新判斷「要不
要排」的來回，佇列往前推進一步。

**判斷，不是量測**：背景非阻塞排隊的期望值是正的（下限持平、上限有
益），所以這一輪改用這個方式，不再堅持「兩個排隊中就完全不排」。

## 什麼情況下這條追加決定該被推翻

- **如果之後發現 `timeout 45m` 到期並不會殺掉背景子行程**（例如它們被
  detach 到不同的 process group 而不受影響）⇒ 背景排隊的上限比這裡估的
  更高，可以更積極地用這個方式補排圖佇列，不必每次都猶豫「排不排」。
- **如果背景排隊的行程被發現真的干擾了其他並發 round 的 flock 佇列
  順序**（例如造成非預期的插隊或鎖持有時間異常拉長）⇒ 這個決定要收回，
  退回「兩個排隊中就不排」的土法。
- 派工端本身修好、同一時間只有一份 round ⇒ 這整份文件的討論都不再
  適用，可以恢復成單純的「有空就排、不必猶豫」。
