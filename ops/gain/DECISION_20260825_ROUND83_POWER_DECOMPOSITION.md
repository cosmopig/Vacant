# DECISION round83 — 配對 power 的分解：P4 用錯了統計量

日期 2026-08-25 04:16–04:5x UTC　模型 Opus 5　作者 round83
工具 `ops/gain/analyze_power_decomposition.py`（本輪新增，附 self-test）

> **一句話**：round78 §6 的 P4 規則拿「OFF 邊際失敗率」當作「量測窗口」的
> 代理量，但三臂比較用的是**配對**檢定，配對 power 的分母是 `p_disc`
> 不是邊際失敗率。分解之後：**ON vs OFF5 在這個題庫上換再難的題也答不出來**，
> 而**OFF vs ON 早就答得出來**（n=371 下 power 0.999）。所以 Route B
> 不是下一步，**同一支 run 內把 OFF 與 ON 一起量**才是。

---

## 1. 背景：本輪要檢查的前提

round78 §6 P4（量測前訂死，本輪**不**修改它的字面規則）：

```
全庫 OFF 失敗率 >= 35%   ⇒ route A（擴 n）
25% <= 失敗率 < 35%      ⇒ 重算 required-n
失敗率 < 25%             ⇒ B（換題庫／弱化 worker）成為必要
```

隱含前提：**失敗率低 ⇒ 天花板 ⇒ 沒有量測窗口 ⇒ 要把題目變難。**
本輪檢查的就是這個前提。

## 2. 分解（這是恆等式，不是模型）

McNemar 的資訊**只來自 discordant pairs**。因此

```
required_N = n_disc_needed(ψ) / p_disc

  p_disc = P(兩臂結果不同)              ← 「題目難度」大致影響這一項
  ψ      = b/(b+c)，discordant 裡誰贏   ← 「機制真的比較好」影響這一項
```

`n_disc_needed(ψ)` 在 ψ→0.5 時發散。**ψ≈0.5 代表兩臂實際上是同一種過程**，
這時把題目變難只動分母，救不回 power。P4 的映射假設難度是唯一旋鈕——
那對 marginal accuracy 成立，**對配對 power 不成立**。

## 3. 量具驗證（先證明它在已知答案上會叫）

`analyze_power_decomposition.py --self-test`：5 組、0 failure。其中三組是
拿 **round77 已發表的 p 值**當已知答案對照（`exact_mcnemar_p`）：

```

b=4,c=6 -> 0.753906   （round77 原文 p=0.7539）  ✓
b=5,c=2 -> 0.453125   （round77 原文 p=0.4531）  ✓
```

正確性定義與 `analyze_fullbank_off.py` 逐字相同（`accepted and meets_demand`），
並植入缺陷測試：`accepted=False, meets_demand=True` 必須算不正確。

⚠ 過程中**我自己寫錯過一個測試**，照實記：第一版植入缺陷測試斷言「非條件
power 必須低於條件 power」，實測 0.7656 > 0.7639 而 FAIL。查下去是**測試錯不是
程式錯**——exact test 的 power 對 `n_disc` 是**鋸齒狀**不是凹的。改成兩個不受
鋸齒影響的性質（`p_disc=1` 時兩者恆等；`p_disc=0.5` 時必須明顯更低）才過。
教訓：*power 曲線的單調性直覺在離散精確檢定上不成立，別拿它當判準。*

## 4. 實測（三對，capacity=371）

| 對 | b / c | p_disc | ψ | diff | exact p | required_N | 371 下的 power |
|---|---|---|---|---|---|---|---|
| ON vs OFF5 | 4 / 6 | 0.1786 | 0.40 | −3.57pp | 0.7539 | **1144** | — |
| OFF vs ON | 6 / 1 | 0.1186 | 0.857 | +8.47pp | 0.125 | **134** | **0.9988** |
| OFF vs OFF5 | 5 / 2 | 0.1228 | 0.714 | +5.26pp | 0.4531 | **368** | 0.8047 |

（`required_N` 是**非條件** power：`n_disc ~ Binomial(N, p_disc)` 一起積掉，
不是「假設剛好拿到 k 個 discordant」的條件 power。round77 用常態近似得
n≈1096，本輪精確算得 1144——**兩者一致，不是推翻 round77 的算術**，
本輪推翻的是 P4 對那個數字的**解讀**。）

## 5. 結論一：ON vs OFF5 換再難的題也答不出來

要在 371 題內答出 ON vs OFF5（維持觀測到的 ψ=0.60），需要

```
p_disc >= 0.55      （實測掃出來：p_disc=0.55 -> required_N=371）
```

而目前 `p_disc = 0.1786`。**0.55 這個門檻高到不可能**：

- 兩臂在共同子集上的 accuracy 是 0.696 / 0.732。若兩臂**完全獨立**，
  `p_disc = 0.409`。**0.55 比獨立情形還高** ⇒ 需要兩臂**負相關**
  （彼此答對互補的題）才可能達到。
- 實測相關性是**正**的：0.1786 / 0.409 = **0.437**。兩臂共用同一顆底層模型、
  看同一批題，正相關是預期中的。

**⚠ 前提逐條列出（不要下一輪當事實引用）：**

1. 前提 A：兩臂 accuracy 相近。實測 0.696 vs 0.732 ✓（n=56）。
2. 前提 B：兩臂正相關。實測比值 0.437 ✓（n=56，**單一觀測，未做區間**）。
3. 前提 C：ψ 維持在觀測值 0.60。**這是最弱的一環**——ψ 是從 **10 個**
   discordant pair 估的。
4. 前提 D：題庫容量 371 固定（MBPP+ 378 減 7 題資源排除）。

**推翻條件（觸發任一條，本節結論作廢）**：
(a) 某個 Route B 變體實測做出 `p_disc > 2·a·(1−a)`（＝負相關）；
(b) ψ 在更大樣本下離 0.5 顯著更遠（例如 ≥0.68 ⇒ 371 題就夠）；
(c) 換到容量 >408 的題庫（那時 p_disc=0.5 的極限值就落在容量內）。

**(b) 才是真正該注意的**：ψ 只有 10 個 pair 撐著，它完全可能是錯的。
本節說的**不是**「ON 和 OFF5 一樣好」，而是「**若真實效應就是觀測到的這麼小，
這個題庫再怎麼調難度都解析不出來**」。

## 6. 結論二：等預算的答案是一個「上界」，不是「沒答案」

「有成效」判準 3 要的是 ON 對 OFF5 誰贏。本輪的答案寫法是：

> 在 371 題容量下，80% power 能分辨的最小差距是 **6.43pp**
> （`resolvable_floor_at_capacity`）。觀測到的差距是 **−3.57pp**，
> 落在解析度以下。
> ⇒ **|ON − OFF5| < 6.4pp，且點估計的方向對 ON 不利。**

這是一個**上界**，不是「量不到」。它回答了 loop prompt 的
「打不贏也是結論，照實寫」——**Vacant 的完整機制在等呼叫數下，
相對 self-consistency 的增益小於 6.4pp，方向還是負的。**

## 7. 結論三：真正該跑的下一個 run 不是 Route B

`OFF vs ON` 在 371 題下 power = **0.9988**，required_N = 134。
這一對問的正是整個專案的標題問題——**「加了 Vacant，產出有沒有更接近需求」**
——而它**答得出來**，而且**不需要改任何實驗條件**（零「挑對自己有利的設定」風險）。

⚠ **但 134 這個數字不可以直接拿去當 n**。它是用**點估計** ψ=0.857 回推的，
而 ψ 是 **6/7** 一個 pair 撐起來的：Clopper–Pearson 95% 下界 = **0.4213**，
**低於 0.5** ⇒ 目前的資料連「ON 比較差」都還沒確立（p=0.125）。
用觀測效應回推 n 是**系統性樂觀**的。保守規劃表：

| 假設真實 ψ | required_N |
|---|---|
| 0.857（點估計） | 134 |
| 0.80 | 195 |
| 0.75 | 284 |
| 0.70 | **436（超過容量）** |

**判斷（這是判斷，不是量測）**：規劃 n 應取**全庫 371**，不取 134。
理由：371 已經是容量上限，成本只比 284 多 30%，而它涵蓋到 ψ=0.75 的情形；
取 134 有約一半機率白跑。

⚠ **配對必須在同一支 run 內**。現有的 OFF vs ON 是**跨 run** 配對
（OFF 來自 `g_off60_qwenonly_20260824`，ON 來自 `g_onoff5_..._v3`）。
配對本身按 task_id 有效，但**後端條件會漂移**（round82 的 gemma 探測事故就是
一個現成的例子）。⇒ 下一支正式 run 要 `--arms OFF,ON` **同一支**。

## 8. 新觀察（**假說，不是結論**）：infra_void 可能在審查掉難題

本輪監看時撞見 `mbppplus_Mbpp/235` 連續 3 次（retries_max=4）

```
EmptyResponse: content 為空（finish_reason=length，reasoning 24271/26986/26663 字）
```

每次約 **165 秒**。模型在 reasoning 裡跑掉、從未吐出答案。**本輪收尾前已確認
它第 4 次仍失敗、正式成為 `infra_void`**：

```
mbppplus_Mbpp/235  plain-2 重試 4 次仍失敗：
  EmptyResponse: content 為空（finish_reason=length，reasoning 25307 字）
```

共燒掉約 11 分鐘（4 × ~165s）後，這一題從分母裡消失。

**為什麼這件事重要**：SPEC_GAIN 把 `infra_void` 定義成「這一格沒量到」，
不進分子也不進分母。但 `finish_reason=length` **不是網路故障**——它是模型
自己的行為，而且**在重試下重現**（3 次都一樣）。如果這種 void 系統性地
發生在**難題**上，那麼 void 機制正在**把難的尾巴從分母裡切掉**，
使量到的失敗率**偏低**——那正好會製造出 P4 讀到的「失敗率太低＝題目太簡單」。

**⚠ 這是假說，不是發現。** 目前證據只有 **1 題**。全庫 void 統計：

```
g_off371（進行中，49/371）
   voids=3：HTTPError×2（round82 探測事故）＋ EmptyResponse/length×1（Mbpp/235）
   ⇒ **這一型 void 目前 1/371 題，佔已嘗試 49 題的 2.0%**
g_onoff5_v3            calls 層 EmptyResponse/length = 7（重試後成功，未成 void）
```

**預先寫死的檢查（等 g_off371 跑完做，不准跑完再挑）**：
把 void 題與已量到題的**難度代理量**（prompt 長度、hidden test 數、
canonical solution 行數）做比較。若 void 題顯著更難 ⇒ 分母被審查，
`failure_rate` 是低估，**P4 的輸入本身不可信**。
若沒差 ⇒ 這個假說作廢，照實寫作廢。

**本輪不改任何 void 處理邏輯。** 改它會改變實驗條件，而假說還沒驗證。

## 9. Route B 的預先登錄（**在難度圖存在之前寫**）

如果將來仍要走 Route B，以下規則**現在**訂死——因為 `g_off371` 的逐題難度圖
還沒出來，此刻寫的規則不可能是挑數字挑出來的：

- **B-S1（選樣）**：任何用於後續 ON/OFF5 比較的子集，其定義必須是
  **不跑任何 arm 就能算出來的**（outcome-independent）。若真要用 OFF 的結果
  選題，則必須同時滿足：(a) OFF 在該子集上**重新量一次**，選樣用的那次量測
  **絕不**當成 arm 使用；(b) 結果只能報成**子集條件下**的，不得外推回全庫；
  (c) 門檻在看到 ON/OFF5 數字**之前**固定。
  理由：照 OFF 失敗選題再沿用同一批 OFF 數字，回歸均值會**憑空造出** ON 的增益。
- **B-S2（代理量凍結）**：難度代理量的定義若在看到難度圖**之後**才發明，
  一律標記為 post-hoc，不得單獨用來定義實驗子集，必須另跑一支確認性 run。
- **B-S3（Route B 的成功判準，現在訂死）**：Route B 只有在把
  `required_N` 壓到 ≤ 容量時才算成功。**把 OFF 失敗率推進 20–60% 是必要條件、
  不是充分條件**——照第 5 節，失敗率進窗口而 ψ 不動的話，
  ON vs OFF5 仍然答不出來。**「有成效」判準 1 達標 ≠ 判準 3 達標。**
- **B-M1（換模型的共同盲區陷阱）**：round82 考慮過把 worker 換成
  `gemma-4-12b-it-qat`。這有兩種實作，**答的是不同的問題**：
  - **B1a**：worker 與 reviewer **一起**換成弱模型。只動難度，
    維持 SPEC §3 「同家族共同盲區」的既有條件。
  - **B1b**：只換 worker，reviewer 留 qwen。這**引入能力不對稱**，
    ON 的任何增益都有一部分是「大模型檢查小模型」，

  ⇒ 若走 Route B 的換模型子選項，**預設 B1a**；要走 B1b 必須另立 DECISION
  並把結論改寫成「異質 worker/reviewer 配置下的增益」，不得當成本專案的主張。
