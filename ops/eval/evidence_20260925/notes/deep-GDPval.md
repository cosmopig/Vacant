## 4. Published baselines

- **Official (OpenAI paper, arXiv:2510.04374, §3.1, ar5iv text extraction 2026-09-25)**: models evaluated were **GPT-4o, o4-mini, o3, GPT-5, Claude Opus 4.1, Gemini 2.5 Pro, Grok 4** — all frontier, closed models. **No open-weight model, and no model ≤35B, was evaluated by OpenAI in the paper.** Each model sampled 3× per prompt, graded by 3 different human experts per sample (9 comparisons/prompt/model). Primary metric = win rate vs. human-expert deliverable (blind pairwise). Human baseline: mean completion time `H_T = 404 min`, mean completion cost `H_C = $361`; mean review time `R_T = 109 min`, review cost `R_C = $86` (paper §3.2, exact figures).
- **Automated grader agreement**: 66% agreement with human expert graders vs. 71% human inter-rater agreement (paper §Overview / Fig. 4; also stated in inspect_evals `README.md`).
- **inspect_evals' own replication** (`src/inspect_evals/gdpval/README.md:77-89`): GPT-5, thinking=low, via this exact harness → **47.3% ± 6.2%** average score, 219/220 graded (1 task errored: "Responses API did not complete within 3600.0 seconds" — i.e. ~1 hour agent wall-time cap exists on OpenAI's Responses API side, not in the harness). **The paper authors note their own official leaderboard score for the same released model is 31.9% (wins-only) / 34.6% (wins+ties) — a large gap (47.3% vs ~32-35%) between the community harness's number and OpenAI's own number for what's nominally "the same" GPT-5 run.** This is the harness's own admission that "no difference at all" reproduction is **not currently achieved even for the flagship model**, let alone small models — a critical caveat for anyone citing this harness's numbers as equivalent to the official leaderboard.
- **Small open-weight models (≤35B)**: no official OpenAI numbers exist. The only published numbers found are from **Artificial Analysis' "GDPval-AA v2.1"** (`artificialanalysis.ai/evaluations/gdpval-aa`, read 2026-09-25) — an **independently-run, methodologically-different** benchmark that reuses the GDPval *task set* but scores via Artificial-Analysis's own blind pairwise LLM-judge → **Elo rating** (not OpenAI's win-rate-vs-human-expert metric, not OpenAI's GPT-5 judge, not submitted to evals.openai.com). Elo scores for models ≤35B (as displayed 2026-09-25):
  - Qwen3.8 27B (xhigh): 1409 · (medium): 1368 · (low): 1342
  - Gemma 4 31B (Reasoning): 606 · Gemma 4 26B-A4B (Reasoning): 553 · Gemma 4 12B (Reasoning): 413
  - Qwen3.5 9B (Reasoning): 407
  - IBM Granite 4.2 30B: 564
  **These are NOT comparable to OpenAI's official win-rate numbers** (different grader, different scoring scale, different methodology) — cite as "GDPval-AA (Artificial Analysis' own variant)", never as "GDPval score".
- **Reproduction-check candidate**: none exists that uses the exact official protocol (evals.openai.com grading) for a small open model. The closest thing to a controlled comparison is inspect_evals' own GPT-5 run above, itself already diverging from the official number.

## 5. Which agents can run under the official protocol

- The gdpval Task's solver is **Inspect's own native tool-loop** (`use_tools([bash,python]) → generate() → extract_deliverable_files()`), i.e. the model is called directly via Inspect's `ModelAPI` (HTTP to whatever provider), and Inspect's own Python code executes `bash`/`python` tool calls inside the sandbox. **There is no subprocess invocation of pi, OpenCode, Claude Code, or Codex anywhere in gdpval.py/util.py**, and grepping the whole `inspect_evals` repo for "claude code", "opencode", "codex", "mini-swe", "terminus" found no CLI-agent integration pattern anywhere in the repo (the one hit, `ipi_coding_agent`, *mentions* Claude Code/Copilot/Cursor only in prose as the class of agents its prompt-injection benchmark is *modeling*; its own solver is likewise Inspect's native `generate()` loop, not a real CLI agent).
- However, **inspect_ai core (v0.3.268) does ship a generic bridge mechanism** — `inspect_ai.agent.AgentBridge` / `sandbox_agent_bridge` / `human_cli` (`python -c "import inspect_ai.agent as a; dir(a)"`, confirmed present) — designed to let an *actual* external agent process (running inside the sandbox, speaking an OpenAI-compatible API back to Inspect) drive the task instead of Inspect's own loop. **gdpval does not use this bridge today**; retrofitting pi/OpenCode/Claude Code/Codex onto gdpval would mean writing a custom solver that (a) installs the chosen CLI agent inside the (already 5-8 GB) sandbox image, (b) launches it headless pointed at the bridge endpoint, and (c) collects `deliverable_files/` the same way — a nontrivial but plausible integration, not a "just point it at the CLI" swap.
- **Vacant's own hook model needs a real CLI agent process to hook.** Since the official protocol as shipped calls the model directly (no pi/OpenCode/Claude Code/Codex process exists to attach hooks to), **Vacant cannot attach to "official" GDPval runs as-is**. The only path is the retrofit above (§6) — run one of the four target agents *as* the acting agent inside the sandbox via a custom solver, which is where Vacant's hooks (via `vacant do`/`vacant hook`) would then apply normally, exactly as they do for any other headless CLI-agent run.

## 6. Adding arm B (reviewer-persona self-check, no Vacant evidence) and arm C (Vacant installed)

Both arms require the CLI-agent retrofit above (§5) — they cannot be bolted onto Inspect's native `generate()` loop by design, since Vacant hooks a CLI *process's* tool calls, and a reviewer-persona self-check step is naturally "one more agent turn/subagent", which is easiest to express as another instruction to the same CLI agent, not another `generate()` call in Inspect's own solver chain (though a lightweight arm-B *could* be approximated purely in Inspect by appending one more `generate()` step with a "review your own deliverable_files as a skeptical QA persona" prompt before `extract_deliverable_files()` — cheap, no new infra, but only approximates "self-check", not Vacant's evidence-grounded check).
- **Arm A (control, official protocol)**: unmodified `[use_tools, generate(), extract_deliverable_files()]`.
- **Arm B (reviewer-persona self-check, no Vacant)**: insert one extra solver step between `generate()` and `extract_deliverable_files()` that re-prompts the *same* model with a persona ("You are a skeptical QA reviewer...") and the deliverable files it just wrote, asking it to revise. No file provenance, no trace of what was actually read vs. assumed — this is exactly the "intrinsic self-review, no external signal" condition Huang et al. ICLR 2024 / Tyen et al. ACL 2024 predict rarely helps.
- **Arm C (Vacant installed)**: swap `generate()` for a solver that shells out to one of the four target CLI agents (headless, via `vacant do`) running *inside* the sandbox against the same `reference_files/`+prompt, with Vacant's Stop-hook feedback loop wired to a cheap "grounding" check translatable to this benchmark's specific shape — concretely: (a) did the agent's bash/python history show it ever `cat`/`open`/parse each file in `reference_files/` before writing a claim that cites it (Vacant's `trace/locate.py`+`blame.py` already do exactly this "value → first-written-step" trace, applicable unmodified); (b) any numeric/date/named-entity claim in `deliverable_text` or the deliverable files with no located source step gets flagged and sent back before delivery — this maps 1:1 onto the rubric's own "not fabricated" / "matches figures computable from the log" items seen in real rubric_json (§7 below has concrete examples), which is direct, independent confirmation that "ungrounded claim" is a real, judge-relevant failure mode on this exact benchmark, not a made-up one.
- What "check each step is justified / use the given materials / don't invent / verify before delivery" cashes out to concretely on GDPval, from the real rubric_json items pulled in this run (see §7): e.g. task `0ed38524…`'s rubric item *"Every issue or theme named in the talking points appears in the ECID Constituent Feedback Tracking Log.xlsx (in any district) and is not fabricated"* and *"Any quantitative references in the talking points match figures computable from the [reference log]"* are **exactly** the accountability-points CLAUDE.md's owner example describes (unsourced specifics in a deliverable) — this benchmark's own rubrics independently validate the target failure mode.

## 7. Calls/tokens per task; feasibility under call budgets

- **No official per-task tool-call or token count is published** anywhere found (paper, inspect_evals README, jeqcho's replication dataset card) — flagging as **unverified/not found**, not guessed. The paper only states aggregate human-vs-model time/cost (§4) and that OpenAI's own frontier-model runs used "the web search tool and the code interpreter tool, with background sampling" (arXiv 2510.04374, quoted verbatim, ar5iv text) plus a `best-of-N sampling with N=4` prompt-tuning variant (same source) — neither of these gives a call count.
- **What this run actually measured** (§3 Step B, real billed data, 1 task, minimal non-official sandbox, turn-limited to 8): 8 model calls, 23,640 prompt + 1,392 completion tokens, and the agent had **not yet started writing anything** by call 8 — still in file-discovery/dependency-troubleshooting. This is a strong signal that a *real* attempt at a GDPval task (with the actual data-science/office toolchain available, not our stripped sandbox) needs **well more than 8 turns** — the README's own mandatory-formatting-check prompt (`PROMPT_ELICIT_CAPABILITIES_SUFFIX`, not used by default but written for exactly this task) lists 5 sequential mandatory steps each involving multiple file/tool operations (convert to PNG, inspect each page, write programmatic checks, re-verify), consistent with dozens of turns per task for a serious attempt; treat any number below "tens of calls per task" as implausible and anything cited without a source as an estimate, not a measurement.
- **Under the 50 free-model-calls/UTC-day cap** (`MODELS.md`): even a conservative 10-20 calls/task estimate means **a single GDPval task can plausibly consume the entire daily free quota by itself**; running even a 3-5 task "sensible subset" per day on the free tier is optimistic, and the full 220-task gold set is not remotely feasible on the free cap (would take weeks at 1 task every few days, ignoring free-endpoint rate limits/availability MODELS.md already flags as volatile).
- **Under a 1000-calls/day cap**: at an estimated 10-30 calls/task, roughly **30-100 tasks/day** is plausible — a meaningful subset (not the full 220) per day.
- **In USD** (paid fallbacks per `MODELS.md`): this run's single task cost **$0.00207 for 8 calls / ~25k tokens** on qwen3.5-9b, but that task never got past file-discovery. A completed task (writing real PDF/XLSX/PPTX deliverables, reading multi-file references, going through several format/formatting-check iterations) would plausibly use 5-20× the tokens of this truncated run — order-of-magnitude **$0.01-$0.05/task** on qwen3.5-9b or gemma-3-12b-it — so the full 220-task gold set is very plausibly **$2-$15** on these cheap models (a real number is impossible to give without a completed run; flagging this as an estimate, not measured). The exhibition's own budget note ("儲值了五美金...儘管用") comfortably covers a subset (10-30 tasks) at this per-task order of magnitude, but not with headroom to also cover the other benchmarks this study is surveying in parallel, and **not with the official Docker sandbox**, which this container cannot build regardless of USD budget (disk, not money, is the binding constraint for GDPval specifically).

## 8. Unavoidable differences from the published/official runs (record every one)

1. **Sandbox**: ran against a 187 MB minimal substitute (`python:3.11-slim`, no LibreOffice/office-suite Python stack) instead of the official ~5-8 GB Dockerfile (147 pinned packages + LibreOffice + JRE + ffmpeg-dev + build-essential), because the official image's estimated size exceeds this run's disk budget (3-4 GB own budget, ~13 GB shared free at low point) and this container has no GPU/extra headroom to spare. **Consequence, demonstrated live**: a real model given this task in the substitute sandbox cannot read the `.xlsx` reference file at all (no openpyxl/xlrd/LibreOffice, no network to `pip install` them — Inspect's Docker sandbox launch does not route through this container's `$HTTPS_PROXY`). Any score obtained from this substitute sandbox would be **artificially near-zero regardless of model quality** and must never be compared to a real run.
2. **Dataset revision**: to see rubric_json/gold deliverable_files at all, one must diverge from the harness's own pinned `a3848a2a8...` revision (from before OpenAI added those columns) to `main` (or a newer explicit pin) — the harness as checked out literally cannot do local rubric scoring.
3. **Grading**: the official metric (blind pairwise win-rate vs. human expert, graded by evals.openai.com's GPT-5 judge or real human experts) cannot run here at all — no API/account access exists for evals.openai.com from this environment (task rules forbid sign-ups/web forms in general, and separately: WebFetch on evals.openai.com only returns an empty React shell, so even its account-requirement details could not be confirmed one way or the other — flag as **unverified**, not "no login needed"). Any local score (e.g. from parsing rubric_json with a small judge) is **by construction a different, non-official measure** and must be labeled as such if ever reported (this run did not build such a local scorer — out of scope for the smoke, noted for §Questions below).
4. **Turn/message/time caps**: official protocol has none of Inspect's `--turn-limit/--message-limit/--time-limit` set by default; this run added `--turn-limit 8` (mockllm and live smokes) purely to bound cost/time, which is why the live task did not finish.
5. **Model**: qwen/qwen3.5-9b (9B, fp4-quantized, pinned provider `darkbloom/fp4`) vs. the paper's evaluated set (GPT-4o/o4-mini/o3/GPT-5/Claude Opus 4.1/Gemini 2.5 Pro/Grok 4) — no overlap in scale or openness; this is intentional per the owner's instruction to stay small/local-like, but means no numeric comparison to the paper's own headline results is meaningful.
