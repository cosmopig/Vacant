## 1. Official protocol — exact commands, files, params

### Original repo (RUCKBReasoning/SpreadsheetBench)
- **Prompt template**, single-round: `inference/prompt_format.py:1-31` (`PROMPT_FORMAT_SINGLE`). Fields: instruction, spreadsheet_path, spreadsheet_content (first `--row` rows, default 5, rendered via `pandas.DataFrame.to_string()`), instruction_type, answer_position, output_path.
- Multi-round ReAct variants: `PROMPT_NO_DF_RCT_FORMAT` / `PROMPT_DF_RCT_FORMAT`, same file lines 33-95, add "`max_turn_num` rounds of interaction, two action types" text.
- **Inference driver, single-round**: `inference/inference_single.py`. `gen_solution()` builds one prompt per task, calls `get_llm_response` once, extracts a fenced code block (`extract_code`), executes it once via `code_exec.py` against a Jupyter-kernel Docker sandbox (`code_exec_docker/`), then separately (`run_solution()`) reruns the SAME extracted code against test cases 2 and 3 (string-substituting the input/output filenames) — i.e. the model only ever sees test case 1.
- **Inference driver, multi-round**: `inference/inference_multiple.py`. Settings `row_exec | react_exec | row_react_exec` (`inference/scripts/inference_multiple_{row,react,row_react}_exec.sh`). Loop caps at `--max_turn_num` (**default 5**, `inference_multiple.py:138`) turns of code-gen → execute → feed back stdout/traceback.
- **Model call**: `inference/llm_api.py` — plain `openai.OpenAI(api_key, base_url).chat.completions.create(messages=..., model=...)`. **No temperature/top_p/max_tokens argument is set anywhere in the client call** — whatever the provider's default is, is what was used. No `n`/pass@k parameter; single attempt per task (pass@1 only).
- **Code execution sandbox**: `code_exec_docker/` — two Docker images (`xingyaoww/codeact-execute-api`, `xingyaoww/codeact-executor`) running a persistent Jupyter kernel per conversation id, reached over HTTP at `--code_exec_url` (default `http://localhost:8081/execute`).
- **Evaluation / scoring**: `evaluation/evaluation.py:204-232`. Compares `{tc}_{id}_answer.xlsx` (ground truth) against `{tc}_{id}_input.xlsx` in the *original* script — **note**: the shipped `evaluation()` function as committed compares the answer file to the ORIGINAL input file, not to a model-produced `_output.xlsx` (the correct `outputs/...` path is present but commented out at `evaluation.py:215`); this is a repo bug/placeholder, not something we rely on — the real comparison logic lives in `compare_workbooks`/`cell_level_compare` (lines 33-188), which both the original and Harbor evaluators share almost verbatim. Cell comparison rounds floats to 2dp, converts Excel-epoch datetimes, treats `""`/`None` as equal, and requires exact type+value match otherwise (`compare_cell_value`, lines 18-47).
- **Pass criteria**: per task, `test_case_results` over 3 test cases (verified_400 has only 1 test case per task, see below) → `soft_restriction` = fraction passed, `hard_restriction` = all-or-nothing (1 iff all 3 pass). For `verified_400` specifically (1 test case/task) soft==hard, as the Harbor README states explicitly.
- **Recalculation backend**: `evaluation/open_spreadsheet.py` (added after the original NeurIPS release — see PR #32 below) opens every `.xlsx` and forces formula recalculation before `openpyxl` reads cached values; LibreOffice 7.5+ headless on macOS/Linux, `win32com`+Excel on Windows (auto-detected, or `--backend`). **The paper-era `win32com`-only pipeline was Windows-only**; LibreOffice support (used by Harbor) was added later via https://github.com/RUCKBReasoning/SpreadsheetBench/pull/32 — confirmed from the README's "Environment Setup" section and the Harbor adapter's "Modifications" note citing PR #32.
- Paper (arXiv:2406.14991, NeurIPS 2024 D&B spotlight) describes the same single-round/multi-round(ReAct) split and OJ-style 3-test-case eval; I did not find a discrepancy between paper text and code beyond the win32com→LibreOffice backend swap, which post-dates the paper.

### Harbor adapter (`adapters/spreadsheetbench-verified/`)
- **Task generation**: `src/spreadsheetbench_verified/adapter.py`. Clones/extracts `verified_400`, handles 3 upstream file-naming schemes (standard `{tc}_{id}_input/answer.xlsx`, `{id}_init/golden.xlsx` mismatched-ID, bare `initial.xlsx`/`golden.xlsx`) and normalizes to Harbor's canonical `{tc}_{id}_{input,answer,output}.xlsx`.
- **Task config**: `task-template/task.toml` — `network_mode="public"`, `timeout_sec=600.0` for both agent and verifier; `environment`: 1 CPU, 4096 MB RAM, 10240 MB storage, 0 GPU, `build_timeout_sec=600.0`.
- **Environment image**: `task-template/environment/Dockerfile` — `FROM python:3.11-slim`; `RUN pip install --no-cache-dir openpyxl==3.1.3 pandas==2.2.0 numpy==1.26.4`; mkdir `/app/{spreadsheets,output}` `/logs/verifier`. LibreOffice is **not** in this image (matches original: executor has no LibreOffice either).
- **Prompt seen by the agent**: `task-template/instruction.md`, filled by `adapter.py:237-245`. Same 5 fields as the original single-round prompt MINUS `spreadsheet_content` (agent can open the file itself) — this is a deliberate, documented deviation (README "Prompt Changes" section) from the original benchmark's externally-managed LLM loop, needed because Harbor drives an autonomous coding-agent loop rather than a single completion.
- **Oracle solution**: `task-template/solution/solve.sh` — copies `*_answer.xlsx` → `*_output.xlsx` verbatim (no code execution at all).
- **Scoring**: `task-template/tests/evaluate.py` — same `compare_cell_value`/`cell_level_compare` logic as upstream (byte-for-byte equivalent transform/compare functions), but with a hardened `parse_answer_position` fixing 11 correctness bugs the adapter found in `verified_400` (documented in `adapter_metadata.json` and README): 6 filename-resolution failures, 4 `answer_position`-parsing crashes (column-only ranges `A:G`, commas inside quoted sheet names, non-breaking spaces, spaces after commas), 1 vacuous-pass bug on `BD2:308` (empty comparison range silently "passing"). Writes `reward.txt` = soft reward (0.0–1.0) and `report.json`.
- **Test harness**: `task-template/tests/test.sh` — `apt-get install libreoffice-calc` **at verify time inside the verifier container** (not baked into the agent image, matching the original benchmark's separation of executor vs. evaluator environments), recalculates both output and answer `.xlsx` via `libreoffice --headless --calc --convert-to xlsx`, then runs `evaluate.py`.
- **Registry pin**: `harbor/registry.json`, 400 entries, `git_url=https://github.com/laude-institute/harbor-datasets.git`, `git_commit_id=0ad7209b09780e78c6c80f194e49e353191be1cc`.
- **Run commands** (README, verified against this session's own `harbor run` — see §3):
  ```
  uv run harbor run --dataset spreadsheetbench-verified --agent oracle
  uv run harbor run --dataset spreadsheetbench-verified --agent <agent_name> --model "<model_name>"
  uv run harbor run --config adapters/spreadsheetbench-verified/run_spreadsheetbench-verified.yaml --agent oracle
  ```

### (1) Which is "official"?
Both are real, and they are NOT the same protocol — they measure different things:
- **Original repo's own harness** (`inference_single.py` / `inference_multiple.py` + `code_exec_docker`) = the NeurIPS-2024 paper's actual eval: a *non-agentic*, externally-orchestrated LLM loop (the harness, not the model, parses code out of a chat completion and runs it in a Jupyter sandbox with 1–5 turns). This is what any published leaderboard number that cites the paper directly is measuring.
- **Harbor's adapter** = a *re-framing* into an agentic, file-based task: a coding agent (Claude Code, pi, etc.) is dropped into a container with the input `.xlsx` and told to produce the output `.xlsx` itself, using its own tools/loop, no externally-imposed turn cap beyond the 600s task timeout. It is a genuinely different harness that happens to reuse the same dataset and (fixed) scoring code.
- Harbor's own parity claim (README "Comparison with Original Benchmark") is **not** "Harbor reproduces the paper's numbers" — it is "Harbor's adapter pipeline == a *forked* copy of the original evaluation pipeline (`Rebabit/SpreadsheetBench@harbor-parity`) running the *same agent* (`claude-code@2.1.80`+`claude-haiku-4-5`)", 68.83% (fork) vs 68.25% (Harbor), 3 runs × 400 tasks, **agent-driven on both sides** — this is an adapter-migration parity check, not original-harness-vs-Harbor parity. I could not find any published number for a real agent (as opposed to the paper's single/multi-round LLM API loop) run through the *original* benchmark's own scripts, because the original scripts have no agent loop at all — only single/multi-round LLM completions.
- **For our comparison we use the Harbor adapter as the reference protocol**, because (a) it's the only one that supports an autonomous coding-agent loop, which is what Vacant hooks, (b) the owner's four target agents (pi/OpenCode/Claude Code/Codex) have no native way to run inside the original repo's completion-only harness without writing a new adapter ourselves, and (c) the adapter's 11 grader-bug fixes make it strictly more correct than upstream `evaluation.py` on `verified_400` (this is a Harbor-only claim, self-reported by the adapter authors — see `adapter_metadata.json`/README; not independently re-derived by me beyond confirming `evaluate.py`'s parsing code by inspection).

### Infra blocker + fix (recorded so it's reproducible, and so the 400-task run doesn't repeat it)
1. `uv run harbor ...` (no flag) resolves harbor's `[dependency-groups].dev` group by default, which pulls `harbor[tinker]`/`harbor[cloud]`/`harbor[computer-1]` → torch+full CUDA stack (~7.3GB in `~/.cache/uv` before any install even completed). **Fix: always pass `--no-dev`** (`uv run --no-dev harbor ...`); this installs only harbor's 22 base runtime deps (92 packages resolved, no torch/CUDA) and is sufficient for `harbor run`/`agent`/`dataset` commands. Reclaimed with `uv cache clean` (freed 7.3GB) before proceeding.
2. Harbor's docker-compose `build` step (`docker.py:717`, default bridge network, no `--network host`) failed `pip install openpyxl==...` inside the generated task Dockerfile with `SSL: CERTIFICATE_VERIFY_FAILED: self-signed certificate in certificate chain` against pypi.org. Root-caused (independently, then cross-confirmed against a sibling deep-dive's identical finding in `deep-Terminal_Bench_2_0_.../NOTES.md`): **all container egress in this sandbox is transparently TLS-intercepted regardless of docker network mode or explicit proxy env vars** — it is not conditional on `--network host`; the interception happens even on the default bridge network. `docker pull` succeeds because it's the Docker *daemon's* own outbound connection, not the container's network namespace. **Fix used**: pre-built a base image (`docker build --network host --build-arg HTTPS_PROXY=... -t sb-verified-base:py311-deps`, from a Dockerfile identical to the task-template's `FROM python:3.11-slim` + the exact pinned `pip install openpyxl==3.1.3 pandas==2.2.0 numpy==1.26.4` line) using `--network host` (where the loopback proxy at `127.0.0.1:36343` is reachable) and confirmed a subsequent `pip install` of the same exact pins is a no-op with `--network none` (pip skips the network entirely for an already-satisfied exact version pin). Then patched the 2 cached task Dockerfiles (`~/.cache/harbor/tasks/<hash>/<task_id>/environment/Dockerfile`) to `COPY` the CA bundle into the image and set `ENV PIP_CERT=... REQUESTS_CA_BUNDLE=...` before the `RUN pip install` line (confirmed this alone, keeping the *original* `FROM python:3.11-slim`, also works on the default bridge network with no `--network host` at all — i.e. the actual fix is "trust the CA", not "use host networking"; base-image prebuild above was belt-and-suspenders). **Both images (`sb-verified-base:py311-deps`, `python:3.11-slim`) were `docker rmi`'d after use.** LibreOffice's `apt-get install libreoffice-calc` in the verifier (`test.sh`) needed **no fix at all** — Debian's default mirrors are plain HTTP, not intercepted.
3. This is a workaround for *this sandboxed container only*; a normal machine (the owner's laptop, or the exhibition machine) has real unfiltered internet and none of this applies. Recorded here so the "unavoidable differences" list (§8) captures it honestly rather than silently.

## 5. Which agents can run under the official protocol

- **Harbor adapter (our reference protocol)**: `harbor agent list` (this session, harbor@6cb9ff31) shows `pi`, `opencode`, `claude-code`, `codex` all present as native Harbor agents (among ~50 total), confirmed directly (not from docs) by running `uv run --no-dev harbor agent list` and `harbor agent schema pi`. All four are "installed agents" (`harbor/src/harbor/agents/installed/`) that Harbor npm-installs inside the task container and drives via CLI, so **Vacant's hook-every-tool-call approach (which patches each agent's own native hook/extension mechanism) applies exactly as it does everywhere else** — Harbor doesn't wrap or sandbox the agent's own tool calls in a way that would block Vacant's hooks; it just orchestrates container lifecycle + prompt delivery + reward scoring around the agent's normal CLI invocation. I did not read `opencode.py`, `claude_code.py`, or `codex.py`'s full source (out of time budget) to confirm each one's custom-model wiring the way I did for `pi.py`, but the sibling `deep-Terminal_Bench_2_0` NOTES.md states (its own finding, not independently re-verified by me) that `MODEL_CONNECTION.passthrough=True` (the base-URL/API-key passthrough mechanism) is generic across 40+ agents including all four, "not narrowed to 3 providers" — flagging as secondhand.
- **Original repo's own harness**: no agent loop at all (see §1) — not applicable to pi/OpenCode/Claude Code/Codex, only to a raw completion API. To run any of the four "as an agent" under the *original* SpreadsheetBench, someone would have to write a new adapter (exactly what Harbor's team already did).
- **Official/alternative scaffolds**: none found specific to SpreadsheetBench beyond the paper's own scripts and Harbor's adapter — no mini-swe-agent/Terminus reference implementation for this benchmark (unlike, e.g., Terminal-Bench).

## 6. Adding arm C (Vacant) / arm B (reviewer-persona, no Vacant) without changing the protocol

- The Harbor task boundary is exactly the agent's own container + tool-call loop (`environment/`, agent runs `solve` via its native CLI, `tests/test.sh` runs afterward, untouched by the agent). Vacant's per-project hook (project = the task's working directory inside the container) attaches the same way it does for any other Harbor/coding-agent task: install Vacant's hook into the agent's own config before `harbor run` starts the trial (or bake it into a custom environment Docker image layered on top of `task-template/environment/Dockerfile`), let it record every read/write/exec step against `/app/spreadsheets/1_{id}_input.xlsx` and `/app/output/1_{id}_output.xlsx`, and let its Stop-hook loop fire before the agent's final turn — **all of this happens strictly before `test.sh`/`evaluate.py` ever runs**, so the benchmark's own scoring code, dataset files, and pass criterion are untouched. Arm C = same `harbor run` command, same task.toml/Dockerfile/dataset, agent config additionally points at Vacant's hook.
- Arm B (reviewer-persona self-check, no Vacant evidence) = same, but the only addition to the agent's prompt/loop is an instruction to "before finishing, take on the persona of an expert spreadsheet reviewer and re-check your own output" — with NO access to Vacant's recorded trace (which cells it actually read, which formulas it verified) — i.e. exactly the "intrinsic self-review, no external signal" condition the cited research (Huang et al. ICLR 2024; Tyen et al. ACL Findings 2024) predicts rarely helps.
- **What "check each step is justified / use the given materials / don't invent / verify before delivery" means concretely on this benchmark**, grounded in what actually fired in the one live trace I have (§3): (a) *used the given materials* = did the agent `openpyxl.load_workbook` the actual `1_{id}_input.xlsx` before writing any value into the answer range, vs. hard-coding a guessed value (Vacant's trace distinguishes "value traced to a read of the input file" from "value has no traced source" — a real ground-truth column reference like `PK01/P810760109` appearing in the agent's own earlier tool output but NOT making it into the final file is exactly the failure my live run produced); (b) *step justified* = does the row count / cell range the agent actually wrote match the row count / cell range it itself computed two tool calls earlier (my live run: computed 9 matches, wrote 5 — a self-consistency gap fully visible in Vacant's trace without ever looking at the answer key); (c) *verify before delivery* = did the agent's own "let me verify the output" step (present in my trace, `STEP 5`) actually re-read the FULL answer range and diff it against its own earlier computed values, or only spot-check a subset (in my trace it re-read only `B4:B12`/partial `E` values, not the full `E4:E12` it was scored on).

## 7. Model calls & tokens per task, and daily-budget math

- **From this session's own live trace (§3, task `10452`, pi + qwen3.5-9b, max_turns=15)**: **7 model calls**, **85,116 prompt tokens**, **4,546 completion tokens** (of which 1,807 reasoning), **$0.00740**, wall time contributing to a 2m26s total trial (includes container build+agent+verify). This is the only real per-task number I have for this exact benchmark+agent+model combination; I did not find published trajectory logs (the paper/Spreadsheet-RL don't release per-call logs, and Harbor's own parity run's raw trajectories are not bundled in the repo I cloned).
- Prompt tokens are large relative to completion because pi's system prompt + tool schemas + spreadsheet-reading tool outputs (openpyxl dumps of ~15 rows/columns) accumulate across 7 calls; this will scale up somewhat for larger/wider spreadsheets elsewhere in `verified_400` (I did not sample enough tasks to give a distribution, only 1 live task run — this is a single data point, not a benchmark-wide average).
- **Under the 50-free-calls/UTC-day cap**: at 7 calls/task, **≤7 tasks/day** on a free model (assuming similar call counts; some tasks may need fewer/more depending on max_turns and how quickly the agent converges or gives up). Covering the full 400-task set at this rate would take **≥58 UTC days** on free-tier alone — not remotely feasible on the free 50/day cap for a full-set run; only small subsets (5–10 tasks) fit in a single day.
- **Under a 1000-calls/day cap**: ~140 tasks/day at 7 calls/task → full 400-task set in **~3 days**.
- **In USD with the paid fallbacks** (`MODELS.md` "UPDATE" section): at $0.00740/task (qwen3.5-9b @ darkbloom/fp4 pricing, $0.08/M in + $0.13/M out) — **full 400-task set ≈ $2.96**; a sensible subset (e.g. 30–50 tasks spanning both instruction_types) ≈ **$0.22–0.37**. The other pinned paid candidate, `google/gemma-3-12b-it` @ deepinfra/bf16 ($0.05/M in, $0.15/M out — cheaper input, same-ish output pricing) would likely land in a similar per-task cost range given similar token counts, though I did not run it live to confirm (would need a second live smoke, which I judged not worth spending out of the $0.15 cap given the qwen3.5-9b run already answered the calls/tokens question this section needs).
- These are pi-specific counts; OpenCode/Claude Code/Codex will very likely differ (different system-prompt overhead, different default tool sets) — not measured here, flagged as a gap.

## 8. Unavoidable differences from published runs

1. **Harness identity, not just presence/absence of Vacant.** The only "official, parity-checked" number (claude-code+haiku-4.5, 68.83/68.25%) is on Harbor's *agentic* adapter, already one层 removed from the paper's own completion-loop harness — any Vacant-vs-no-Vacant comparison inherits that same one-step remove from the NeurIPS paper's literal numbers. Recorded honestly in §1.
2. **Split**: all small-open-model published numbers I found (Spreadsheet-RL, §4) are on the ORIGINAL 912-task split, not `verified_400`. A same-model run on `verified_400` will not be directly comparable to those percentages even before Vacant enters the picture — different (smaller, curated) task pool, single test case instead of three.
3. **Sandbox TLS/network workaround** (§3 infra note): this container's docker builds needed a CA-trust patch not present in any published run's environment; purely infra, doesn't touch task content, dataset, or scoring, but is a difference in how the environment was provisioned that a from-scratch reproduction on a normal machine would not need.
4. **Base image identity for the 2 smoke tasks**: I temporarily pointed at a locally pre-built `sb-verified-base:py311-deps` image during debugging, then reverted the adapter's own template to the stock `FROM python:3.11-slim` and instead patched only the 2 cached task Dockerfiles directly (not the adapter source) — so **the actual final images used for both the oracle and pi live runs are byte-identical to what a fresh `harbor dataset download` would produce, plus 3 inserted lines (COPY ca-bundle + 2×ENV) that add nothing at runtime beyond CA trust**. Recorded for transparency; both extra images were deleted after use.
5. **Model/quantization**: the owner's live smoke used `qwen/qwen3.5-9b` pinned to a specific OpenRouter provider/quantization (`darkbloom/fp4`) chosen to resemble a locally-run quantized small model per the owner's explicit instruction — this is not a model that appears in any published SpreadsheetBench table (published Qwen3 numbers use presumably-unquantized weights via whatever inference stack Spreadsheet-RL's authors used, not specified beyond "Qwen3-*" names in the table I read).
6. **Single-task, single-run live smoke**: my live pi run is n=1 on 1 task — no variance estimate, no statement about typical qwen3.5-9b performance on this benchmark, only a concrete existence proof of (a) the plumbing working end-to-end, (b) real per-task cost/token numbers, (c) one real (non-infra) failure mode worth noting for the accountability-evidence design.
