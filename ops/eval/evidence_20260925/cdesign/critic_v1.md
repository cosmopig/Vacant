## (blocker) Rounded or float-noise values are flagged as 'unsourced': correct DABstep answers get pushed back
DETAIL: DABstep asks 'Round to 2 decimals'. The usual agent flow prints a full-precision float and then writes the rounded value (`echo 0.55 > answer.txt`, or a write tool). I checked locate.contains, the matcher that blame uses: ('0.5500000000000001','0.55'), ('fee = 0.549999','0.55'), ('mean 12.3456','12.35'), ('rate 0.082','8.2%') and ('1198050','$1.2M') all return False (probe output is in scratchpad/cdesign/critic/probes.txt). The echo step types the value itself: typed=True, no source contains it, the origin is agent and the chain has a single step, so blame says `direct`. The design would call that 'unsourced'. derive.py (§5.3) only recognises aggregates over tables, ratios, sums/differences and date formats. Rounding a single observed number, float noise, scientific notation, ×100 percentages and M/K abbreviations are not listed. The S1 N1 fixture avoids this only because its script prints exactly 365950. Result: correct DABstep answers receive 'no source found … open the given files or compute the value in a command and redo'. That spends a round under max_turns=15 and can turn a right answer into a wrong one, which is the harm metric in decision §6.6.
FIX: In derive.py, and also as a pre-check before blame, treat a written number as derived when some observed number (in the window's tool outputs or read contents) rounds to it at its printed precision. Cover half-up, half-even and truncation; strip float noise (repr of float), scientific notation, ×100 with %, and ÷1e3/1e6/1e9 with K/M/B affixes. Add negative fixtures D2b (prints 0.5500000000000001, writes 0.55), D2c (prints 0.08198…, writes 8.2%) and N1b (reads the sales, writes '$1.2M'). Each must produce 0 pushbacks.

## (blocker) The 'opened' matcher misses absolute paths, so it fails on Harbor's /app/data/ layout
DETAIL: §5.1 says a shell command observes a material when it contains the relative path or basename 'as a whole token bounded by start/end/quote/space/(/)/,/='. '/' is not a boundary, and absolute paths are never mapped back to workspace-relative ones. Harbor's DABstep instruction.md says 'reference files in `/app/data/`' (notes/deep-DABstep.md L102). Agent code therefore reads '/app/data/fees.json', `f"{DATA}/manual.md"` or `data_dir + '/manual.md'`. Neither 'data/fees.json' nor 'fees.json' sits between allowed boundaries there, so a correct run gets 'Not opened in the recorded steps: data/fees.json …'. The prompt-token matcher (a)–(d) also never defines how the absolute token '`/app/data/`' (with backticks) maps to the index. As written it either matches nothing, so D1 is silently missed in the real benchmark, or it matches after punctuation-stripping has mangled it. The acceptance fixtures D1/D2 use the relative 'data/' and a relative cwd, so none of this is exercised.
FIX: Resolve every path-like substring in the command text, whether absolute, ./-relative, or built by string concatenation or f-strings (match the '/<rel>' suffix), against the hook cwd and the project root. Add '/' and '{' '}' '+' as left boundaries for the basename match. For prompt tokens, strip backticks and quotes only, keep '/', and map absolute paths under the project root to relative ones. Rebuild D1/D2 from the verbatim Harbor instruction.md, with cwd=/app and all 7 context files.

## (blocker) Materials named only by a directory push back on correct work (DABstep: 7 files, most tasks need 1–3)
DETAIL: Rule (d) turns a directory token into 'every file under it'. unread_material is pushable in round 1 whatever else the result contains. In DABstep the prompt names /app/data/ with 7 files: payments.csv, fees.json, manual.md, merchant_data.json, acquirer_countries.csv, merchant_category_codes.csv and payments-readme.md. The study's own live run shows the correct dabstep-5 answer needs neither manual nor fees (deep-DABstep.md L222-226), and correct runs rarely open acquirer_countries/merchant_category_codes. So nearly every C trial, correct ones included, gets one pushback: 'open the ones the deliverable depends on and redo those parts'. C then behaves like 'always one generic extra round', which is exactly the no-external-signal self-correction that decision §2.2 cites as useless or harmful. It also empties the 'C on zero-finding tasks' comparison (decision §4.3). The accept spec's D2 opens all 4 fixture files, which hides the problem. The OS read witness in §6.4 cannot catch it either: the file really was not opened, and it simply was not needed.
FIX: Keep unread_material in the note only, unless (a) the prompt names that file individually (by basename or path), or (b) the same Stop already has another pushable finding in a deliverable (for example an unsourced value, as in D1). In case (b), put the unread directory members on that finding's line. Add negative D2d: a correct answer from payments.csv only, with manual.md and fees.json never opened. It must get 0 pushbacks.

## (blocker) dropped_values fires on ls/grep/find output and on 'pick one of these' answers, and pushes the agent to break answer.txt
DETAIL: The list source is any successful window shell step whose output holds ≥3 tokens of ≥4 characters containing a digit or / - _. Listing and search commands qualify. `ls /app/data` prints payments-readme.md, merchant_data.json, acquirer_countries.csv and merchant_category_codes.csv. `grep -rl parse_date pkg tests README.md` and `find` print path lists (in N3b every line contains '/'). DABstep also prints candidate lists such as merchant names with underscores (Crossfit_Hanna, Belles_cookbook_store, Golfclub_Baron_Friso, Martinis_Fine_Steakhouse, Rafa_AI) or MCC codes (5411, 5812 …), and then correctly answers with one of them. Then M=1 < N, the prompt holds no '1' and no 'top 1', and the final message does not name the others, so a finding fires: 'answer.txt: 1 of the 5 values printed at step n are in the file; … Action: write all of them'. Doing what it says makes the DABstep scorer fail. In a repo, any README that mentions one path from an earlier grep also fires. None of the negative fixtures (N7 only) exercises listing commands or selection answers.
FIX: Take lists only from steps that ran code reading a material (not ls/find/tree/grep/rg/git or the other probe words). Require the deliverable to be a sheet or CSV, or to contain ≥2 of the tokens as a contiguous block (a list that was started and cut short). Never apply the check to a deliverable whose prompt says 'only'/'single'/'the answer', or to one-line files. Add negatives: ls-then-mention, grep -rl then a README edit, and 'which merchant has the highest X' answered with one name.

## (major) 'Unsourced' has two definitions that disagree; the hop-based one lets agents clean invented values by re-reading them and makes the note claim 'Fixed' when nothing was fixed
DETAIL: §5.2 defines unsourced as 'fault agent, located, source None, and every chain hop is the actor's own write', then says 'This is blame's direct condition'. They are not the same. blame.py L1175 sets direct only when the chain has exactly one step. A round-2 rewrite of plan.md that keeps 'October 1, 2026' produces the chain [wrote plan.md (r2), its own earlier write (r1)], which is not direct. Under `direct` the S8 finding vanishes in round 2, and stopcheck/feedback compute resolved = prev_open − now (feedback.py L203, stopcheck.py L126). The chain then records 'resolved' and the note says 'Fixed' while the value is still in the file. Under the hop rule, any 'observation hop' counts as sourced. So a very common step, `cat plan.md` or `grep -n 'October' plan.md` to re-check the draft, makes its invented values 'sourced' ('the command read plan.md' → back to its own write). The same goes for a sub-agent that invented a value: the 'a sub-agent's reply' hop counts as sourced, so on Claude Code, which delegates heavily, invented values are 'traced'. The note would then say 'k traced to files or commands' for values that were never observed.
FIX: Classify by where the chain ends, not by which hops it passes through. Unsourced ⇔ origin.kind=='agent', the origin step typed the value (the value is literally in that step's input: a write/edit tool, or echo/heredoc text), and nothing in the chain ends at an input, prompt, pre_existing, external or command-computed origin. Reads of files the same actor wrote do not count as sources. Compute 'resolved' from the value's presence at its location, never from 'the id was not regenerated'. Add S8 variants where round 2 does `cat plan.md` before rewriting, and N8b where a sub-agent invents a value.

## (major) Numbers from general knowledge, today's date and everyday units are flagged in document tasks that give no materials
DETAIL: Values are extracted from every document deliverable whether or not the task gave any source. 'README: returns HTTP 404', 'runs on port 8080', 'brew at 85°C for 3 minutes', '12 months', '100%', 'Python 3.12 was released in October 2023', and above all 'Report date: September 25, 2026'. The date comes from the agent's system prompt, which the chain never records. All of these have ≥2 significant digits or a full date and no recorded observation, so they are pushed back with 'open the given files or compute the value in a command … or label each value as an assumption'. The agent then labels real facts as 'assumptions'. The person's document gets worse, which goes against 產品原則 ('成果可以比我沒有安裝還好'). No negative fixture covers a knowledge-writing task or a dated report.
FIX: Push unsourced_value only when the task named materials, or when the value's surrounding line or sentence mentions a named material. Otherwise list it in the note only (Unverified: 'not traced to anything this task read'). Always exempt today's date and the session start date in every format, and a table of common units and constants. Add negatives N9 ('write an explainer of HTTP status codes in notes.md', no materials) and N10 (a status report dated today).

## (major) Script-computed reports can be flagged; derive.py cannot see CSVs that are referenced only inside a script
DETAIL: Take `python3 make_report.py`, where the script reads sales.csv and writes report.md itself. blame._shell_origin returns Origin('agent', note='make_report.py computed the value') with the chain [wrote report.md, wrote make_report.py, which the command ran]. Under the design's hop rule, every hop starts with 'wrote …', so every number in the report is 'unsourced'. derive.py only builds tables from read-tool output or 'a shell step mentioning the path', and here the CSV path lives inside the script, so it cannot rescue them. The same happens to `python3 solve.py > answer.txt`. This penalises the most rigorous behaviour (write a script, run it). The persona line itself says 'or a computation done in this task'.
FIX: Treat a value produced by running a script the agent wrote in this task, with that step succeeding, as 'computed in this task' (sourced for the pushback; the note says 'computed by <script>'). For derive.py, count a CSV as observed when an agent-written script that the window ran mentions its path (the same rule §5.1 already uses for materials).

## (major) Ordinary words that match a directory name become materials ('run the tests' → every file in tests/); N3b as specified would likely get pushed back
DETAIL: Prompt tokens are stripped of punctuation and matched against directory names. The N3b prompt 'Rename parse_date … and run the tests.' yields 'tests', which equals the tests/ directory with 50 files. Past the cap of 30 the rule keeps 'only files directly inside', which is still all 50. `python3 -m unittest` and `grep -rl … tests` do not mention each file by path or basename, and 'tests' is not a glob. So all 50 are 'not opened', and N3b's '0 pushbacks' fails. The same happens with 'docs', 'data', 'src', 'build', 'scripts' and 'config' in everyday coding requests. A large directory can even become hundreds of materials.
FIX: Count a directory as a material set only when the token is path-like (contains '/', or is quoted or backticked) and the prompt asks to use its contents. Count recursive commands that take the directory (grep -r, rg, find, ls -R, glob in code, os.walk/Path.rglob on it) as observing every file under it. If a directory holds more than ~10 files, keep it note-only. Put N3b's exact prompt through the L0 tests.

## (major) date_outside_data matches generic column names: S2's own line 6 'Launch Date: November 15, 2026' fires
DETAIL: The rule fires on a sentence containing the CSV stem or a column name as a whole word, plus a full date outside min..max, and no in-range date. sales.csv has the columns date, region, amount. The recorded deliverable scratchpad/evalrun/try1/ws/report.md line 6 is '- **Launch Date:** November 15, 2026'. It contains the column name 'date' (plural and case tolerated), a date outside 2026-07-01..05 within ±2 years, and no in-range date, and it is not a heading. It would get a finding telling the agent that the correct launch date conflicts with the data. The S2 pass criterion 'exactly one evidence line' then fails. The same false positive hits N4 whenever the launch-date line exists.
FIX: Exclude generic column names (date, time, day, month, year, id, amount, value, total, count, name, type) from the tie words, and use only the file stem and domain-specific column names. Also exempt key:value lines whose key names a different event ('Launch Date:', 'Due:', 'Deadline:'). Add S2's line 6 to the L0 test as a negative.

## (major) write_before_read penalises checking materials after writing
DETAIL: The check fires when deliverable D was written before material M was first opened and D was not rewritten afterwards. That is the pattern of an agent that drafts, then opens the schedule or data to double-check, finds everything consistent, and leaves D alone. The product wants that behaviour and this check punishes it. A `file logo.png` run just to confirm the logo exists also fires.
FIX: Fire only when M holds a value, or a date/number from the same field, that differs from what D says; otherwise send it to the note. Or drop the check: an unsourced value already covers a draft written before its source was read.

## (major) failed_step_ignored pushes back on environment failures the agent correctly routed around
DETAIL: Probes (R6) cover ls/which/grep/cat and similar. In offline containers such as Harbor's, and on real machines, agents often run `pip install pandas` (network error), `python3 -c 'import openpyxl'` (ModuleNotFoundError) or `npx …` (ENOTFOUND), then carry on with the stdlib. None of these counts as a probe. They are not re-run successfully, name no file the agent wrote, and are usually not mentioned in the final message. The review then says 'fix and re-run, or say in the final message that it failed', and the agent retries doomed installs and burns turns under max_turns=15.
FIX: Only flag failures of steps that ran an agent-written script or read a given material and came before a deliverable was written (the S5 shape). Treat package installs, import checks, `--version`, network fetches and tool-availability checks as probes. Count 'a later successful step producing the same deliverable by another route' as handled.

## (major) Project checks run the person's build and test commands on every code Stop, with no consent and a large latency cost
DETAIL: Discovery runs `npm run build|lint|typecheck|test`, `make test|check`, `cargo test`, `go test ./...` or pytest twice (before and after copies), up to 120 s each and 300 s in total, on every Stop that changed code. On macOS there is no bwrap, so the 'plain sandbox' has the network and absolute-path access (localhost databases, ~/.config via absolute paths, deploy steps hidden in `make check`). This is arbitrary project code executed by default by an install the person believes is passive. In a TUI, every turn that touched one file makes the person wait for two full suites plus two materialisations (up to 20k files / 200 MB) before control returns. G6's 'Stop p95 ≤ 2 s' is measured without project checks, so it does not describe the default. In Terminal-Bench, C's wall-clock budget is spent on Vacant's test runs.
FIX: In zero-config, default to re-running only the test command the agent itself ran, on the after copy, and only when a test claim or a code change after the last green run needs it. Cache the 'before' result per window-start index. Put 'run the project's own checks' behind an explicit opt-in (or the contract). Report G6 with project checks on.

## (major) An always-on, permanent project chain slows down with time, grows without limit, and can switch itself off for good
DETAIL: In zero-config, every project the person opens gets one chain that lives forever. Each Stop calls rec.verify(), a signature check over the whole chain; I measured Ed25519 verify at ~122 µs per entry here, so 30k events (a few hundred sessions) is about 3.7 s per Stop before any evidence work. rec.events() is fully re-parsed by classify_prompt on every prompt and by _actor_tokens. The first look stores a blob of every file up to 8 MB (workspace.py L210), and every tool output up to 2 MB, including `cat config.yaml` or `env` output with secrets (only secret file names are hash-only). That is a full, unencrypted copy of every repo, with no retention or GC. Before this change, recording was opt-in (a contract or VACANT_TRACE=1). One truncation or corruption, from a full disk or a crash mid-write, makes verify() false forever: that project is never checked again and prints 'the record of this task does not verify' on every task.
FIX: Split the chain into segments per session (or per person request) with a signed link to the previous head, and verify only the current segment plus the link. Add retention: keep N days or X MB and GC unreferenced blobs, configurable only through `vacant uninstall --purge` and data-dir docs, not a new setting. When a segment is broken, start a new one and say so once. Tell the person at install time, in one line, that tool outputs and file versions are stored locally, and say how long they are kept.

## (major) Arm C in the benchmark would use settings no user has (VACANT_MODE / VACANT_HOME), which breaks 產品原則 3
DETAIL: §3 keeps env VACANT_MODE 'for benchmark arms', and decision Appendix A sets VACANT_HOME=/logs/agent/vacant for C. 產品原則 3 says the C container may use only the install commands a user would run. If C sets either variable, the benchmark measures a configuration the product never ships: state goes to a different directory, and the mode is not resolved from install.json. The design does not say how C's records are collected without these variables. It also does not say how 'vacant install ran before pi existed ⇒ pi skipped ⇒ C = A' is detected.
FIX: Arm C: run exactly the documented commands, with no Vacant env vars. After each trial, the harness copies $HOME/.vacant out of the container. Each C trial must assert that install.json lists pi and that the chain holds step and Stop events; if not, it is a C failure (ITT), not a silent A. Keep VACANT_MODE for tests only, and write that rule down in the preregistration.

## (major) 'Exactly two commands, no restart' is not true on common systems
DETAIL: `pipx` is not installed by default (macOS needs brew, Ubuntu needs apt). `pip install --user` is refused under PEP 668 ('externally-managed-environment') on Debian 12, Ubuntu 23.04+ and Homebrew Python. requires-python>=3.11 fails on Ubuntu 22.04 (3.10) and on stock macOS python3 (3.9). `pipx ensurepath` or ~/.local/bin needs a new shell (the install audit had to export PATH by hand). There is also a known collision: PyPI's `vacant` package installs a different `vacant` binary (README L102). So the real minimal path is often 3–5 steps, and the design and README would be making a claim that is wrong.
FIX: Ship one documented path that works on a bare machine: a `uv tool install vacant-network` or pipx one-liner plus `vacant-network install`, which also covers the name collision; or a small install script that checks the Python version and PATH. Make `vacant install` print the exact PATH fix when its own bin directory is not on PATH. Test the documented commands in usersim on ubuntu:24.04 and debian:12, not only python:3.11-slim.

## (major) 'Label as an assumption' and the disclosure rule damage single-answer files and let the model disclose instead of fixing
DETAIL: Every unsourced line ends with '… or label each value as an assumption'. The D1 expected review says the same about answer.txt. ## (major) Persona and unread actions nudge the agent to read huge files into context
